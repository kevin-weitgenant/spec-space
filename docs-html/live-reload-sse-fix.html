Fix: live-reload travava a 7ª aba

Um EventSource eterno por aba esbarrava no limite de ~6 conexões HTTP/1.1 por origem. A 7ª aba de docs ficava "carregando" para sempre. O fix: um único SSE multiplexado no manager + eleição de líder no browser via Web Locks + retransmissão por BroadcastChannel.

1O sintoma

O que o usuário via, em linguagem crua.

Com o manager servindo N pastas de docs num único processo (localhost:4400/<slug>/), abrir muitas abas de docs no mesmo browser produzia um comportamento estranho e 100% reproduzível:

  • As 6 primeiras abas carregavam normalmente, com live-reload funcionando.
  • A 7ª aba em diante ficava "carregando" para sempre — página branca, spinner, nada.
  • Fechar uma das 6 abas antigas liberava imediatamente uma das abas travadas.

Reproduzido empiricamente via CDP (Chrome DevTools Protocol) abrindo 7+ abas programaticamente: só as 6 primeiras completavam o load. O número 6 gritava "limite de browser", não "bug de lógica" — mas isso só ficou óbvio depois da investigação.

Por que era grave
O docs-in-html é usado com muitas abas abertas ao mesmo tempo (uma por doc em edição, mais o shell por raiz). Travar na 7ª aba tornava o manager inutilizável no fluxo real de trabalho.

2A investigação

Como se chegou da "aba travada" ao limite de conexões.

Primeiro desconfiado: o servidor

A hipótese inicial foi que o manager estava lento ou travando ao servir a 7ª raiz. Teste direto:

  • curl na URL travada respondia em ~1ms — servidor saudável.
  • O log do manager mostrava a requisição da página chegando e o HTML sendo enviado.
  • O HTML chegava ao browser, mas a aba continuava "carregando".
Diagnóstico-chave
Se o servidor responde em ~1ms e mesmo assim a aba não termina o load, o bloqueio é client-side: a aba está esperando algum recurso que nunca completa. "Nunca completa" + "conexão viva" = uma requisição pendurada para sempre. A lista de recursos que cada aba pedia: HTML, CSS, JS… e um EventSource SSE eterno.

Fechando o cerco

Olhando o client/reload.js da época: cada aba injetada fazia new EventSource("/__reload__") — uma conexão HTTP que nunca fecha, por design (é o que faz o live-reload ser "live"). Com 6 abas, o browser esgota seu pool de conexões para aquela origem; a 7ª aba pede seu próprio HTML+recursos e o browser não tem slot para atendê-los. Contando as conexões via CDP: 6 EventSource pendurados. Número redondo demais para coincidência.

3A causa raiz

O limite de 6 conexões HTTP/1.1 por origem — explicado do zero.

Rampa: o limite de conexões, para quem nunca ouviu falar

Quando seu browser conversa com um servidor em HTTP/1.1, cada pedido usa uma conexão — como uma linha telefônica dedicada. Para que um site lento não monopolize a rede, os browsers limitam quantas linhas simultâneas você pode abrir para o mesmo servidor (origem): o Chrome e o Firefox usam ~6.

Páginas normais não sofrem com isso: pedem HTML, CSS, imagens, e cada linha é liberada quando a resposta termina. O problema é o SSE (Server-Sent Events): por natureza, a resposta nunca termina — o servidor mantém a linha aberta para empurrar eventos quando um arquivo muda. É a funcionalidade inteira, não um bug do SSE.

Logo: 1 aba com SSE = 1 linha permanentemente ocupada. Com 6 abas, as 6 linhas estão tomadas por EventSources. A 7ª aba não consegue nem baixar seu HTML. É um clássico do desenvolvimento web — a mesma armadilha derruba apps com muitos websockets e iframes.

Por que o design antigo escalava mal

CamadaComportamento antigoConexões no browser
Client (reload.js)1 EventSource por aba, aberto no load1 por aba, eterna
Serve single-rootSSE em /__reload__ da própria raizN abas = N conexões
Manager multi-rootCada raiz com seu próprio canal SSEN abas = N conexões (mesmo pior: multiplicável por raiz)

O orçamento é da origem (localhost:4400), não por raiz/slug — ter 10 raízes não aumenta o limite. A conclusão da investigação vira a especificação do fix: o browser inteiro pode ter no máximo 1 conexão SSE com o manager. Todo o resto do design deriva disso.

4O fix

Três peças: multiplexação no servidor, eleição de líder no cliente, filtro por raiz no receptor.

Antes : aba 1→SSE · aba 2→SSE · … · aba 7 — sem conexão, travada
Depois : aba-líder→1 SSE único /__reload__ →BroadcastChannel →todas as abas (filtram por raiz)

Antes: N abas = N SSE (máx 6). Depois: o browser inteiro = 1 SSE, retransmitido localmente.

Peça 1 — Hub SSE único no manager (servidor)

O manager passou a expor um único canal SSE em /__reload__ na raiz do servidor, carregando eventos de todas as raízes. Cada evento é etiquetado com sua origem:

// manager.js — cada root watcher alimenta o hub via callback
function makeRoot(dir, slug) {
  return createRoot(dir, { base: "/" + slug, onReload: (rel) => hubBroadcast("/" + slug, rel) });
}
// evento no fio: { "base": "/slug", "path": "arq.html" }

O encadeamento: reload.js ganhou o parâmetro onEvent(relPath) (dispara para cada mudança de arquivo); roots.js repassa opts.onReload para o createReload(root, opts.onReload) de cada raiz; o manager conecta esse callback ao hub. Assim, um save em qualquer raiz vira um evento {base, path} no canal único.

Compatibilidade single-root
O serve de raiz única continua mandando {path} sem base — e o cliente novo trata isso: sem base, não há filtro e o evento vale para todos. Nenhuma regressão no fluxo original.

Peça 2 — Eleição de líder no cliente (browser)

Se só pode existir 1 SSE por browser, quem o segura? Uma aba eleita, via Web Locks API (navigator.locks):

// client/reload.js (essência)
var bc = new BroadcastChannel("docs-in-html");
bc.onmessage = (e) => onEvent(e.data);          // seguidores recebem aqui
navigator.locks.request("docs-in-html-sse", { mode: "exclusive" }, (lock) => {
  if (!lock) return;                             // não ganhou — vira seguidor
  openSSE((raw) => {
    bc.postMessage(raw);                         // retransmite TODOS os eventos brutos
    onEvent(raw);                                // e também se aplica
  });
  return new Promise(() => {});                  // segura o lock pela vida da página
});
  • Eleição: todas as abas pedem o lock "docs-in-html-sse"; a primeira vira líder, as demais ficam pendentes (seguidores).
  • Retransmissão: o líder retransmite todos os eventos brutos — de todas as raízes — via BroadcastChannel('docs-in-html'), que chega instantaneamente a todas as abas da origem sem consumir nenhuma conexão HTTP.
  • Failover automático: fechar a aba-líder libera o lock e a próxima aba pendente assume o SSE — sem intervenção, sem timer.
  • Fallback: browsers sem Web Locks/BroadcastChannel caem no SSE direto por aba (comportamento antigo; ok com poucas abas).

Peça 3 — Filtro por raiz no receptor

Como o canal é compartilhado por todas as raízes, cada receptor filtra antes de agir, comparando o base do evento com o seu próprio window.DOCS_BASE (definido na injeção por inject.js; vazio no single-root):

// client/reload.js
function onEvent(d) {
  if (!d || !d.path) return;
  if (typeof d.base === "string" && d.base.replace(/\/+$/, "") !== BASE_N) return; // outra raiz → ignora
  if (shouldReload(d.path)) location.reload();
}

Só depois de passar no filtro o shouldReload roda (arquivo sou eu? asset compartilhado? o shell só recarrega consigo mesmo, preservando o estado da sidebar).

5Lições do caminho

Dois erros intermediários que quase entregaram um fix que não fixava.

Erro 1 — Eleição global, SSE por raiz

A primeira tentativa fez a eleição de líder por raiz: uma aba-líder por slug, cada uma com seu próprio SSE em /<slug>/__reload__. A lógica parecia certa, mas…

Por que falhou
O limite de ~6 conexões é por origem, não por raiz. N raízes = N conexões SSE (uma líder cada) — o mesmo teto estourado, só que agora distribuído. A lição: orçamento de conexão é da origem, então a deduplicação também tem que ser da origem. Daí o hub único multiplexado na raiz do manager.

Erro 2 — Líder filtrando antes de retransmitir

Na segunda tentativa, o líder já filtrava os eventos pela sua própria raiz e só retransmitia o que sobrava:

Por que falhou
O líder de uma aba da raiz A descartava os eventos das raízes B, C… — e as abas seguidoras dessas raízes ficavam cegas aos próprios eventos (live-reload morto nelas). A lição: o líder é um canal burdo (dumb pipe) — retransmite TUDO cru; o filtro é responsabilidade de cada receptor, que é o único que sabe qual é a sua raiz. Filtrar o mais tarde possível, no destino.

6Como validar

O protocolo usado na validação do fix — e que você pode repetir.

Carga: 10 abas simultâneas via CDP

  1. Suba o manager com várias raízes registradas (localhost:4400).
  2. Via CDP, abra 10 abas de docs de uma vez e espere os loads.
  3. Esperado: 10/10 completam o load (antes do fix: só as 6 primeiras). No DevTools → Network, deve haver exatamente 1 conexão __reload__ pendurada, segurada pela aba-líder.

Reload em aba seguidora

  1. Escolha uma aba que não é a líder (Network sem SSE próprio).
  2. Edite no disco o doc aberto nela.
  3. Esperado: recarrega sozinha em ~150ms (debounce do watcher) — provando que o caminho líder → BroadcastChannel → seguidor funciona.

Filtro por raiz

  1. Com uma aba aberta na raiz docs-html-docs, edite um arquivo de outra raiz.
  2. Esperado: a aba de docs-html-docs não recarrega (evento {base} diferente do seu DOCS_BASE).

Single-root sem regressão

  1. Rode o serve de raiz única (docs serve na pasta) e abra um doc.
  2. Esperado: SSE em /__reload__ enviando {path} sem base; o cliente novo aceita (sem base, sem filtro) e o reload funciona como sempre funcionou.

Failover do líder

  1. Identifique a aba-líder (a do SSE no Network) e feche-a.
  2. Esperado: outra aba assume o lock e abre seu próprio SSE; edite um arquivo para confirmar que o reload continua vivo em todas as abas.
Nota de migração
Abas que já estavam abertas com o reload.js antigo mantêm o comportamento velho até serem fechadas e reabertas — em particular, uma aba-líder antiga continua segurando o lock docs-in-html-sse com seu SSE por raiz. Após atualizar o projeto, feche todas as abas de docs e reabra-as para o comportamento novo valer em todo o browser.
