Plano: docs-in-html Manager

Um supervisor único que descobre, inicia e navega entre todas as suas instâncias de docs — uma URL no browser, um clique para abrir o Warp na pasta certa.

1Contexto

O problema que você já vive hoje, e o que o ecossistema atual fornece de gancho.

A dor
Cada projeto tem sua pasta de docs servida pelo docs-in-html na unha. Isso significa: (a) lembrar quais pastas têm docs, (b) abrir um terminal em cada uma, (c) rodar o serve (e caçar portas que colidem), (d) abrir outra sessão do pi/Warp naquela pasta quando quer que o agente edite as docs. Com N projetos, são 2N rituais manuais por dia.

O marcador já existe

O _config.json é criado pelo init (e auto-scaffoldado pelo serve) em toda pasta de docs — é o contrato perfeito de descoberta: se existe dir/_config.json, aquilo é uma instância de docs. Como contrafato, toda pasta de docs também tem HTML, mas _config.json é mais específico e barato de testar (um stat por diretório).

Detalhe do repo atual
As peças necessárias já estão lá como funções reutilizáveis — buildTree (manifest.js), SHELL (shell.js), injectScripts (inject.js), readConfig/applyShellConfig (config.js) e o live-reload (reload.js). O que falta é juntá-las num contexto por raiz em vez de globais de um único serve — ou seja, a arquitetura D é mais evolução natural do que ruptura.

2Intuição

Não gerencie servidores; gerencie docs. O resto deriva disso.

Um scan global parece a resposta óbvia, mas inverte o controle: você deixa o estado do seu ambiente depender de varreduras de disco. A intuição melhor é:

  1. Não gerencie processos; gerencie pastas. A unidade de registro não é “um servidor rodando” — é “um diretório de docs”. Servidores valem e caem; a pasta é o que persiste.
  2. Um registro persistente (~/.docs-in-html/registry.json) mapeia slug → {dir, título}. Registrada uma vez, a pasta é servida/watchada sempre que o manager existir.
  3. Um único processo, uma única URL. O manager é um serve multi-raiz: localhost:4400/projeto-x/… resolve direto no processo, com um watcher por docs. Você nunca mais decora portas nem spawna nada.
  4. Scan é import, não runtime. A varredura por _config.json acontece uma vez (e sob demanda) para popular o registro — depois disso, o manager só observa o que foi registrado.
Browser→ Manager :4400 (multi-raiz)→ watcher projeto-x · watcher specs-api

Uma porta para o mundo de fora; um watcher por docs por dentro.

3Abordagens analisadas

Quatro caminhos, do mais ingênuo ao mais robusto.

A. Scan global contínuo do filesystem

Varrer C:\Users\kevin (ou $HOME) recursivamente atrás de _config.json, a cada abertura do manager. Funciona, mas:

  • Custo real e alto. Um perfil de usuário tem facilmente 10⁵–10⁶ diretórios (node_modules, .git, caches, AppData). Mesmo pulando essas pastas, uma varredura completa em Windows custa de segundos a dezenas de segundos — e você pagaria isso a cada uso.
  • Watchers inviáveis em escala. Ficar observando o disco inteiro para detectar novas docs é frágil, consome recursos e depende de APIs específicas de cada SO.
  • Falsos positivos. Nada impede um _config.json solto de outra ferramenta; o scan precisaria validar conteúdo (chaves title/favicon) para ter confiança.
Veredito
Ótimo como import one-shot com cache (roda no primeiro setup, mostra a lista, você confirma o que registrar); ruim como mecanismo de descoberta contínua.

B. Registro + supervisor (o manager cria tudo)

O manager mantém o registro e é quem spawna os serves. Descoberta não é necessária no dia a dia: nova docs = botão “adicionar pasta” (ou arrastar) no manager, que valida o _config.json, escolhe porta e registra.

  • Simples — sem watchers, sem scan em runtime, sem corrida de estado.
  • Cross-platform — Node puro, mesmo perfil do docs-in-html atual.
  • Lacuna — docs que você servir manualmente (fora do manager) ficam invisíveis… o que nos leva a C.

C. Beacon: serves se anunciam ao manager

Sua ideia da “tag”: um hook no serve.js que, ao subir, faz um POST localhost:4400/api/announce com {dir, port, title}. O manager registra na hora, mesmo para serves iniciados à mão. É elegante porque o serve sabe a verdade (porta real, título do _config.json) — não há inferência.

  • Detecção exata — porta, título e favicon vêm prontos, sem ler nada.
  • Firewall — em Windows o primeiro POST local pode disparar um prompt de firewall; um manager rodando em localhost puro geralmente escapa, mas é um ponto de atenção.
  • Retrocompat — versões antigas do pacote não anunciam; o beacon é acréscimo opcional, nunca o mecanismo principal. Fail-safe: se o manager não responde, o serve segue normalmente.

D. Um único processo, multi-raiz (sem filhos) — escolhida

Em vez de N serves, o manager é um serve multi-raiz: recebe o request /projeto-x/foo.html, resolve a raiz no registro e reutiliza as funções já exportadas (buildTree, SHELL, injectScripts) para servir direto. Menos processos, menos RAM, e o live-reload ganha um canal único de WebSocket multiplexado por slug.

  • Arquitetura mais limpa a longo prazo; um watcher por docs.
  • Um só comando para tudo: registra a pasta e ela passa a ser watchada/servida — a UX “B” (registro) e o mecanismo “D” viram uma coisa só.
  • Refatoração — o serve.js atual usa constantes globais (ROOT, etc.); servir N raízes exige reestruturar em contexto por raiz. É o custo de entrada, pago uma vez.

Decisão (atualizada)
D é a arquitetura escolhida — um único processo multi-raiz, com registro de pastas watchadas (evolução natural de B, que vira a camada de registro dentro de D). A continua como import pontual (botão “escanear”, skip-list e cache) e C como bônus futuro. O proxy reverso da fase-1-original foi descartado: se só existe um processo, não há nada a proxiar.

4Proposta: fase 1 em detalhe (arquitetura D)

Um único processo multi-raiz — o manager é um serve que serve N raízes — alimentado por um registro de pastas watchadas.

Status: ✅ implementado e validado
Etapas 1–6 executadas (revisão de código independente incluída — 2 achados críticos corrigidos: injeção de comando no endpoint Warp e crashes por request malformado). Checkpoints verificados: single-root byte-idêntico ao HEAD original; 7 docs reais registradas e servidas em :4400/<slug>/; live-reload e navegação testados num browser real (CDP), console limpo; delegação sem processo extra; scan frio em ~0,2 s. Restam apenas os itens de release (help/README/version bump opcional).

Fluxo de uso

docs-in-html <dir>serve + registra (default) registry.jsonalimenta manager :4400serve /x/… /y/…
  • Registro sem comando novo: o serve comum (docs-in-html <dir>) passa, por padrão, a registrar a pasta no ~/.docs-in-html/registry.json ao subir — você não muda seu hábito: serve como sempre serviu, e a pasta entra no manager de graça. --no-register como opt-out. Remover do registro é pela UI do manager (ou --unregister), não por um subcomando dedicado.
  • Um processo, N raízes: docs-in-html manager sobe o servidor em 4400 (ou $DOCS_MANAGER_PORT). Cada docs vive num prefixo: localhost:4400/projeto-x/…. Reusa buildTree, SHELL, injectScripts e applyShellConfig por raiz — nada de proxy, nada de filhos.
  • Um watcher por docs: fs.watch recursivo (ou @parcel/watcher se a recursão nativa falhar em algum SO) por raiz registrada; cada evento recarrega só a árvore daquela raiz. O live-reload vira um WebSocket único multiplexado por slug — o cliente só ouve o canal da sua docs.
  • Refactor do core: o serve.js atual é um script com globais (ROOT etc.). A mudança estrutural da fase 1 é extrair um contexto por raiz (createRoot(dir, {base}) → tree, config, watcher) e o router de prefixos por cima. O CLI de serve single-root atual continua idêntico por fora — passa a ser um caso especial do contexto único.
  • UI do manager (localhost:4400/): grid de cards — favicon + título do _config.json de cada raiz, ações: abrir, abrir no Warp, revelar no Explorer, desregistrar. HTML puro, zero build, no espírito do projeto.
  • Import por scan (botão “escanear”): caminha $HOME (pastas extras configuráveis), pula node_modules, .git, AppData, Library, .cache, dotfiles, limita profundidade (~6) e valida o JSON encontrado. Resultado em tabela com checkboxes — você escolhe o que registrar. Cache em ~/.docs-in-html/scan-cache.json para só revarrer o que mudou (mtime de diretórios).
  • Prefixos vs globais: como cada docs fica atrás de /<slug>/, o shell precisa injetar <base href="/<slug>/"> — o contexto por raiz já carrega esse base, sem flag nova no CLI de serve.

Comportamento do docs-in-html <dir> conforme o manager
Manager rodando: o CLI não sobe server adicional — registra/atualiza a raiz no manager e apenas avisa no terminal, com o link: ✓ adicionada ao manager: http://localhost:4400/projeto-x/. Não abre browser, não rouba o foco — quem navega é você, quando quiser, pela página do manager. Nada de servidor duplicado, nada de porta 8000 ocupada à toa: o manager é o serve daquela pasta.
Manager parado: comportamento de hoje — server próprio, watcher, porta 8000, auto-open (com o registro silencioso no registry para a próxima).
Detectar o manager é barato: um ping em localhost:4400/api/ping antes de subir o server. É uma mudança deliberada de comportamento quando o manager existe — mas só nesse caso; sem manager, o contrato atual é intocável.
E o npx? Continua funcionando — o registry não mora no pacote
O ~/.docs-in-html/registry.json vive na home do usuário, não junto ao pacote. O npx docs-in-html <dir> executa o mesmo código, no mesmo processo, com as mesmas permissões de escrita na home — logo, registra normalmente, sem instalação global. O que o npx não dá é só comodidade: o manager é um processo de longa duração, e rodá-lo via npx toda vez (re-download/check de versão) é chato — aí sim a instalação global (ou um atalho de auto-start no login) vale a pena. Ou seja: registro via npx: sim, manager via npx: possível, manager no dia a dia: global. Cuidado único: manter o formato do registry simples e tolerante a versões (chaves desconhecidas preservadas), já que versões diferentes do pacote podem escrever nele.

Etapas

  1. Refactor do core — roots.js. Extrair o estado global do serve.js para contexto por raiz; reconstruir o serve atual em cima (mesma UX, mesmas flags). Checkpoint: comportamento idêntico ao de hoje, testado servindo esta própria docs-html.
  2. Registry. registry.js + o serve passando a gravar/remover entradas (--no-register/--unregister). Checkpoint: servir pastas diferentes popular o mesmo registry.
  3. Manager multi-raiz. manager.js: router de prefixos, um watcher por raiz, WebSocket multiplexado, live-reload por docs, endpoint /api/ping. Checkpoint: duas docs acessíveis em :4400/a/ e :4400/b/ com reload instantâneo em ambas.
  4. Delegação do CLI. O serve, ao subir, pinga o manager: se responder, registra/ativa a raiz nele e imprime o aviso com o link (✓ adicionada ao manager: :4400/<slug>/) — sem server próprio e sem abrir browser. Sem resposta, fluxo atual. Checkpoint: com manager rodando, docs-in-html <dir> imprime o link, nenhum processo novo fica de pé e nenhum browser se abre.
  5. UI de cards. client/manager.html: grid com título/favicon do _config.json, abrir/remover, botão “adicionar pasta”.
  6. Integrações do SO. Endpoints /api/open-warp (warp <dir> via child_process, fallback para terminal padrão) e /api/reveal (Explorer/Finder).
  7. Import por scan. scan.js + botão “escanear” na UI, com checkboxes de confirmação e cache.
  8. Polimento e release. Help atualizado, README, bump de versão (minor), publicação no npm.

Resultado esperado ao final

O dia a dia depois do plano
  • docs-in-html manager sobe uma vez (boot/login) — e a partir dali você abre localhost:4400 no browser e vê todas as suas docs num grid, com título e favicon de cada uma; um clique entra na docs, com sidebar, tree e live-reload iguais aos de hoje.
  • Nenhum ritual de portas/terminais: servir uma pasta nova com docs-in-html <dir> (npx ou global) já a registra; ela aparece no manager na hora. O botão “escanear” traz as docs históricas em um lote.
  • Do card da docs, “abrir no Warp” abre o terminal na pasta certa — a ponte para a sessão do pi — e “revelar” abre o Explorer/Finder.
  • O manager é um único processo Node, zero dependências novas (se fs.watch recursivo bastar), cross-platform, e o modo single-root atual continua funcionando igual para quem não quer manager.
  • Recursos: N watchers, 1 processo — nada de N serves espalhados nem portas para decorar.

Recomendação
Mesmo pacote — e sem subcomando de registro: o serve existente registra por padrão, e apenas docs-in-html manager é comando novo. A arquitetura D exige o refactor de contexto por raiz — e ele é valioso justamente no core, não ao lado dele. Um pacote separado só faz sentido se quisesse manter o serve 100% congelado, o que D descarta por definição. Mitigação do risco: o refactor mantém o comportamento do CLI atual como teste de regressão (mesma UX, mesmas flags, agora implementado sobre roots.js).

5Integração com o Warp

Do que a documentação oficial do Warp nos dá hoje.

  • CLI warp <dir> — abre uma janela/sessão do Warp diretamente num diretório. Existe nas três plataformas (o Warp no Windows suporta PowerShell, cmd, bash…). É o caminho direto para o botão “abrir no Warp”: o browser não pode spawnar processos, então o card chama POST /api/open-warp no manager, que executa warp <caminho> via child_process — com o shell certo por plataforma (PowerShell no Windows, open/direct no macOS/Linux).
  • URI scheme warp:// — dispara ações programáticas: launch configurations, tab configs (warp://tab_config/nome, com ?new_window=true). Útil como atalho futuro (“abrir esta docs com o comando pi já rodando”), mas não abre diretório arbitrário — exige um TOML de tab config por projeto. Fica como evolução: o manager poderia gerar essas launch configs com cwd da docs + comando inicial (ex.: pi) a partir do registro.
  • Launch configurations (YAML) — o Warp já tem o conceito de layouts salvos com cwd e comandos iniciais por pane. É exatamente o formato certo para “abrir projeto X com pi + serve do docs”: o manager pode emitir esses YAMLs automaticamente, um por docs registrada.
Decisão sugerida
Fase 1: warp <dir> via endpoint do manager (simples, cross-platform, resolve o caso “abrir o pi na pasta”). Fase 2: gerar launch configs por projeto para já abrir com pi rodando. Detectar ausência do warp no PATH e oferecer fallback (abrir no terminal padrão do SO).

6Decisões encerradas

  • ✓ Watcher: fs.watch recursivo nativo (zero-dependency). Linux sem recursão → fallback de recursão manual + aviso. A troca por @parcel/watcher fica como plano B (dependência opcional), isolada atrás de roots.js.
  • ✓ Empacotamento: mesmo pacote, sem comando watch — o serve padrão registra; só manager é comando novo.
  • ✓ Auto-start: manual por ora — docs-in-html manager explícito; atalho de login é documento futuro.
  • ✓ Ping de delegação: timeout curto (~300ms) antes de decidir subir server próprio.
  • ✓ Porta do manager: 4400 fixa ou $DOCS_MANAGER_PORT (CLI e manager leem a mesma variável, então a delegação concorda automaticamente). O manager grava managerPort no registry como fonte secundária para o ping (CLI usa a env primeiro, o registry como fallback). Porta ocupada → mensagem clara e exit, sem porta flutuante.
  • ✓ Unregister: docs-in-html <dir> --unregister remove do registry e sai + botão “remover” na UI.
  • ✓ Beacon: fora desta execução — serves de versões antigas são simplesmente ignorados.
  • ✓ Slug = título: o slug vem do title do _config.json (ex.: “My Project — Handbook” → my-project-handbook): slugified para URL, exibido como título no card e na aba. Renomear o título no config muda o slug — o registry revalida no boot e avisa quando um link antigo deixa de existir. Colisões (dois títulos iguais) resolvem com sufixo -2 e aviso na UI.
  • ✓ Escopo do scan: default $HOME, profundidade 6, skip-list fixa (node_modules, .git, AppData, Library, .cache, dotfiles) + pastas extras configuráveis no registry.
  • ✓ npx: registry na home do usuário, não no pacote — registro via npx funciona; formato tolerante a versões.

7Validação: a execução se autotesta

Cada etapa termina com evidência verificável — não com “parece que funcionou”.

Camada 1 — CLI/HTTP (bash + curl)

  • Etapa 1 (refactor): servir a própria docs-html/ deste projeto e comparar as respostas HTTP antes vs. depois do refactor — status, headers, body do shell, do manifest (/manifest.json ou equivalente) e de um HTML interno byte a byte. Diferença = bug.
  • Etapa 2 (registry): servir duas pastas temporárias e conferir o ~/.docs-in-html/registry.json resultante (entradas, sem duplicação ao repetir o comando, --no-register não grava, --unregister remove).
  • Etapa 3 (manager): curl :4400/a/… e :4400/b/… para duas raízes; /api/ping; porta ocupada → exit com mensagem; DOCS_MANAGER_PORT respeitada.
  • Etapa 4 (delegação): com o manager de pé, rodar docs-in-html <dir> e verificar: link impresso, nenhum processo novo (tasklist/ps antes/depois), nenhum browser aberto. Sem manager → server próprio sobe normalmente.
  • Etapa 6 (scan): árvore de teste com node_modules/dotfiles plantados — nenhum falso positivo; cache revalida por mtime.

Camada 2 — Browser real (Chrome DevTools Protocol)

Além do curl, a UI é testada num browser de verdade: iniciar Edge/Chrome com remote debugging e dirigir a página por CDP — navegar, clicar, inspecionar DOM e capturar erros de console:

  • UI de cards: localhost:4400 renderiza um card por raiz com título/favicon corretos; clique abre a docs com sidebar e tree.
  • Live-reload: com a página aberta, editar um HTML no disco e observar o WebSocket disparar a recarga (sem polling manual).
  • Console limpo: zero erros JS no shell, no manager e nas docs internas (incluindo Mermaid, se a docs de teste tiver diagramas).
  • Ações: “remover” tira o card e derruba a rota; “abrir no Warp” invoca o endpoint (o processo warp é verificado por mock/inspeção, sem depender do Warp instalado).

Camada 3 — Revisão por subagentes

  • Um revisor read-only examina o diff de cada etapa contra este plano (o refactor do serve.js é o crítico: globais destruídas, nenhuma flag/UX mudada).
  • Um testador executa os checkpoints das camadas 1–2 de forma independente e reporta só evidências (curl, screenshots DOM, saídas).
  • Execução paralelizável quando as etapas permitem (ex.: revisão da etapa N enquanto a etapa N+1 é implementada).
Critério de pronto por etapa
Etapa só é considerada concluída com: (1) checkpoint do plano passando, (2) zero erro de console no browser, (3) revisão de diff limpa. Qualquer falha trava a etapa seguinte — sem “resolver depois”.

8Quiz

1. Por que o scan global por _config.json foi rebaixado a “import pontual” em vez de mecanismo contínuo?

✅ B. O marcador é ótimo; o problema é o custo de recorrência e a inviabilidade de watchers em escala. Uma vez com cache, o scan é uma ferramenta de import — não de runtime.

2. O que resolve a lacuna do registro puro (docs servidas manualmente ficarem invisíveis ao manager)?

✅ C. O serve é a fonte da verdade (porta real, título). O beacon é opcional e fail-safe: se o manager não existe, o serve segue normal.

3. Por que a UI do manager precisa de um endpoint de servidor (e não pode abrir o Warp sozinha, via JS)?

✅ B. A sandbox do browser impede spawn. O card faz POST /api/open-warp; o manager executa warp <caminho> com o shell adequado de cada plataforma.

4. Qual recurso do Warp melhor representa o futuro “abrir a docs já com o pi rodando”?

✅ A. Launch configs são exatamente “cwd + comandos na inicialização”. O URI scheme warp://tab_config abriria um TOML salvo — não um diretório arbitrário.

5. Na arquitetura D, por que o refactor de “contexto por raiz” (roots.js) é o coração da fase 1?

✅ C. Sem estado global, não há como distinguir duas docs no mesmo processo. O refactor é exatamente trocar globais por contexto por raiz — e ainda melhora o modo single-root sem mudar sua UX.

6. Como o registro de pastas entra no fluxo, sem comando novo?

✅ B. Nenhuma nova coisa para aprender: docs-in-html <dir> continua sendo o único gesto — a diferença é que a pasta agora também entra no registry e aparece no manager.
