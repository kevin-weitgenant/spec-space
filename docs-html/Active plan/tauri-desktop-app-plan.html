1Contexto

Onde o spec-space está hoje e o que exatamente o Tauri substitui — e o que ele não substitui.

Hoje o fluxo do usuário é orientado a terminal: você roda spec-space ./specs, um processo Node sobe o servidor em localhost:4400, registra a pasta no manager e abre o navegador. O manager (src/server/manager.js + client/manager.html) já serve todos os projetos de uma vez, cada um em /<slug>/, com sidebar tree, live reload via SSE, diffs de mudança, edição inline e pan/zoom de diagramas. Ou seja: a "aplicação web" já existe e já é multi-projeto — o que falta é a casca nativa.

O problema que este plano resolve
Exigir um terminal + spec-space manager + navegador são três barreiras entre o usuário e as docs. O objetivo é: clique duplo no ícone do desktop → janela nativa maximizável, com abas, sem barra de endereço, sem Chrome visível.
Rampa para iniciante (pode pular)

Tauri é um framework que empacota uma UI web (HTML/CSS/JS) numa janela de aplicativo nativa. Em vez de embutir um navegador inteiro como o Electron, ele usa o webview que o sistema operacional já tem (WebView2 no Windows, WKWebView no macOS, WebKitGTK no Linux). Resultado: binários de ~5–15 MB em vez de ~100+. O backend é em Rust, mas para um app que já tem um servidor Node, o Rust fica quase trivial — só orquestra janelas e processos. A versão atual é a Tauri 2.

Arquitetura atual (o que permanece intacto)

Todo o núcleo do spec-space — server, injeção de nav, scan, registry, export — continua sendo Node puro, zero dependências. O Tauri envolve; não reescreve.

2Intuição

A janela nativa é só uma "tela sem navegador" apontada para o servidor que já existe; as abas são UI sua dentro do webview.

Terminal→ spec-space manager→ localhost:4400→ Chrome/Edge

Hoje: o usuário atravessa o terminal e termina num navegador.

Ícone no desktop→ Janela Tauri (abas)→ localhost:4400→ server Node (existente)

Depois: o servidor Node continua igual; só a ponta do usuário muda.

A ideia central: o processo Tauri é o no que acorda primeiro. Ele (1) lança o servidor Node como processo filho (sidecar), (2) espera a porta responder, (3) abre uma janela cujo conteúdo é o manager. O usuário nunca vê terminal, nunca digita URL.

As abas

Não são abas do navegador (não existem — não há navegador). São abas desenhadas em HTML dentro do app, como as do VS Code: uma barra no topo onde cada aba guarda "qual doc/projeto está aberto". Por baixo, cada aba corresponde a um <iframe> vivo (ou um histórico + recarregamento) apontando para uma URL do manager.

docs-in-html checkout-api · plano-jwt +
┌ sidebar tree (existente) ┐  │  conteúdo da doc da aba ativa…

Aparência-alvo: barra de abas no topo (novo), sidebar e conteúdo são o spec-space de sempre.

Por que iframes e não webview por aba
Tauri 2 permite múltiplos webviews, mas cada um é pesado e o estado (sidebar colapsada, scroll) já é preservado pelo client existente. Iframes dentro de um único webview são mais leves, mantêm SSE/live reload funcionando por aba, e simplificam arrastar/fechar/reordenar. Múltiplas janelas nativas ficam como extensão futura (item 5 do roadmap).

3Mudanças

Um novo pacote desktop/ no monorepo, mais um script client para a barra de abas. Nada do núcleo é reescrito.

Novo: desktop/ — o app Tauri

Diretório separado (não vai no pacote npm atual). Contém a configuração do Tauri (tauri.conf.json: identidade, ícone, tamanho de janela, permissões mínimas), o mínimo de Rust (main.rs: gerenciar o sidecar Node e a janela) e o frontend da janela — uma página shell enxuta que só hospeda a barra de abas e os iframes.

Sidecar Node: embarcar o runtime

O servidor precisa rodar sem Node instalado na máquina. Duas opções: empacotar o src/ + client/ como sidecar com um runtime embutido (ex.: binário node por plataforma, ou empacotar com pkg/deno compile), mantendo o princípio zero-dependências do projeto. O plano recomenda sidecar com binário por plataforma: o Tauri já suporta binários externos por-alvo de build.

Novo: client/tabs.js (+ CSS) — barra de abas

Script injetável, no mesmo estilo dos scripts existentes (changes.js, reload.js): desenha a barra de abas quando detecta que roda dentro do shell Tauri (via query param ou window.__SPEC_SPACE_DESKTOP__), gerencia lista de abas (título, favicon do projeto, fechar com clique do meio, Ctrl+T/Ctrl+W), sincroniza a aba ativa com a navegação dentro do iframe e persiste as abas abertas para restaurar na próxima sessão.

Ajuste: src/cli/serve.js — modo headless

Uma flag (ex.: --sidecar) para: não abrir o navegador (já existe --no-open), escolher porta livre dinamicamente e reportá-la ao Tauri (stdout/IPC), e silenciar logs interativos. Sem mudanças de comportamento para o uso via terminal.

Novo: pipeline de build/distribuição

Scripts no desktop/ que geram os instaladores (.msi/.exe NSIS no Windows, .dmg no macOS, .AppImage/.deb no Linux) via tauri build, com ícone derivado do icon.png existente. Auto-update pode entrar depois (Tauri 2 tem plugin updater).

4Fases & riscos

Cada fase entrega um app utilizável; nenhuma depende das seguintes para ter valor.

Fase 1 — Prova de conceito (dev machine)

desktop/ com Tauri apontando para um manager rodando manualmente. Janela sem abas, carregando localhost:4400. Meta: validar que injeção, SSE, diffs e edição inline funcionam dentro do webview. Verificação: abrir 3 projetos, editar um arquivo, ver o reload na janela.

Fase 2 — Barra de abas + sidecar

Tauri lança o servidor como filho, espera a porta, aí abre a janela. tabs.js entra. Verificação: fechar a janela encerra o processo Node (sem órfãos no gerenciador de tarefas).

Fase 3 — Distribuição

Runtime Node embutido por plataforma, builds de instalador nos 3 OSes, ícones. Verificação: instalar num Windows limpo sem Node e abrir as docs.

Riscos conhecidos
Porta 4400 ocupada (outro manager rodando) → o modo sidecar deve buscar porta livre; tamanho do binário cresce com o Node embutido (~40–70 MB, ainda menor que Electron); permissões de assinatura no macOS (Apple Developer ID) se quiser distribuir fora do seu círculo; WebGL/perf de Mermaid no WebView2 é bom, mas o pan/zoom deve ser revalidado na fase 1.
Alternativa de baixo custo: PWA
Antes de qualquer Tauri, dá pra chegar a 70% do efeito com um manifest + service worker no manager: "instalar" o site cria ícone no desktop e janela sem barra de endereço. Abas, porém, não existem numa PWA (cada instalação é uma janela). Vale como passo interimário, não como destino.

5Quiz

1. No app Tauri, quem sobe o servidor Node do spec-space?

✅ B. O Tauri atua como "no": acorda primeiro, sobe o sidecar Node, e só então abre a janela apontada para o localhost. O servidor existente em JavaScript permanece intacto — nada é reescrito em Rust.

2. Por que as abas são implementadas com iframes dentro de um único webview, e não um webview Tauri por aba?

✅ C. O Tauri até suporta múltiplos webviews — a escolha é de custo/benefício: um webview só, com abas HTML + iframes, é mais leve, reaproveita o client existente que já preserva estado, e cada iframe mantém sua conexão SSE viva.

3. O que muda em src/cli/serve.js?

✅ A. O ajuste é mínimo e aditivo: uma flag de modo sidecar (porta dinâmica + reporte da porta escolhida), mantendo o CLI idêntico para quem usa o terminal.

4. Um usuário instala o app num Windows sem Node.js. Por que funciona?

✅ B. A fase 3 de distribuição empacota o runtime junto do app, por alvo de build — mecanismo que o Tauri suporta nativamente ("external binaries"). É isso que destrava o "clique duplo funciona em qualquer máquina".

5. Qual limitação descarta a PWA como solução final aqui?

✅ C. A PWA entrega ícone no desktop e janela sem barra de endereço (ótimo como passo interimário), mas o requisito de várias abas navegáveis só é atendido com abas desenhadas no app — o que o shell Tauri viabiliza.
