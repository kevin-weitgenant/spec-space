Plano: tabela de endpoints no root module

Extrair as guardas de segurança e os oito endpoints POST de dentro do closure gigante de handle() em roots.js, transformando o despacho numa tabela método→função testável sem servidor.

Candidato 1 da revisão de arquitetura · docs-in-html · roots.js (293 linhas) + manager.js + novo teste

1 · Contexto 2 · Intuição 3 · Mudanças 4 · Quiz

1Contexto

Rampa para iniciante (pode pular)

O docs-in-html é um servidor de desenvolvimento sem build: você aponta para uma pasta de HTMLs e ele serve os arquivos, gera uma barra lateral automática e recarrega a página quando algo muda. O coração disso é o módulo roots.js: a função createRoot(root, opts) devolve um "contexto" por pasta — { root, base, handle, reload } — onde handle(req, res) é a função que o Node chama a cada requisição HTTP, igual a um listener de servidor. Dois consumidores montam sobre essa mesma interface: o serve.js serve uma única pasta em /, e o manager.js serve N pastas, cada uma em /<slug>/, reescrevendo a URL antes de delegar ao mesmo handle. Além de servir arquivos, handle responde a pequenos endpoints de gerenciamento (criar pasta, renomear, salvar, deletar…) usados pela barra lateral do navegador.

No código atual, handle é um único closure de ~170 linhas que acumula responsabilidades bem distintas. Lendo roots.js de cima a baixo, encontramos nesta ordem:

  • Guardas de segurança — readJsonBody (limite de tamanho no corpo JSON), safeRelPath (rejeita .., caminhos absolutos, nomes com <>:"|?* ou que começam com ./_) e resolveIn (resolve dentro do root e confere com abs.startsWith(root + path.sep)). Elas são declaradas dentro de handle — privadas ao closure, invisíveis ao resto do módulo.
  • Oito handlers POST inline — /__delete__, /__rename__, /__mkdir__, /__save__, /__reveal__, /__order__, /__title__, mais o GET /__manifest__. Cada um é um bloco if (req.method === "POST" && raw === "/__x__") aninhando callbacks de fs.
  • Contabilidade de config — shiftIcons e pruneIcons mantêm as chaves de config.icons em sincronia quando arquivos são renomeados ou apagados.
  • Serviço estático — serveShell (index.html do usuário ou shell embutido, com <base> e injeção de scripts), serveFile + tabela MIME, e o endpoint /__docs__ que serve os clients com seu próprio prefix-check.
  • Lógica de deep-link — se a requisição de um HTML vem com Sec-Fetch-Dest: document (navegação de topo, não iframe), embrulha no shell.
O problema central

As guardas de segurança são críticas e, ao mesmo tempo, intrinsecamente intestáveis: por viverem dentro do closure de handle, a única forma de exercitá-las é com um servidor HTTP real, uma requisição real e um sistema de arquivos real. Um resolveIn("../../etc/passwd") nunca pode ser testado diretamente — só indiretamente, através de uma resposta 400 vinda da rede.

Há ainda uma duplicação: readJsonBody aparece praticamente idêntica em roots.js (dentro de handle, cap padrão 4096) e em manager.js por volta da linha 108 (cap padrão 1 MB), com os mesmos comentários sobre abort de cliente. Dois corpos, um comportamento — clássico convite a drift.

Os dois call sites concretos:

  • serve.js (modo single): createRoot(ROOT, { base: "" }) e http.createServer(ctx.handle).
  • manager.js (multi-root): makeRoot chama createRoot(dir, { base: "/" + slug, onReload: ... }); o servidor do manager casa o primeiro segmento da URL com o slug, reescreve req.url e delega a r.ctx.handle.

O contrato externo — createRoot(root, opts) devolvendo algo com handle(req, res) — é o seam que ambos os consumidores usam. A refatoração abaixo não mexe nesse seam; ela reorganiza o interior.

2Intuição

A intuição é simples: segurança que só pode ser testada por HTTP é segurança que ninguém testa. Coloque a guarda num lugar onde um teste comum possa chamá-la.

Pense num aeroporto. Hoje a inspeção de bagagem acontece no meio do corredor de embarque, misturada com o anúncio de voos, a venda de café e o embarque em si. Para verificar se a inspeção detecta uma faca, você teria que comprar uma passagem e embarcar de verdade. O plano é construir uma sala própria para a inspeção — e, de quebra, dar a cada portão de embarque uma placa com seu nome, em vez de um corredor único onde os funcionários gritam os destinos.

Exemplo concreto: o que muda ao testar path traversal

Hoje, verificar que ../../etc/passwd é rejeitado exige subir um servidor, escutar numa porta, disparar um fetch POST e inspecionar que veio 400. Depois da mudança, o teste importa a guarda do módulo e chama:

resolveIn(root, "../../etc/passwd")   // → null
resolveIn(root, "guides/v2")          // → { rel: "guides/v2", abs: ... }

Sem rede, sem servidor, sem sequer arquivo em disco. A mesma chamada que o handler de delete faz internamente, agora visível.

Exemplo concreto: o que muda ao adicionar um endpoint

Hoje, um nono endpoint significa mais um bloco if dentro do closure, repetindo o padrão readJsonBody → resolveIn → fs-callback → resposta. Depois, significa escrever uma função endpointFoo(ctx, req, res) e registrar uma linha na tabela. O despacho vira dado, não código:

const ENDPOINTS = {
  "/__delete__": { method: "POST", fn: endpointDelete },
  "/__rename__": { method: "POST", fn: endpointRename },
  // ...
};

Antes e depois

guardas escondidas no closure → 8 ifs inline em handle() → readJsonBody ×2 (drift)
guardas exportadas do módulo → tabela método→função → readJsonBody única, importada

O closure monolítico vira despacho por dados + funções nomeadas por endpoint.

E o fluxo de uma requisição continua o mesmo por fora — só o interior de handle fica raso:

As três vitórias, no vocabulário de design: locality (as guardas de segurança passam a viver num único lugar, e mudanças nelas ficam visíveis e revisáveis), leverage (uma interface de endpoints serve os dois consumidores — serve.js e manager.js — e o manager deixa de carregar sua cópia de readJsonBody), e testabilidade (path traversal vira um teste de unidade, não um teste de integração com HTTP + fs).

3Mudanças

Três arquivos, sem quebra do contrato { root, base, handle, reload }. Nenhuma mudança de comportamento esperada — o shell, o live-reload e a barra lateral continuam idênticos do ponto de vista do navegador.

1. roots.js — do closure monolítico à tabela de endpoints

Guardas sobem para o escopo do módulo. safeRelPath e resolveIn saem de dentro de handle e passam a receber root como parâmetro explícito (hoje elas o capturam do closure de createRoot). readJsonBody também sai, virando um utilitário do módulo — exportado, para que o manager possa importá-lo. Nada da lógica muda: mesmas rejeições, mesmo cap padrão de 4096, mesmo comportamento de req.destroy() acima do limite. O que muda é a profundidade do aninhamento e a visibilidade.

Um endpoint, uma função nomeada. Cada bloco if inline vira uma função endpointDelete, endpointRename, endpointMkdir, endpointSave, endpointReveal, endpointOrder, endpointTitle — todas com a mesma assinatura, recebendo o contexto do root (o diretório e o que for preciso de config) mais req/res. Cada função contém exatamente o corpo que hoje vive no seu if, incluindo o cap especial de 10 MB do /__save__. shiftIcons/pruneIcons continuam sendo usadas por delete/rename, agora como helpers visíveis no módulo em vez de vizinhas acidentais.

O despacho vira dados. Uma constante ENDPOINTS mapeia caminho → { método, função }. O novo handle fica raso: tenta o reload/SSE, consulta a tabela, e caso não encontre cai no caminho de sempre (manifest, /__docs__/, shell, arquivo estático). ServeShell, serveFile, a tabela MIME e a lógica de Sec-Fetch-Dest ficam exatamente onde estão — atrás do seam de handle, intocadas por fora.

Exports crescem. O módulo passa a exportar readJsonBody, safeRelPath e resolveIn (ou uma pequena fachada de guardas), para consumo do manager e dos testes. createRoot continua devolvendo { root, base, handle, reload }.

Por que nenhuma mudança de comportamento?

É uma refatoração de estrutura, não de semântica. Cada handler preserva seus status codes (400, 404, 409, 500), suas validações e a ordem de despacho. Isso reduz o risco e torna o diff essencialmente mecânico de mover blocos para funções.

2. manager.js — remover a cópia de readJsonBody

A readJsonBody local (~linha 108, cap 1 MB) é deletada, e o módulo passa a importar a de roots.js. Como a diferença entre as duas versões era só o cap padrão — e todos os call sites do manager já dependem do cap maior —, os pontos de uso do manager que precisam do 1 MB passam o cap explicitamente por argumento, mantendo o comportamento atual byte a byte. O restante do manager (resolveWarp, hubBroadcast, syncRoots, endpoints /api/*) não muda em nada.

3. Novo arquivo de teste — exercitar as guardas sem servidor

Um teste novo (ex.: roots.test.js) que importa safeRelPath/resolveIn e as cobre como funções puras: rejeição de .., caminho absoluto, backslash, nomes com caracteres proibidos, segmentos vazios; aceitação de caminhos normais aninhados. Um segundo bloco cobre a tabela de endpoints no nível de unidade — por exemplo, que o teste de delete sobre um caminho malicioso sequer chega ao fs (a guarda devolve null antes), usando um diretório temporário. Não há servidor, porta ou fetch: o teste chama as funções diretamente. É o payoff de todo o plano.

Ponto de atenção

Ao mover safeRelPath/resolveIn para o escopo do módulo, o parâmetro root passa a ser explícito — fácil errar a ordem dos argumentos em oito call sites recém-criados. O revisor deve conferir cada handler com atenção redobrada, pois essas duas funções são a linha de defesa contra path traversal.

4Quiz

1. Por que as guardas de segurança (safeRelPath, resolveIn) são difíceis de testar hoje?

✅ C. As guardas vivem privadas dentro do closure; sem exportá-las, a única forma de alcançá-las é atravessar todo o caminho HTTP → handle → endpoint, com servidor e fs reais.

2. O que o novo teste de delete sobre um caminho malicioso (ex.: ../../etc/passwd) demonstra?

✅ B. O valor central do plano: a defesa fica visível como função pura; o teste comprova que o caminho malicioso morre na guarda, sem efeitos colaterais.

3. O que permanece atrás do seam de handle — ou seja, continua dentro do fluxo do handler e não vira endpoint na tabela?

✅ D. O plano extrai guardas e endpoints de gerenciamento; o serviço estático (shell, arquivos, MIME, deep-link) fica onde está, atrás do mesmo contrato handle(req, res).

4. Por que o manager.js pode simplesmente importar o readJsonBody de roots.js sem mudar de comportamento?

✅ A. Os corpos são idênticos exceto pelo cap default; explicitá-lo por call site preserva o comportamento e elimina a duplicação sujeita a drift.

5. Qual das alternativas descreve corretamente o que muda para os dois consumidores do root (serve.js e manager.js)?

✅ C. O contrato externo (o seam) é preservado; serve.js nem precisa ser tocado, e o manager só troca sua cópia de readJsonBody por um import.
