1Contexto

Onde o projeto está, o que já foi entregue e onde estão os commits.

O spec-space é um dev server Node zero-dependencies que serve pastas de docs HTML com sidebar, live reload (SSE), diffs e edição inline. O objetivo maior: virar um app desktop Tauri 2 multiplataforma — janela nativa com abas, sem terminal e sem navegador.

2Arquitetura atual (fase 2, funcionando)

Quatro peças conversando — decorar este desenho economiza horas de debug.

flowchart TD U["Duplo clique no atalho"] --> EXE["spec-space-desktop.exe (Tauri/Rust)"] EXE -->|"porta 4400 ou 4490 já responde?"| UP{manager no ar?} UP -->|sim| REUSE["reusa o manager existente"] UP -->|não| SPAWN["spawn: node serve.js manager --no-open"] SPAWN --> MGR["manager (localhost:4490)"] REUSE --> MGR EXE --> SHELL["janela: desktop/ui/index.html (tauri.localhost)"] SHELL -->|"1 iframe único cross-origin"| MGR MGR -->|"páginas com tabs.js injetado"| SHELL TABS["client/tabs.js (inject.js + manager.js)"] <-->|"postMessage: ping/pong, tab-open, tab-nav, spec-key"| SHELL

Peça por peça

  • desktop/src-tauri/src/main.rs — no boot, testa TCP em 4400/4490; se nenhum responder, spawna node <repo>/src/cli/serve.js manager --no-open como filho (acha o repo subindo diretórios até achar src/cli/serve.js). Ao fechar a janela, mata o filho.
  • desktop/ui/index.html — o shell: barra de abas + UM único iframe compartilhado (id view, com allow="fullscreen"). Aba = URL; trocar de aba navega o iframe. Sonda o manager em 4400 e 4490 (fetch no-cors — CORS do manager não responde, e fetch comum falha). Estado das abas em localStorage (spec-space-tabs). Toda aba é fechável; zero abas = só o "+".
  • client/tabs.js — ponte injetada nas páginas servidas (vira no-op em browser comum: só age quando window.parent !== window.self e o shell responde um spec-ping com spec-pong). Faz: Ctrl/Cmd+clique e clique do meio → nova aba; repassa Ctrl+T/W/ESC; reporta navegação (título/URL da aba). Fullscreen nativo roda sem interceptação.
  • src/domain/inject.js — injeta tabs.js em toda página servida (dev). src/server/manager.js — além disso, serve a cards page (manager.html) com a tag do tabs.js (rota /__docs__/tabs.js; query ?notabs pula a injeção — útil pra debug).
Protocolo postMessage (shell ⇄ tabs.js)
spec-ping/spec-pong (handshake), spec-tab-open {href}, spec-tab-nav {href,title}, spec-key {key: t|w|escape}. Origens: shell é tauri.localhost, páginas são localhost:PORTA — cross-origin, mensagens sempre com "*".

3Lições críticas do WebView2 (pagas com sangue)

Ignorar qualquer uma destas reabre bugs que custaram horas. Elas são o porquê de cada decisão estranha do código.

1. NUNCA use dois iframes cross-origin vivos
Um segundo iframe apontando para o manager, ao terminar de carregar, deadlocka a main thread do renderer do WebView2 — sem exceção, sem console, CDP para de responder. Não é rede (iframes de JSON/404 não travam), é renderer. Por isso o shell usa iframe único e trocar de aba = navegar. Se a fase 3/quatro quiser abas vivas em paralelo, o caminho é múltiplos webviews nativos do Tauri, não iframes.
2. NUNCA force-mate o app durante desenvolvimento
taskkill /F corrompe o LevelDB do perfil WebView2 (%LOCALAPPDATA%\com.kevinweitgenant.specspace\EBWebView\Default\Local Storage). Sintoma diabólico: localStorage.getItem funciona, mas qualquer setItem trava a janela inteira — disfarçou-se de bug de abas/fullscreen por uma sessão inteira. Fix: app fechado, apagar a pasta Local Storage. Para fechar graciosamente por CLI, use taskkill /IM spec-space-desktop.exe (sem /F) quando possível.
3. Fullscreen nativo funciona (mas exige allow)
requestFullscreen() do mermaid-zoom dentro dos iframes aninhados funciona desde que o iframe externo tenha allow="fullscreen". Houve um "fake fullscreen" por CSS que foi removido — os freezes da época eram a lição nº 2, não a API.
4. Detalhes que mordem
  • O teclado mora dentro do iframe — o shell nunca vê Ctrl+T/W; o tabs.js repassa via postMessage.
  • A cards page é servida crua (sem injectScripts) — por isso a rota dedicada /__docs__/tabs.js.
  • O manager neste ambiente sobe na 4490 (não na 4400 padrão) — o shell sonda ambas.
  • Debug remoto: lance o exe com WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223 e use CDP em http://localhost:9223/json. Um avaliar que não responde = main thread travada (ver lições 1/2).
  • ui/index.html é embutido no binário em tempo de compilação — mudou o shell, precisa cargo build de novo (tabs.js/manager.js NÃO: são lidos do disco a cada request).
  • Managers órfãos: se o app for morto com /F, o filho Node sobrevive; o próximo app o reusa (código velho!). Mate órfãos antes de testar mudanças no server.

4Passo-a-passo da fase 3

Meta: instaladores multiplataforma que funcionam em máquina sem Node instalado, substituindo o atalho de dev.

Passo 1 — Modo sidecar no CLI

Em src/cli/serve.js, adicionar flag --sidecar: não abre browser (já existe --no-open), escolhe porta livre dinamicamente (evita colisão com manager do usuário) e reporta a porta escolhida no stdout (linha tipo PORT 45123) para o Rust ler. Sem mudar comportamento do CLI normal. Testar: node src/cli/serve.js manager --sidecar.

Passo 2 — Rust lê a porta e a passa ao shell

Em main.rs: ao spawnar o filho, ler o stdout até a linha PORT; guardar porta em state Tauri. O shell passa a receber a porta via invoke (ou injetando via initialization script) em vez de sondar 4400/4490. Remover a sonda das duas portas (vira fallback).

Passo 3 — Embutir o runtime Node

Opções: (a) sidecar por plataforma com binário Node oficial por alvo (recomendado; o Tauri suporta "external binaries" por target — desktop/src-tauri/binaries/); ou (b) compilar o server a um executável único (ex.: pkg — mas atenção: o projeto se orgulha de zero-dependencies). Entregar src/ + client/ empacotados junto. O main.rs passa a invocar o binário embutido, não o node do PATH.

Passo 4 — Build release + instaladores

cd desktop
npm run tauri build   # gera .msi + NSIS .exe (Windows); .dmg/.app (macOS); .AppImage/.deb (Linux)

Ícones já existem (desktop/src-tauri/icons/, gerados de desktop/appicon.png — o icon.png da raiz é na verdade um JPEG; usar o appicon.png). Validar tauri.conf.json (bundle targets, identifier com.kevinweitgenant.specspace). Instalar num Windows limpo sem Node e abrir as docs — critério de aceite da fase.

Passo 5 — Substituir o atalho de dev

Após instalar, remover/reapontar o spec-space.lnk da área de trabalho (hoje aponta pro exe debug). Considerar plugin de auto-update do Tauri 2 como follow-up (não bloquear a fase nele).

Riscos conhecidos da fase 3
Binário cresce (~40–70 MB com Node embutido — ainda muito menor que Electron); assinatura macOS exige Apple Developer ID se distribuir fora do círculo pessoal; testar o deadlock da lição nº 1 não se aplica (não mexer no modelo de iframe único); portas — sempre dinâmica no modo sidecar.

5Ambiente & comandos de dev

Réguas de medição do dia-a-dia — rodar antes de commitar.

cd desktop/src-tauri && cargo build

6Quiz

1. Por que o shell usa UM único iframe em vez de um por aba?

✅ B. Foi medido por bissecção via CDP: JSON/404 em segundo iframe não travam; página real travava o renderer inteiro, sem exceção. A aba virou URL, e trocar de aba navega o iframe único (custo: recarrega a página).

2. O app congela "do nada" ao abrir abas. Qual a primeira suspeita e o fix?

✅ C. getItem funciona mas setItem trava a main thread — sem erro, sem log. Se alguém rodou taskkill /F, essa é a suspeita nº 1. Fix: remover …EBWebView/Default/Local Storage com o app fechado.

3. Você editou desktop/ui/index.html. O que é preciso para o app refletir a mudança?

✅ A. O frontendDist é embutido pelo codegen do Tauri. Já client/tabs.js e os arquivos do server são lidos do disco por request — esses pegam sem rebuild (mas o manager velho em memória precisa reiniciar para código de server).

4. Na fase 3, por que o modo sidecar deve escolher porta dinâmica e reportá-la?

✅ B. Hoje o shell sonda 4400/4490 e reusa o que estiver no ar — funciona, mas é frágil (manager órfão com código velho já confundiu testes). Porta livre dinâmica + reporte via stdout/IPC elimina a adivinhação.

5. Ctrl+T não funciona quando o foco está numa doc. Por quê?

✅ A. Eventos de teclado ficam no documento focado (dentro do iframe). O tabs.js escuta keydown em capture e posta spec-key pro shell — que é também por que a cards page precisou da injeção do tabs.js (rota /__docs__/tabs.js).
