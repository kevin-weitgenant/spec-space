Plano: extrair o núcleo puro do diff (changes.js)

O changes.js esconde, atrás de uma IIFE sem exports, ~150 linhas de diff puro — o código que decide o que o leitor vê de novo. Este plano tira esse núcleo para client/diff.js, testável com node:test e intacto no navegador.

Candidato 3 · extração de módulo puro · impacto: testabilidade + localidade · escopo: 1 arquivo novo + 2 ajustados

1Contexto

Rampa para iniciante (pode pular). Quando você revisita uma doc do projeto, o navegador compara o texto de hoje com um retrato salvo da sua última visita (em localStorage) e pinta o que mudou: blocos novos ganham um chip verde "novo", blocos editados ganham word-diff âmbar, e aparece um minimapa lateral. Para decidir "o que mudou" entre duas listas de parágrafos, usa-se um algoritmo clássico chamado LCS (Longest Common Subsequence): a maior sequência de itens que aparece, na mesma ordem, nas duas listas — tudo que sobra é inserção ou remoção. Esse cálculo é matemática pura: duas listas entram, uma lista de operações sai. Não precisa de navegador, DOM nem rede.

O client/changes.js é um arquivo de 335 linhas que roda inteiro dentro de uma IIFE com zero exports — ele toca window, document e localStorage no momento em que carrega. A linha 25 do arquivo (if (window.DOCS_EXPORT) return;) já mostra o quão "plugado ao navegador" ele é. Mas, logo depois da coleta de blocos, moram ali quatro funções que não tocam DOM nenhum:

Por que isso importa
Esse é o código com maior potencial de bug visível ao usuário do repositório: os chips "novo", os destaques de word-diff e os marcadores do minimap saem todos dali. E ele é intestável hoje — sem exports e com efeitos de DOM no load, não há como chamar diffOps de dentro de um node:test sem carregar um navegador inteiro. Um off-by-one no LCS, hoje, só é descoberto por um leitor humano.

Como o script chega à página: inject.js monta a lista de tags injetadas e, para toda doc não-shell em modo dev, empurra <script src="${base}/__docs__/changes.js" data-injected defer> antes do </body>. O servidor dev e o export.js compartilham essa mesma heurística — um ajuste ali vale para os dois destinos. É nessa lista que o novo diff.js ganhará sua própria tag, imediatamente antes de changes.js.

O projeto não tem dependências (package.json vazio de deps, Node ≥ 18, CommonJS). Isso não é acaso: a tática aqui é um adapter de módulo — uma guarda UMD — para que o mesmo arquivo sirva aos dois mundos, sem bundler, semdependência nova.

2Intuição

A intuição central: um arquivo pode ter dois rostos. No navegador, ele se anexa ao window; no Node, ele exporta via module.exports. O mesmo texto, dois carregadores, zero duplicação.

O LCS em miniatura

Pense no doc como uma lista achatada de blocos (é literalmente o que collectBlocks produz: texto normalizado de cada h1..h4, p, pre, li, blockquote). Suponha sua última visita e a de hoje:

velho = ["Intro", "Setup", "Uso"]
novo  = ["Intro", "Setup", "Auth", "Uso"]

O diffOps primeiro apar o prefixo comum (["Intro","Setup"]) e o sufixo (["Uso"]), e difa só o miolo — aqui, nada contra algo. As operações saem:

[ {t:" ", a:0, b:0}, {t:" ", a:1, b:1}, {t:"+", b:2}, {t:" ", a:2, b:3} ]

Um único op + — e é exatamente ele que o marks transforma em {b:2, kind:"new"}: um chip novo no bloco de Auth. Agora um caso de edição:

velho = ["Instale com npm install"]
novo  = ["Instale com pnpm install"]

LCS de blocos não casa nada (strings diferentes), então marks vê um par −/+ adjacente, similarity dá nota alta (só uma palavra difere), e nasce {b:0, kind:"edit", old:"Instale com npm install"}. O wordDiff então re-roda o diff no nível de token: "npm" sai riscado em vermelho (dih-wdel), "pnpm" entra sublinhado em verde (dih-wadd).

A seam: puro vs. DOM

Visualize a linha de costura que o plano abre no arquivo atual:

diffOps / wordDiff / similarity / marks → client/diff.js (puro, UMD) → changes.js (só DOM)

Antes: tudo dentro de uma IIFE. Depois: o núcleo migra para um módulo puro; o changes.js consome.

A profundidade dessa seam é o que dá o ganho: todo bug de diff passa a ser reproduzível com duas strings num teste, sem abrir página. E o inverso também — mexer no CSS do minimap nunca mais pode quebrar o LCS, porque não moram mais no mesmo fechamento.

Por que a guarda UMD funciona

No navegador, <script> clássico não define module, então a guarda cai no ramo window e o changes.js encontra window.diffOps à sua espera. No Node, require("./diff.js") define module, e o node:test recebe o objeto com as quatro funções. Um if de quatro linhas compra os dois mundos:

if (typeof module !== "undefined" && module.exports)
  module.exports = { diffOps, wordDiff, similarity, marks };
else
  window.DIFF = { diffOps, wordDiff, similarity, marks };
Leverage
O wordDiff já reutiliza diffOps internamente (diff de blocos e diff de palavras são o mesmo algoritmo em duas escalas). Ao extrair, essa reutilização fica explícita e visível — o módulo puro é uma pequena biblioteca de diff com dois clientes dentro do próprio arquivo.

3Mudanças

Três arquivos, uma ideia: separar o cálculo da pintura. A ordem abaixo é a ordem de implementação — cada passo compõe sobre o anterior.

client/diff.js novo

Um arquivo novo, pequeno e sem surpresas: recebe as quatro funções puras diffOps, wordDiff, similarity e marks copiadas ipsis litteris de changes.js (sem reescrever nada — esta extração é movimento, não refatoração de algoritmo). Duas diferenças conscientes: (1) a guarda UMD no final, como acima, para o mesmo arquivo servir a <script> e a require(); (2) marks recebe a lista nova por parâmetro em vez de ler o texts do closure, fechando a única fresta de impureza que ele tinha. Nenhum import, nenhum acesso a window fora da guarda, nenhum document.

client/changes.js

Emagrece de ~335 para ~185 linhas e vira explicitamente a camada de DOM: collectBlocks, o snapshot em localStorage, o CSS, applyUI (chips, word-diff renderizado, pill, minimap) e o faviconDot com canvas. Onde hoje chama diffOps(oldTexts, texts) passa a resolver o núcleo por window.DIFF (com um fallback defensivo: se o core não carregou, a feature simplesmente não marca — consistente com a filosofia do arquivo de "toda falha = feature silenciosamente off"). A IIFE continua existindo; só o conteúdo dela muda de natureza.

inject.js

Uma linha nova na lista de tags: a tag de diff.js entra imediatamente antes da de changes.js — sem defer entre os dois ou com defer em ambos, desde que a ordem de execução preserve diff-antes-de-changes. Como o bloco inteiro é inserido antes do </body> e compartilhado por servidor dev e export, o seam de injeção já existia; só o estamos usando mais uma vez.

Cuidado com a ordem de scripts
As tags com defer executam na ordem em que aparecem no documento. Se diff.js for injetado com defer e changes.js sem (ou vice-versa), a ordem quebra e o changes roda antes do core existir. A regra simples: mesma flag, ordem certa — diff.js primeiro.

Zero dependências novas: o compromisso zero-deps do projeto permanece.

4Quiz

Clique para responder — pode tentar de novo à vontade.

1. Por que a guarda UMD (if (typeof module !== "undefined")) em vez de simplesmente usar module.exports direto?

✅ B. Um <script> clássico não define module; a guarda é o adapter que deixa o mesmo arquivo puro servir aos dois carregadores, sem bundler nem dependência.

2. No exemplo da Intuição, ["Intro","Setup"] → ["Intro","Setup","Auth"]: quantos e quais ops o diffOps produz no miolo (após o trim de prefixo/sufixo)?

✅ C. O trim casa "Intro" e "Setup" na frente e nada atrás; sobra miolo vazio contra ["Auth"] — exatamente um +, que vira o chip "novo".

3. Qual destes fica em changes.js (a camada DOM) após a extração?

✅ D. Tudo que lê document/window/localStorage/canvas permanece na camada de apresentação; as três primeiras são puras e migram.

4. Ao mover marks para o módulo puro, que ajuste de interface ele exige?

✅ A. O acesso ao texts do closure era a única fresta de impureza; transformá-lo em argumento fecha a interface e torna a função honestamente testável.

5. No inject.js, qual é a regra crítica para as tags de diff.js e changes.js?

✅ B. Se a ordem (ou a flag defer) divergir, o changes executa antes do core existir em window — e os destaques somem silenciosamente.
