1. Aprofundar o módulo Root: tabela de endpoints + guardas

Problem — o root module é raso no lugar errado: a interface é um (req,res) cru, e toda a lógica de segurança (path traversal, nomes, caps) e de bookkeeping de config é closure-private. É onde mora a maior quantidade de código não testado do pacote.

Solution — extrair safeRelPath/resolveIn/readJsonBody (que também existe duplicado em manager.js:108) e um handler por endpoint, recebendo (root, config); handle vira uma tabela método→rota sobre eles.

  • locality: guardas de segurança num lugar só
  • leverage: uma interface, dois call sites (serve + manager)
  • testa path traversal sem servidor
  • deleta o readJsonBody duplicado

Problem — o LCS/word-diff/similarity de changes.js é o código com maior potencial de bug visível do pacote, e está preso num IIFE que toca DOM/localStorage no load: intragável de testar.

Solution — mover para client/diff.js com guarda UMD (if (typeof module!=="undefined") module.exports=…); changes.js importa e fica só com a camada DOM.

  • zero deps, zero framework — roda em node:test
  • locality: bugs de diff isolados do DOM
  • casos reais prontos: unicode, ordem, iguais
  • quick win: 1 arquivo novo

5. Tornar serve.js e export.js requireable

Worth exploring in-process

serve.js:45–71 (argv + process.exit no corpo do módulo) · export.js:44

Before — script, não module

parse argv no top-level
process.exit() em 3 pontos do corpo
0 exports
export.js run(): exit(1) em vez de throw

require("./serve.js") num teste = servidor de verdade ou exit

After — parseArgs/main puros + casca fina

parseArgs(argv) → {mode, dir, port…} (puro)
main(opts) → Promise/exit code (sem exit)
rodapé: if (require.main===module) main()
export.js: throw → CLI pega e printa

Problem — o CLI inteiro é efeito colateral de require; não há interface para testar parse de flags, fallback de portas ou delegação sem subir processo.

Solution — parseArgs(argv) e main() exportados, side-effects isolados no rodapé (require.main === module); export.run() lança erro em vez de process.exit.

  • interface: parseArgs testável direto
  • bin inalterado para o usuário
  • padrão já existe no pacote: saneLayout

Estratégia de testes (o "como" por trás dos candidatos)

Framework: node:test + node:assert — builtin do Node ≥18, mantém o zero-deps de runtime (devDep nenhum). Ordem de construção:

1. test/diff.test.jsunidades puras do núcleo extraído do changes.js (cand. 3): LCS em unicode, word-diff, similarity. Nenhuma infra necessária.
2. test/config, manifest, registryhumanize (acentos), merge dos legados _icons/_order, slugify (colisões, "api" reservado), saneLayout (órfãos, grupos vazios). Temp dirs reais bastam — ou o adapter mem do cand. 2.
3. test/inject.test.jsheurística por tabela: página com #docList em tag vs em prosa; mermaid/figure/zoomable; staticMode (DOCS_EXPORT + bootstrap de deep link); data-injected em toda tag.
4. test/roots.endpoints.test.jsguardas via interface nova (cand. 1): ../escape, backslash, nome esquisito, cap do body, delete de pasta não-vazia, rename→shiftIcons.
5. test/http.test.jsintegração fina, poucos casos: sobe createRoot num port efêmero, asserts de Sec-Fetch-Dest (document→shell, iframe→doc puro), injeção na resposta, no-store.
6. test/serve.args.test.jsparseArgs (cand. 5): flags, subcomandos, --port explícito vs fallback.
7. CI (GitHub Actions)node --test em windows + linux a cada push — o pacote tem código por-SO (reveal, warp, portas) que só o matrix pega.

Clientes DOM (nav/zoom/manager.html): ficam fora do node:test — o custo de um adapter de DOM não se paga hoje. A política testável deles vai para lib.js/diff.js (cands. 3 e 4); o resto é coberto pelos smoke tests de injeção. Playwright fica como passo futuro, se valer.

Top recommendation

3 — Extrair o núcleo puro do diff, imediatamente seguido do 1 — endpoint table no root module

O diff é o quick win (1 arquivo, teste puro no mesmo dia) e destrava a confiança para o refactor do root module — que é o de maior leverage: concentra toda a lógica de segurança não testada e os dois call sites (serve e manager). O seam de ambiente (cand. 2) entra naturalmente quando o cand. 1 pedir o primeiro adapter de teste.

Domain vocabulary

module
— unidade de código com uma interface única (aqui: cada .js do pacote).
interface / implementation
— o que o module expõe vs o que esconde.
deep / shallow
— module profundo: interface pequena, muita função escondida. Raso: interface quase do tamanho da implementation.
seam
— linha onde um adapter pode ser trocado sem tocar quem chama (aqui: node:fs, spawn, watch).
adapter
— implementação de um lado do seam (node em prod, mem/noop em teste).
leverage
— uma interface servindo N call sites.
locality
— um conceito/mudança mora num lugar só (ex.: regra de slug hoje em 3).
deletion test
— deletar o module concentra complexidade (bom) ou só move?
root
— uma pasta de docs servida; contexto criado por createRoot.
shell
— página com id="docList"; o contrato estrutural do layout.
doc
— um .html da pasta, renderizado no iframe do shell.
manifest
— árvore JSON (docs/pastas/ordem/mtime) que alimenta a sidebar.
registry
— ~/.docs-in-html/registry.json: pastas conhecidas + layout do mural.
mural
— página de cards do manager com grupos e ordenação.
identidade do doc
— "quem sou eu": pathname menos o BASE, com fallback index.html.
ops
— (novo) module de ambiente: fs/opener/watch/homeDir atrás de um seam.
