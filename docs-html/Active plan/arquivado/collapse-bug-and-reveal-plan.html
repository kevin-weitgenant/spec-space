Background

The sidebar in docs-in-html is a file tree rendered by client/nav.js from a manifest that the server (serve.js) generates from the docs folder. Two mechanisms matter here:

Collapse state is a map, not DOM. Which folders are open/closed lives in localStorage as docs-in-html:collapsed — a plain object like {"guides/": true, "api/": true}. When the tree renders, each folder head gets a closed CSS class if its path is in that map. Clicking a chevron toggles one entry and flips the class directly — cheap, no re-render.

Re-renders are guarded by a signature. Every time a file changes on disk, the client re-fetches the manifest and calls applyTree(tree). But rebuilding the DOM would wipe scroll position and any in-progress state, so applyTree first computes a signature — a string like "d:guides|f:guides/a.html|d:api|…" — and bails out early if the signature hasn't changed. The signature only encodes the set of paths, not their content and not the collapse state.

On the server side, the write endpoints all follow the same pattern: a POST /__something__ route that validates the path against resolveIn() (which guarantees the path resolves inside the served root), does one filesystem operation, and returns JSON. The server already knows how to open things in the OS: it uses start / open / xdg-open to launch the browser at startup.

Beginner ramp: “Shell” pages are assembled by shell.js/inject.js when you open a doc — the sidebar script runs alongside the doc in an iframe. The client also receives ROOT_INFO from the server: the absolute root path and the OS path separator (used by the existing “Copy full path” action). That channel is how the browser learns what OS it's on.

Part 1 — The “Collapse all” bug bug

The context menu on the sidebar (right-click → “Collapse all”) calls collapseAll(), which does exactly the right thing to the data:

collapsed[all[i].path] = true;   // mark every folder closed
save();                          // persist to localStorage
applyTree(currentTree);          // …ask for a re-render

The flaw is that last line. applyTree recomputes the signature of currentTree — but the tree hasn't changed at all; only the localStorage map has. The signature matches the previous one, so applyTree returns early and never rebuilds the DOM. The data says “everything collapsed”; the screen still shows open folders. A refresh would fix the view, because a fresh render reads the map — the state was saved correctly, the UI just wasn't told.

collapseAll()
→
collapsed[...] = true
→
save() ✔
→
applyTree()
→
signature unchanged → early return

The fix (one line): invalidate the cached signature before re-applying, so the guard can't short-circuit: set currentSignature = null right before calling applyTree(currentTree) inside collapseAll(). The rebuild then happens, reads the updated map, and every folder head renders with the closed class. This same trick is the correct pattern for any future action that changes only localStorage-backed UI state.

Part 2 — Reveal in File Explorer feature

Yes, it's possible, and cleanly: browsers can't touch the OS, but the dev server can. We add one new endpoint and one menu item.

Server: POST /__reveal__ { path }

Same shape as /__delete__: validate with resolveIn() (so ../ tricks fail with 400), then open the OS file manager with the absolute path. Cross-platform by branching on process.platform — each OS has a canonical command:

PlatformCommandBehavior
Windows (win32)explorer /select,"C:\docs\a.html"Opens the parent folder with the file pre-selected. For folders: explorer "C:\docs\guides" opens it.
macOS (darwin)open -R "/docs/a.html"-R = reveal & select, works for both files and folders.
Linuxxdg-open "/docs"No selection support in the spec — we open the containing folder for files, the folder itself for folders.
Security note: paths arrive from the browser, so we only ever spawn with an absolute path produced by resolveIn() — already proven to live under ROOT. We spawn the OS command directly (no shell string interpolation of user input) and ignore its exit code; worst case is a non-zero exit for a file deleted since the manifest was fetched, which we report as a plain 500 to the client. No new attack surface beyond what /__delete__ already exposes — and reveal doesn't write anything.

Client: kebab menu item

In makeKebab() (the “⋯” button on each tree row), add one entry alongside “Copy path”: “Reveal in File Explorer / Finder / Files” — the label adapts to the OS. To know the OS, we extend the existing ROOT_INFO handshake: the server already sends { root, sep } to the client; we add platform: process.platform. The menu item does a fetch("/__reveal__", { method: "POST", body: … }) — fire-and-forget, no refresh needed since nothing on disk changes.

Static export

The export command freezes the folder for static hosting — no server, no endpoints. The existing pattern is the EXPORT flag in the client, which already hides kebab buttons entirely in the export. Since the reveal item lives inside the kebab menu, it disappears automatically — zero extra work.
