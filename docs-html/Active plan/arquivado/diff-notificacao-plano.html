Plano · Mudanças visíveis no doc + minimap + bolinha na tab

Quando o agente altera um doc, a aba aberta hoje só recarrega às cegas. A v2 do plano (após feedback no protótipo v1) faz a mudança nascer visível no próprio documento — destaque verde + chip “novo”, word-diff inline nos trechos editados — com um minimap estilo VS Code marcando as regiões alteradas e a bolinha azul na tab via favicon dinâmico. Sem modal, sem toast, sem diff no servidor.

1Contexto

O que já existe e o momento exato onde a feature entra.

Rampa (pode pular). O servidor (reload.js) observa a pasta com fs.watch e emite {base, path} no canal SSE /__reload__. O cliente (client/reload.js) mantém uma conexão SSE por browser (Web Locks + BroadcastChannel) e dá location.reload() quando o próprio doc muda. inject.js injeta os clients dev em todo HTML servido.
agente salva spec.html→ SSE {path}→ location.reload() 💥→ (aqui entra a feature)

2A virada de design (v1 → v2)

O que foi descartado do protótipo v1 — e por quê.

v1 (descartado)v2 (este plano)
Toast com botões “ver mudanças / recarregar”Nada de toast: a página continua recarregando (comportamento que já é bom), mas o que é novo nasce destacado dentro do doc.
Modal overlay com o diff em blocos de códigoSem modal: destaque inline — fundo verde suave + borda + chip “novo” nos blocos adicionados; word-diff (riscado vermelho / verde sublinhado) nos parágrafos editados, como sugestões de edição.
Diff calculado no servidor, enviado no payload SSEDiff 100% client-side: o client guarda um snapshot do DOM no localStorage a cada load; no load seguinte compara e marca o que mudou. O servidor não muda nada.
Notificação de mudança in-pageA “notificação” vira favicon dinâmico com ponto azul (truque de canvas — o mesmo do Gmail) + prefixo ● no <title>: o Chrome mostra na própria tab.
—Novo: minimap lateral estilo VS Code com marcadores nas regiões alteradas, clicável para pular.
Por que diff client-side é melhor aqui

O diff precisa ser em nível de elementos do DOM (parágrafo, heading), não de linhas de arquivo — para destacar o bloco certo. O DOM já está parseado no browser, então comparar lá é natural. De quebra: zero mudança no servidor, funciona multi-root no manager sem código novo, e sobrevive a restart do servidor (o baseline é da aba, não do processo).

3Como funciona

O snapshot

Todo doc, ao carregar, extrai uma lista “achatada” de blocos: h2/h3/p/pre/li (na ordem do documento) com o textContent de cada um. Guarda em localStorage sob a chave docs-in-html:snap:<base>:<path>. Isso é após o load — os scripts dev injetados usam data-injected e são ignorados, então nunca poluem o diff.

O load seguinte

load do doc→ extrai blocos atuais→ LCS de elementos vs snapshot→ marca added/changed→ sobrescreve snapshot

Elementos novos (não estavam no snapshot) ganham a classe de destaque com chip “novo”. Elementos presentes mas com texto diferente ganham o tratamento de edição com word-diff inline (sub-LCS de palavras dentro do par alterado). O snapshot é então atualizado — a próxima visita compara contra esta versão.

A bolinha na tab

Se houve mudanças marcadas: o client desenha o favicon original num <canvas> e coloca um ponto azul no canto, trocando o href do <link rel=icon>, e prefixa o title com ●. Quando o usuário clica “já vi tudo” (ou o último destaque é dispensado), o favicon e o title voltam ao normal. Se o favicon vier do _config.json (emoji), ele é rasterizado no canvas igual — qualquer favicon de imagem funciona.

O minimap

Coluna fina fixa na lateral direita do viewport (fora do conteúdo, position:fixed), renderizada a partir da mesma lista de blocos: cada bloco vira uma barrinha com altura proporcional, headings mais escuros. Blocos com destaque ficam verdes (novo) ou âmbar (editado). Clique numa barrinha → scrollIntoView no bloco correspondente. Aparece só quando há mudanças não vistas — doc limpo, zero UI extra.

4Mudanças no código

novo client/changes.js

Toda a feature: snapshot localStorage, diff de elementos (LCS) + word-diff, classes de destaque, favicon dinâmico + title, minimap, barra “N mudanças · ↓ próxima · ✓ já vi tudo”. Um arquivo, sem deps.

edita inject.js

Injeta changes.js em todo doc (exceto shell) em modo dev, junto ao edit client. Export estático não recebe — nada a notificar.

mínimo client/reload.js

Nada estrutural: o reload automático ao mudar o próprio HTML continua — é ele que carrega a versão nova, que o changes.js então compara. (Opcional: só garante que o snapshot seja salvo antes do reload, o que já acontece naturalmente no load.)

opcional client/nav.js

Badge ● na sidebar para docs alterados que não estão abertos (escutando o docs-in-html:change já disparado hoje), limpando ao abrir. Complemento natural; pode ficar pra depois.

Servidor: zero mudanças

reload.js, roots.js, manager.js intocados. O evento SSE atual {base, path} já basta — quem dispara tudo é o location.reload() que já existe.

5UX detalhada

  • Fluxo: agente salva → aba recarrega (piscada normal) → o que é novo aparece com destaque verde e chip “novo”; editado com word-diff; minimap surge com marcadores; tab ganha ● azul.
  • Acumulação é grátis: múltiplas salvadas viram um reload cada — e o snapshot sempre atualiza no load, então cada visita mostra só o delta desde a última visita. Se você não olhou, os destaques ficam (comparação contra o snapshot da última visualização).
  • “Já vi tudo” na barrinha sticky limpa destaques, word-diff colapsa para o texto novo, favicon volta ao normal.
  • Escrita do próprio editor visual (/__save__): a própria aba que salvou compara contra seu snapshot — sem mudanças percebidas. Outras abas mostram o delta. Correto por construção.
  • Degradê gracioso: doc carregado sem snapshot (primeira visita, localStorage limpo) → nenhuma marcação, nenhuma UI. A feature só fala quando tem algo a dizer.

6Riscos e mitigações

RiscoMitigação
Docs muito grandes estouram o localStorage (5–10 MB)Snapshot guarda textContent truncado por bloco (ex.: 2 KB) + hash; cota cheia → feature desliga em silêncio (try/catch em tudo).
LCS em docs com centenas de blocosLCS de elementos é barato (poucas centenas de nós, não linhas); prefixo/sufixo iguais são cortados antes. Se doer, otimiza depois.
Reordenação de parágrafos parece “tudo mudou”LCS já lida: bloco movido = mesmo texto = sem marcação (posição não entra na comparação, só identidade textual).
Markdown/HTML inline (negrito, links) perdido no word-diffWord-diff só em blocos “changed”; renderiza com <ins>/<del> preservando o HTML original dos spans — comparar por texto, destacar por nós de texto.
Favicon original é externo/CORS bloqueia canvasFallback: favicon próprio gerado (círculo com a primeira letra do title) + ponto. Caso raro — docs locais usam emoji/data-URI.
Usuário perde o reload instantâneo “puro”Não perde: o reload continua; os destaques são aditivos. Se fizer falta uma opção “sem marcação”, flag no _config.json depois.

7Ordem de implementação

  1. client/changes.js: snapshot + LCS de elementos + marcação inline (core).
  2. Word-diff inline nos pares alterados.
  3. Favicon dinâmico + prefixo no title.
  4. Minimap + barra “N mudanças / próxima / já vi tudo”.
  5. inject.js: injetar o script.
  6. Testes manuais: salvada única e múltipla, doc grande, editor visual, localStorage limpo, manager multi-root.
  7. Opcional: badge ● na sidebar (nav.js).

8Quiz

Teste se o design ficou claro — clique para responder.

1 · Por que o diff é calculado no cliente (localStorage) e não no servidor, como na v1?

O reload que já existe carrega a versão nova; comparar o DOM atual contra o snapshot da última visita é natural no cliente. Bônus: o baseline é da aba, não do processo — funciona mesmo se o server caiu e voltou, e com mudanças feitas enquanto nenhuma tab estava aberta.

2 · Você nunca abriu uma doc nesse browser e o agente a editou 5 vezes. Ao abrir, o que aparece?

Degradê gracioso: sem snapshot, sem marcação, sem UI — a feature só fala quando tem algo a dizer. O caso “nunca abri” seria coberto pelo badge ● na sidebar (item opcional), que compararia do lado do servidor.

3 · O que acontece com a bolinha azul na tab?

Não existe “badge de tab” nativo para páginas — o favicon dinâmico via canvas é o padrão de mercado. Como o shell (top window) não recarrega junto com o iframe, o baseline limpo do favicon/title é guardado em sessionStorage para não acumular “● ●”.

4 · Um parágrafo foi movido de lugar sem mudar uma vírgula. O que o destaque mostra?

O LCS casa o texto antigo com o novo independente de posição, e o pool de blocos “não contabilizados” reconhece um + cujo texto já existia como movimento. Falso positivo de reordenação foi exatamente o caso de teste T4 da implementação.

5 · Quanto o servidor mudou para suportar a feature?

O evento SSE {base, path} já bastava — quem dispara tudo é o location.reload() que já existia. O no-store foi um bug pré-existente de live reload descoberto durante o teste E2E no browser real.

9Sidebar e aba aberta

Duas perguntas frequentes: a sidebar participa? A doc precisa estar aberta numa tab?

A sidebar: badge ● nos itens

Além dos destaques dentro do doc, a sidebar participa com um sinal próprio: quando uma doc muda sem estar aberta, seu item na sidebar ganha um ● verde — o jeito de perceber mudanças em docs que você não está olhando sem precisar abri-las. Ela continua sem recarregar (estado de colapso/scroll preservado). Quem “carrega” o sinal na tab é o favicon e o title do shell, que o changes.js altera de dentro do iframe (mesma origem).

O badge ● na sidebar — implementado

O nav.js escuta o CustomEvent("docs-in-html:change") que o reload client já disparava em cada mudança, e marca com um ● verde os itens da sidebar cujas docs mudaram — o dot some quando você abre a doc (os destaques inline assumem dali). Detalhes: o dot é um ::after posicionado no item (zero DOM extra), a doc atualmente aberta nunca ganha dot (ela mostra os destaques no próprio corpo), e o conjunto de docs alteradas sobrevive a rebuilds da sidebar (re-aplicado após build()). Limite conhecido: o dot só nasce de mudanças que acontecem enquanto o shell está aberto — mudanças de quando tudo estava fechado aparecem só como destaques inline ao abrir a doc.

Precisa a doc estar aberta numa tab?

Não — e essa é a propriedade mais importante do design. O que os destaques comparam é “agora” contra “a última vez que este browser abriu esta doc” (snapshot no localStorage). O snapshot é atualizado em cada visita, não em cada edição. Então:

CenárioResultado
Doc aberta numa tab, agente editaReload em tempo real (via SSE) + destaques imediatos — precisa do server rodando
Doc fechada, agente edita (server rodando ou não), você abre depoisDestaques aparecem no load: “mudou desde a última visita”. Sem server, sem SSE — e funciona igual
Várias edições acumuladas enquanto você não olhouUma visita mostra o delta acumulado inteiro (a comparação é sempre contra a última visita)
Você nunca abriu esta doc neste browserNada — sem “antes” não há diff (o ● da sidebar cobre parte desse caso, enquanto o shell estava aberto)

6 · A sidebar mostra hoje quando uma doc mudou?

O dot é um ::after no item, alimentado pelo CustomEvent("docs-in-html:change") que o reload client já disparava — o nav.js só passou a escutá-lo. A doc atualmente aberta nunca ganha dot (mostra os destaques no próprio corpo), e mudanças feitas com tudo fechado só aparecem como destaques inline ao abrir.

7 · O server foi morto, o agente editou a doc direto no disco, e só amanhã você reabre tudo. Os destaques aparecem?

O SSE (que exige server) só serve para o reload em tempo real. A marcação em si roda em cada load, contra o baseline do browser — e o dot na sidebar usa o mtime do manifest, então até ele sobrevive a server fora do ar. Abrir o arquivo direto do disco também funcionaria, desde que você já tivesse visitado a doc antes na mesma origem.
