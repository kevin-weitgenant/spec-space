1Contexto

Como a página de cards funciona hoje — do registry ao HTML — e onde as três features vão se apoiar.

Rampa para iniciante (pode pular). O manager é um servidor Node (manager.js) que lê uma lista de pastas de docs do arquivo ~/.docs-in-html/registry.json e serve cada uma em /<slug>/. A página inicial é um único HTML estático (client/manager.html) com JS puro, sem build. Um card por pasta, renderizado a partir de GET /api/docs.

O registry é o estado do manager

Hoje o registry.json tem exatamente uma chave útil, docs: um array plano de caminhos absolutos. A ordem dos cards é, na prática, a ordem desse array — que só muda quando algo é adicionado ou removido. Não existe noção de agrupamento, e o loader é tolerante por design: chaves desconhecidas são preservadas, arquivo ausente vira registry vazio, arquivo corrompido é backupeado e resetado. Essa tolerância é a nossa porta de entrada para estender o formato.

O ciclo de vida da página

GET /api/docs→ render() monta os cards→ setInterval re-fetch a cada 5s→ render() de novo (innerHTML)

O loop de polling — importante: ele reconstrói todo o grid a cada 5 segundos.

O inimigo oculto: o polling de 5 segundos
Como render() limpa e refaz o innerHTML do grid a cada refresh, qualquer estado que more só no DOM (um drag em andamento, um modal aberto, um card arrastado visualmente) é destruído no meio da interação. Hoje isso é invisível porque a página quase não tem estado. Este plano adiciona estado de interação — então o polling precisa aprender a se comportar: pausar enquanto o usuário está arrastando ou com um modal aberto, e reconciliar (não recarregar do zero) quando os dados mudam por fora.

A remoção hoje

O card tem um botão ✕ Remover vermelho na fileira de ações, que chama o confirm() nativo do navegador — funcional, mas feio, e o vermelho fixo chama mais atenção do que a ação merece: remover uma docs do manager é uma operação reversível e rara, não uma destruição.

2Intuição

Uma ideia unifica as três features: a lista plana de pastas vira uma lista de "cartões em um mural" — com posição própria e com prateleiras (pastas) onde podem ser guardados.

Layout, não banco

Pense no registry como um quadro de cortiço: hoje cada pasta ocupa o próximo buraco livre, na ordem em que chegou. A mudança dá a cada card duas novas liberdades — posição (onde no mural) e prateleira (em qual pasta visual) — e ambas são metadados de apresentação, não de registro. Uma docs continua registrada ou não, independentemente de estar na "prateleira Trabalho" ou solta no topo. Por isso o novo estado mora numa chave separada (layout) dentro do mesmo arquivo: se ela sumir ou for inválida, os cards simplesmente voltam ao comportamento atual, sem nada quebrado.

docs: [a, b, c, d, e, f] → docs: [a, b, c, d, e, f] layout: { ordem + grupos }

O array docs continua sendo a fonte da verdade do registro; o layout só diz como exibi-lo.

Dados de exemplo

Com seis docs e duas pastas criadas ("Trabalho" e "Estudos"), o registry fica assim — note que e e f não estão em nenhuma pasta e aparecem na área "Sem pasta":

{
  "docs": ["C:\\…\\projeto-a\\docs", "C:\\…\\projeto-b\\docs", …],
  "layout": {
    "order": ["g1", "a", "b", "g2", "c", "d", "e", "f"],
    "groups": { "g1": { "name": "Trabalho" }, "g2": { "name": "Estudos" } },
    "assign": { "a": "g1", "b": "g1", "c": "g2", "d": "g2" }
  }
}

A chave order intercala ids de grupos e chaves de docs (o caminho absoluto serve de id estável — pastas não mudam de lugar sem serem re-registradas). É uma "playlist" única: reordenar cards e pastas é editar a mesma lista; mover um card para dentro de uma pasta é uma atribuição em assign.

O ✕ e o modal: coerência com a raridade da ação

Remover é raro e reversível (é só adicionar de novo). A UI deve refletir isso: o ✕ some no cotovelo do card — visível apenas no hover, cinza, sem moldura — e o vermelho só aparece no momento da decisão, dentro do modal. O confirm() nativo sai de cena por não ser estilizável e por bloquear a thread.

Passe o mouse e clique no ✕ — é o card real do plano.

Remover "Docs-html DOCS"?

Só tira a docs do manager — nenhum arquivo é apagado, e você pode adicioná-la de novo a qualquer momento.

3Mudanças

Quatro arquivos, na ordem em que as peças se apoiam: primeiro o modelo de dados, depois a API, depois a página.

registry.js — o modelo de layout

Um novo conjunto de funções de leitura/escrita da chave layout (carregar, salvar, criar/renomear/apagar grupo, mover doc para grupo, reordenar). A disciplina central é a higiene: toda escrita revalida o layout contra os docs realmente registrados — caminhos que não estão mais em docs são podados de order e assign; ids de grupo referenciados sem definição geram o grupo de novo ou são limpos. Docs novas que ainda não constam no layout entram no fim, fora de qualquer pasta. Apagar um grupo não remove os docs: eles voltam para "Sem pasta".

manager.js — endpoints e enriquecimento da lista

Dois pontos de mudança. Primeiro, GET /api/docs passa a devolver, junto de cada card, o id/nome do grupo a que pertence, e a ordem global — a página recebe o mural pronto. Segundo, um endpoint único POST /api/layout recebe o layout inteiro (order + groups + assign) e o salva — em vez de meia dúzia de endpoints granulares. Isso é seguro porque o servidor valida: só aceita caminhos registrados e descarta o resto, e responde com o layout saneado de volta, que a página adota como nova verdade. A remoção existente ganha um detalhe: ao tirar um doc do registry, o layout é limpo junto (a função de higiene cuida disso de graça).

client/manager.html — o mural de verdade

É onde quase toda a experiência mora, em quatro blocos:

  • ✕ e modal: o botão vira um ícone fantasma absoluto no canto superior direito (opacidade 0 → 1 no hover do card); o clique abre um modal em HTML/CSS com título, a mesma mensagem tranquilizadora do confirm() atual ("nenhum arquivo é tocado") e os botões Cancelar / Remover. O modal de confirmação é reaproveitado como componente para as ações destrutivas de pastas (renomear não precisa; apagar grupo sim).
  • Drag & drop: cada card e cada cabeçalho de pasta é arrastável (drag & drop nativo do HTML5, sem bibliotecas). Os alvos são: qualquer posição entre cards (indicador de inserção), e o corpo de qualquer pasta. Soltar dispara o POST do layout e atualiza otimisticamente a tela. Alvos válidos ganham destaque visual; arrastar um card para a área "Sem pasta" tira ele do grupo.
  • Pastas: um botão "＋ Nova pasta" cria o grupo (nome editável inline na hora, e depois por duplo-clique no título). Cada pasta renderiza como uma seção com cabeçalho, contador de docs e corpo que aceita drops; pode ser recolhida (estado aberto/fechado também persistido no layout). Pastas vazias são permitidas e podem ser apagadas via seu próprio ✕ (com o mesmo modal).
  • Reconciliação com o polling: o refresh de 5 segundos não toca no DOM enquanto há um drag ativo ou modal aberto; ao retomar, compara os dados novos com os atuais e só re-renderiza se algo realmente mudou por fora — suas pastas e ordem não "piscam" a cada tick.
Sem biblioteca de drag
O drag & drop nativo (draggable, dragover, drop) cobre tudo o que o mural precisa e mantém a página com zero dependências — o espírito do projeto (HTML+JS puro, sem build). A única fineza é e.preventDefault() em dragover para o drop ser permitido, e um marcador de posição para indicar onde o card cairia.

Compatibilidade e migração

Não há migração: um registry antigo simplesmente não tem layout, e o primeiro carregamento o trata como "tudo solto, na ordem do array docs" — exatamente o comportamento de hoje. O primeiro drag do usuário escreve o layout pela primeira vez. Versões antigas do pacote lendo o mesmo arquivo ignoram a chave (o loader já preserva desconhecidas).

4Quiz

Cinco perguntas para checar se o design ficou claro.

1. Por que a ordem e os grupos moram numa chave layout separada, em vez de o array docs virar uma estrutura aninhada com pastas?

✅ B. A separação torna o layout puramente cosmético: qualquer problema nele é podado pela higiene e o manager continua servindo todas as docs normalmente. Uma estrutura aninhada misturaria as duas responsabilidades — e um erro de agrupamento poderia "perder" uma docs da lista.

2. Qual o papel da função de "higiene" na escrita do layout?

✅ C. Como o registry muda por várias vias (API, CLI, edição manual, polling), o layout pode referenciar coisas que já não existem. A higiene garante que ele sempre volte consistente — é o que torna o formato tolerante como o resto do arquivo.

3. Por que um único POST /api/layout recebendo o mural inteiro, em vez de endpoints granulares (mover, renomear, reordenar…)?

✅ A. O drop é uma operação composta. Grava-la de uma vez simplifica o cliente (não precisa orquestrar chamadas) e o servidor (um ponto único de validação), e a resposta saneada elimina divergência entre o que a UI acha e o que ficou salvo.

4. O que precisa acontecer com o polling de 5 segundos quando este plano for implementado?

✅ C. O polling existe para pegar mudanças externas (CLI, outro terminal) e continua útil. O problema novo é que render() por innerHTML apaga estado de interação; a solução é torná-lo educado: espera e reconcilia, em vez de refazer às cegas.

5. O usuário arrasta um card para DENTRO de uma pasta chamada "Trabalho". O que muda no registry?

✅ B. O registro nunca muda com um gesto de organização. O que muda é a apresentação: a atribuição em layout.assign e, se a posição também mudou, a playlist layout.order. Gravação é imediata via POST /api/layout.
