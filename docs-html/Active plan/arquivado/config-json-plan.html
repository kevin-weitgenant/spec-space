Plan: Um só _config.json pra governar tudo

Background — onde as coisas moram hoje

Hoje existem três fontes de configuração, mais dois valores hardcoded:

O quêOnde está hojeQuem lê/escreve
Animação da sidebar (reveal/slide/guide)_config.json → sidebarAnimserve.js (readAnim) e export.js — já existe!
Ícones de pasta_icons.json — {"guides": "book-open", "dados": "🧮"}lido no manifest.js; mantido sincronizado pelo serve.js ao renomear/mover/deletar (shiftIcons/pruneIcons)
Ordem manual (drag) por pasta_order.json — {"": ["b.html","a.html"], "guides": [...]}lido no manifest.js; escrito pelo POST /__order__
Título da aba do navegadorHardcoded: <title>Docs</title> no shell.jsninguém — imutável
FaviconNenhum (o 📚 do header é só texto, a aba fica sem ícone)—
Detalhe importante: o shell tem duas encarnações. No dev server (serve.js) ele é gerado por request e pode ser o index.html do usuário, se existir. No export estático (export.js) ele é escrito no disco uma vez. Qualquer mudança de título/favicon precisa cobrir os dois caminhos — e o export não pode depender de endpoints de servidor.

A proposta: o formato do _config.json

O _config.json já existe e já é escondido da sidebar (prefixo _). A ideia é promovê-lo a arquivo único de configuração do site, absorvendo os outros dois:

{
  "title": "Minha Docação — Handbook",
  "favicon": "🚀",
  "sidebarAnim": "slide",
  "icons": { "guides": "book-open", "dados": "🧮" },
  "order": { "": ["intro.html", "comecando.html"], "guides": ["api.html"] }
}

Título

title substitui o <title> da aba e o texto 📚 Docs · live do header do shell. No dev server, o serve.js injeta o valor ao servir o shell (mesmo lugar onde já injeta o <base href="/">). No export, o export.js escreve o título direto no index.html congelado. Bônus barato: o nav.js pode atualizar o título da aba conforme o doc aberto ("Introdução · Minha Docação") — o navegador mostra onde você está sem olhar pra sidebar.

Favicon

Duas formas aceitas, para que "fácil" seja realmente fácil:

  • Emoji ("favicon": "🚀") — o servidor gera na hora um mini-SVG com o emoji (<text>🚀</text>) e injeta <link rel="icon" href="data:image/svg+xml,…">. Zero arquivos, funciona até no export (data URI vai embora embutida no HTML congelado).
  • Path de arquivo ("favicon": "assets/favicon.svg") — injeta <link rel="icon" href="/assets/favicon.svg">. O arquivo precisa existir na pasta de docs (o export copia a pasta inteira, então vai junto de graça).

O manifest.js passa a ler icons e order de dentro do _config.json. O serve.js passa a escrever neles no mesmo lugar (o shiftIcons/pruneIcons e o POST /__order__ já fazem o bookkeeping — só trocam o arquivo de destino).

Auto-scaffold no primeiro serve

Novato no pacote, zero passos: quando você roda docs-in-html nome_pasta e a pasta ainda não tem _config.json, o servidor cria um com defaults espertos:

{
  "title": "Nome Da Pasta",
  "favicon": "📚",
  "sidebarAnim": "guide"
}

O título é o nome da pasta humanizado — a mesma regra que o sidebar já usa pra arquivos (meu-projeto → Meu Projeto). O terminal avisa na primeira vez:

docs-in-html · serving C:\docs\meu-projeto
  ✓ criado _config.json — ajuste title/favicon lá (hot reload pega na hora)
  → http://localhost:8000

Como o arquivo já vem com as chaves certas e o live reload observa a pasta, trocar o título vira: abrir o JSON, editar uma linha, salvar — a aba atualiza sozinha. Edição manual de JSON é a UI mais barata que existe; um endpoint de settings seria superdimensionamento.

Quem cria o arquivo é só o serve, nunca o export: o comando de export é read-only na pasta fonte (detalhes na próxima seção) — ele não deve surpreender ninguém escrevendo arquivos numa pasta que só está sendo congelada.

Mudanças por arquivo

ArquivoMudança
serve.jsUma função readConfig() única (substitui readAnim/loadIcons): lê o _config.json uma vez por request. Ao servir o shell, aplica title (replace no <title> e no header) e favicon (injeta o <link rel="icon"> com data-URI ou path). Os writes de bookkeeping (shift/prune de ícones, __order__) passam a editar as seções icons/order do config, preservando as demais chaves. O /__manifest__ já leva anim; passa a levar title também (para o bônus do título por doc, no cliente).
manifest.jsbuildTree lê order e icons do _config.json (com fallback pros arquivos legados, ver abaixo).
export.jsO shell congelado (index.html) recebe o mesmo tratamento de title/favicon que o dev server aplica. O export não escreve config novo — só lê.
shell.jsNenhuma mudança de conteúdo — o shell continua o template neutro (<title>Docs</title> como placeholder que será substituído); adicionamos um <!--title-->-friendly hook se o replace por string ficar frágil.
client/nav.jsBônus: usar o title do manifest para reescrever document.title como "Nome do doc · Título do site" quando o doc muda no iframe.
init.jsNovos projetos via init também ganham o _config.json de exemplo (mesmos defaults do auto-scaffold).

Compatibilidade e migração

Não queremos quebrar ninguém (nem você mesmo) que já tem _icons.json/_order.json funcionando:

Leitura (sem quebra)

Prioridade: seção icons/order do _config.json vence; se ausente, cai para o _icons.json/_order.json legado. O sidebarAnim continua válido como alias — quem já usa _config.json pra animação não percebe nada.

Escrita (migração preguiçosa)

O primeiro write (reordenar, trocar ícone, renomear pasta) absorve o legado: lê os dois arquivos velhos, escreve tudo no _config.json e deixa os antigos intocados (ignorados daí em diante). Sem comando de migração, sem quebra — os arquivos velhos viram vestígio inofensivo.
Caso de borda — index.html do usuário: quando a pasta tem index.html próprio, ele é o shell. Title e favicon aí são responsabilidade do autor do HTML — mas o dev server injeta o <link rel="icon"> mesmo assim se a página não tiver um, e o título só é aplicado se o <title> dele for o default "Docs".

E o export? Como o config se comporta lá

O comando export congela a pasta uma vez: copia tudo, gera o manifest.json com a árvore pronta (ordem e ícones já aplicados) e reescreve os HTMLs com as tags injetadas. No site estático não existe servidor — então o config é assado (baked), não lido:

O que é assado no export

  • Título e favicon — escritos de vez no index.html congelado (mesma injeção do dev server, só que no disco). O favicon-emoji vira data URI embutida.
  • Ordem e ícones — aplicados pelo buildTree na geração do manifest.json.
  • Animação — vai dentro do manifest.json (já é assim hoje com o sidebarAnim).

O que não vai junto

  • O _config.json em si — inútil no estático (ninguém lê) e copiado hoje por acaso, junto com _order.json/_icons.json. A mudança: o copyDir do export passa a pular esses arquivos de configuração no output. Pasta publicada mais limpa, sem vazar o “porão” de configuração.
  • Writes — o export nunca escreve na pasta fonte (nem cria _config.json lá): ele só lê. Se a fonte não tem config, usa os defaults (Docs, sem favicon).
Tradução prática: dev server = config vivo, recém-lido a cada request (o watcher até dá hot reload quando você salva o JSON). Export = fotografia: tudo que o config decidiu fica gravado nos arquivos finais, e o JSON deixa de ser necessário. Editar o _config.json depois do export muda o site dev, não o congelado — exporta de novo pra atualizar.
