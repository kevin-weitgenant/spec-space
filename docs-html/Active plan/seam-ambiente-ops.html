Plano: seam de ambiente — módulo ops

Hoje, nove módulos do docs-in-html chamam node:fs diretamente, e abrir coisas no sistema operacional (Explorer, Finder, xdg-open, Warp, navegador) está implementado — com pequenas variações — em quatro lugares. Este plano introduz um único módulo ops.js: a única porta por onde o projeto fala com o ambiente, e a alavanca que torna registry, scan, reload e manager testáveis sem tocar no seu home nem lançar processos reais.

Candidato 2 · “Seam explícito de ambiente (ops)” · docs-in-html · zero dependências, Node ≥ 18, CommonJS

1Contexto

Rampa para iniciante (pode pular)

O docs-in-html é um pequeno servidor de desenvolvimento escrito em JavaScript para Node.js. Ele serve pastas com arquivos HTML, recarrega a página no navegador quando um arquivo muda (hot reload) e tem alguns comandos de conveniência: revelar um arquivo no explorador de arquivos, abrir uma pasta no terminal Warp, abrir o navegador. Para fazer tudo isso, o programa conversa com o mundo externo — o disco rígido, o sistema operacional, a sua pasta pessoal (o “home”). Em código, essas conversas acontecem por funções como fs.readFileSync, os.homedir() e child_process.spawn.

O problema: quando essas chamadas estão espalhadas pelo código, fica difícil testar o programa sem, ao mesmo tempo, mexer em arquivos reais do seu computador. A ideia central deste plano é empacotar todas essas conversas num único módulo (ops.js), para que os testes possam trocar a versão real por uma versão falsa, que só existe na memória. É como ter um telefone dedicado para falar com o mundo: em produção o telefone é real; nos testes, é um telefone de brinquedo que anota tudo o que você pediria.

Para quem já conhece o código, o diagnóstico é concreto e mensurável.

Arquivo e processo como dependências diretas

Uma busca por require("node:fs") no repo encontra nove módulos: config.js, export.js, init.js, manager.js, manifest.js, registry.js, reload.js, roots.js e scan.js. Cada um carrega os builtins do Node diretamente no topo — não existe nenhum ponto de inserção entre a lógica e o disco. O mesmo vale para node:child_process:

  • roots.js, na rota __reveal__ (linhas ~224-228): três chamadas spawn com detached:true, stdio:"ignore" — explorer /select,... no Windows, open -R no macOS, xdg-open no Linux.
  • manager.js: /api/reveal (linhas ~197-201) repete exatamente o mesmo trio explorer / open / xdg-open; /api/open-warp (linhas ~50-51 e ~206-229) resolve o binário do Warp procurando $WARP_BIN, depois localizações padrão, e por fim execFile("where"/"which"); e a abertura de navegador usa exec(cmd) com start/open/xdg-open.
  • serve.js (linhas ~155-158): mais uma cópia do padrão start "" / open / xdg-open via exec, quando doOpen está ativo.

São três ou quatro implementações duplicadas de “abrir isto no sistema operacional”, cada uma com suas pequenas divergências de tratamento de plataforma — o tipo de código onde um bug corrigido num lugar sobrevive nos outros.

Estado global capturado cedo demais

Os casos mais dolorosos para testes são os que leem o ambiente no momento do require:

  • registry.js (linhas 10-11): const DIR = path.join(os.homedir(), ".docs-in-html") roda quando o módulo é carregado, antes de qualquer função ser chamada. Um teste que queira apontar o registro para um diretório temporário precisa ou fazer monkeypatch antes do primeiro require (com cache de módulo e ordem de carregamento interferindo), ou aceitar que o teste lê e escreve na pasta ~/.docs-in-html real do usuário.
  • scan.js (linha 17): CACHE_FILE deriva daquele mesmo DIR — o cache do scanner mora no seu home, com a mesma restrição.
  • reload.js (linha 23): createReload chama fs.watch(root, {recursive:true}, ...) como efeito colateral do construtor. Qualquer teste que construa um root via createRoot ou chame manager.start ganha watchers reais sobre diretórios reais — que ainda por cima vazam se o teste não fechar.
Por que isso importa agora

Nada disso é bug: o sistema funciona. É dívida estrutural. Enquanto o ambiente for uma dependência implícita, cada novo teste paga um imposto — monkeypatch frágil, tmpdir com limpeza manual, ou simplesmente “não testamos isso”. O plano a seguir troca o imposto por uma interface explícita.

2Intuição

A ideia central é o conceito de seam: um ponto do programa onde você pode trocar o comportamento sem editar o código ao redor.

Pense num código que calcula o preço de uma venda mas grava o log direto no console do sistema. Você não consegue testar o cálculo sem gerar lixo no console. Agora imagine o mesmo código chamando log(msg) — uma função recebida de fora. Em produção você passa a função que escreve no console; no teste, passa uma que só joga as mensagens numa lista. O cálculo não mudou uma linha; o que mudou é que agora existe uma costura onde os dois mundos se encontram. Michael Feathers chama esse ponto de seam; a implementação concreta que você pluga nele, de adapter.

Dois adapters justificam a costura

Um seam só se paga se existem pelo menos duas implementações plausíveis do outro lado. Aqui elas são óbvias:

módulos do projeto
(roots, manager, registry…) → ops.readFile / spawn / watch / homeDir… → adapter Node
(builtins reais) · adapter de teste
(memória / noop)

Uma interface, dois adapters: produção fala com o mundo real; testes falam com um mundo de mentira.

Exemplo concreto com o registry. Hoje, registry.js computa DIR a partir de os.homedir() no require. Com o seam, o módulo passa a pedir o home ao ops no momento em que precisa — e o ops que recebe é o que o chamador injetou. Um teste monta um ops em memória cujo homeDir() devolve um diretório temporário (ou até um caminho fictício, se o readFile/writeFile também forem falsos), e o registry inteiro se torna testável sem que o disco do usuário seja tocado.

Exemplo com o watcher. reload.js chama ops.watch(root, cb). No adapter Node, isso é fs.watch recursivo como hoje. No adapter de teste, é um objeto com um método emit(relPath) que o teste dispara à mão: “simule que o usuário salvou index.html” — e o teste observa o SSE do hot reload reagir, sem nenhum watcher real, sem depender de timeouts do sistema de arquivos.

Exemplo com “abrir no OS”. O trio explorer/open/xdg-open vira ops.openPath(abs), e o Warp e o navegador viram ops.spawn(bin, args) e ops.openUrl(url). Nos testes, são noops que registram as chamadas: um teste de /api/reveal afirma apenas “o adapter anotou openPath("/docs/proj")” — o teste nunca lança um Explorer.

Seis chamadores, um seam, dois adapters. A seta dos testes é a que não existe hoje.

O princípio de localidade

Hoje, saber quais efeitos um teste pode disparar exige ler nove arquivos. Depois do plano, a resposta é uma: “olhe o que o código chama no ops”. O efeito colateral ganha um endereço único — e o resto do sistema pode ser lido como lógica pura.

3Mudanças

Um módulo novo e seis ajustes cirúrgicos, sem mudança de comportamento observável em produção. Nenhuma dependência nova; continua CommonJS, Node ≥ 18.

1 · ops.js (novo)

O módulo define a interface do seam — readFile, writeFile, stat, readdir, rename, unlink, mkdir, rm, watch, spawn (detached), openPath, openUrl, homeDir — com a implementação padrão sendo os builtins do Node. Os helpers de plataforma (openPath escolhendo entre explorer/open/xdg-open, openUrl entre start/open/xdg-open) moram aqui, escritos uma vez. A injeção acontece por opts.ops nas funções que precisam e por um setter a nível de módulo para os casos onde o valor já foi capturado no require — a forma exata:

module.exports = createDefaultOps();      // usado por padrão
module.exports.setOps = (o) => { ... };   // troca o adapter global

A intenção de design: o adapter default é exportado como o módulo inteiro, de modo que o código existente continue parecendo idêntico (ops.readFile(...)), e o teste só chama setOps no beforeEach.

2 · registry.js

As linhas 10-11 deixam de computar DIR de os.homedir() no require. O diretório passa a ser resolvido sob demanda, consultando ops.homeDir() — o que o torna sensível ao adapter injetado mesmo depois do módulo carregado. As operações de leitura/escrita do registro trocam node:fs por ops. Resultado: testar o registry exige apenas um ops com home fictício; nada no seu home real é lido ou escrito.

3 · scan.js

CACHE_FILE deixa de ser constante derivada de DIR no escopo do módulo e passa a ser computado quando o scan roda, a partir do mesmo ops.homeDir(); writeFileSync do cache (linha ~53) e o readdir/resto das primitivas de arquivo migram para ops. Ganho direto: um teste do scanner com cache pode usar memória e ainda exercitar a lógica de “cache expirado/inválido”.

4 · reload.js

O construtor deixa de ter o fs.watch como efeito colateral incondicional: chama ops.watch(root, cb) (linha ~23 hoje), recebendo um objeto observável com close(). O adapter Node devolve o fs.watch recursivo atual — inclusive o mesmo fallback amigável quando fs.watch não existe. O adapter de teste devolve algo com emit(). createRoot/manager.start em testes param de registrar watchers reais.

5 · roots.js

A rota __reveal__ (linhas ~224-228) troca o trio manual de spawn por uma única chamada ops.openPath(abs) — a distinção “diretório abre nele mesmo, arquivo abre com seleção do pai” vira lógica interna do helper. As demais operações de arquivo do handler de root migram para ops. Duplicação removida: primeira das cópias de “abrir no OS”.

6 · manager.js

Três frentes: /api/reveal (~197-201) passa a ops.openPath; /api/open-warp usa ops.spawn para o Warp e para o where/which da resolução de binário (~50-51) — a política de busca ($WARP_BIN → localizações padrão → PATH) permanece no manager, onde está a lógica de domínio, só a execução cruza o seam; e a abertura de navegador delega a ops.openUrl. Nos testes, um noop registrador permite afirmar “o manager pediu para abrir o projeto, não a pasta de docs” sem lançar nada.

7 · serve.js

O bloco doOpen (~155-158) substitui a string de comando com start/open/xdg-open por ops.openUrl(url); o exec importado no topo deixa de ser necessário. O serve continua sem saber nada de plataformas.

Ordem e agrupamento

As mudanças se constroem em sequência: primeiro o seam (ops.js), depois os consumidores do home capturado cedo (registry.js → scan.js, que depende do primeiro), em seguida os efeitos de processo (reload.js, roots.js, manager.js, serve.js — cada um independente dos outros, todos dependentes apenas de ops.js). Qualquer passo pode parar no meio sem deixar o sistema quebrado: cada migração é invisível em produção, porque o adapter default é comportamentalmente idêntico ao código atual.

O que não muda

Nenhuma rota nova, nenhum formato de arquivo novo, nenhuma flag de CLI. O comportamento em produção é byte a byte equivalente — este plano é infraestrutura para a qualidade dos testes que virão depois.

4Quiz

1. O que caracteriza um seam num programa?

✅ B. Seam é a costura: o local onde duas partes se encontram de forma que uma pode ser substituída (por um adapter) sem alterar a outra. Não exige pureza nem rede — exige trocabilidade.

2. Por que registry.js:10-11 (DIR = path.join(os.homedir(), ...) no require) é um problema de teste?

✅ C. O estado ambiental é congelado no momento do require. Com o seam, homeDir() é consultado sob demanda via ops injetado, e o teste troca o adapter a qualquer momento.

3. Por que se diz que “dois adapters justificam o seam”?

✅ A. O valor de uma interface está nas trocas que ela permite. Aqui: Node ops em produção, ops em memória/noop nos testes — a segunda existe justamente para exercitar o seam.

4. No plano, reload.js passa a chamar ops.watch(root, cb). Qual é o ganho principal para testes do hot reload?

✅ D. Hoje construir um root já registra fs.watch recursivo em diretório real (efeito colateral do construtor). Com o seam, o evento de mudança vira algo que o teste dispara deterministicamente.

5. Em manager.js, a busca do binário do Warp ($WARP_BIN → localizações padrão → where/which) permanece no manager, e só a execução vai para o ops. Por quê?

✅ B. Um bom seam é estreito: atravessa a fronteira apenas o que é efeito no mundo (spawn/execFile). A política de onde procurar é comportamento do sistema e continua testável por cima do seam.
