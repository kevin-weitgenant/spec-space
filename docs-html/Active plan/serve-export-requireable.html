Plano: serve.js e export.js requireable

Hoje, require("./serve.js") num teste ou inicia um servidor de verdade, mata o processo, ou os dois. Este plano separa o que decide (parse de argumentos) do que faz (rede, arquivos, exit), tornando os dois entrypoints da CLI importáveis e testáveis — sem mudar nada para quem usa o bin.

1Contexto

Rampa para iniciante (pode pular)

No Node, um arquivo pode ser duas coisas ao mesmo tempo: um programa (quando você o executa direto, node serve.js ou via bin do package.json) e um módulo (quando outro arquivo faz require("./serve.js") para reaproveitar suas funções). O Node expõe uma forma de distinguir os dois casos: dentro do módulo, require.main === module vale true apenas quando o arquivo foi executado direto. A receita clássica de CLI bem-comportada é: funções puras e exportadas no corpo do módulo; efeitos colaterais (abrir servidor, sair do processo) numa "footer" guardada por if (require.main === module). Assim o mesmo arquivo serve aos dois públicos.

Outra peça: process.exit(n) encerra o processo inteiro imediatamente. Num teste (que roda dentro do mesmo processo), isso mata o runner. Bibliotecas testáveis preferem lançar Error — o chamador decide se vira exit code.

O que existe hoje, nos arquivos reais:

serve.js — tudo acontece no corpo do módulo

O parse de argumentos roda no top level: em serve.js, logo após o help(), o laço for (linhas ~45–65) varre process.argv.slice(2) em variáveis soltas — dir, port (default Number(process.env.PORT) || 8000), mode, portWasExplicit, doOpen, outDir, noRegister, unregister. E o corpo do módulo contém quatro pontos de process.exit() que disparam no momento do require:

-h / --helpimprime ajudamata o processo com exit 0

No caminho padrão (serveSingle), há mais process.exit(1) nos handlers de erro de porta (explícita ocupada, EACCES, fallbacks esgotados). Ou seja: um require("./serve.js") num teste ou morre, ou sobe um servidor HTTP de verdade com watch de filesystem — nada reutilizável, nada testável. O módulo não exporta nada.

Dentro desse bloco vive lógica que mereceria teste: a semântica de porta (MAX_FALLBACKS = 20; --port explícito é ordem — deve estar livre ou morre com mensagem clara; sem --port, cai para a próxima livre com aviso), a delegação ao manager (pingManager()/addToManager() via delegation.js), o auto-scaffold de _config.json (writeConfig(ROOT, defaultConfig(ROOT)) quando não existe), o registry.add(ROOT) silencioso, e a abertura de browser por SO (start/open/xdg-open via exec).

export.js — quase lá

export.js já é um módulo de verdade: exporta run(root, outDir). Mas na entrada há if (!fs.existsSync(src)) { console.error(...); process.exit(1); } (~linha 44): pasta inexistente derruba o processo em vez de sinalizar o erro ao chamador. Todo o resto de run é trabalho de disco (copiar pasta, gerar manifest.json, client/ → __docs__/, reescrever HTMLs com injectScripts) e permanece intocado.

O precedente já existe no codebase

registry.js faz exatamente o certo: saneLayout(data) (linhas 83–111) é uma função pura — revalida layout contra docs registradas, poda grupos órfãos, acrescenta o que falta — e entra em module.exports = { slugify, load, save, add, remove, ..., } (linha 163). Por isso dá para testar a higiene do layout chamando a função com um objeto qualquer, sem tocar disco. Este plano copia o mesmo padrão para serve.js e export.js.

2Intuição

A intuição é a de sempre: separar a decisão da ação. Decisões são baratas de testar; ações têm o mundo inteiro acoplado.

Pense em serve.js como dois programas colados num arquivo. O primeiro é um tradutor: recebe ["mydocs", "--port", "8123", "--no-open"] e produz um fato estruturado — "quero servir a pasta X, na porta 8123, explícita, sem abrir browser". Esse tradutor é pura aritmética de strings: dado o mesmo argv, o mesmo resultado, zero rede, zero exit. O segundo programa recebe esse fato e age: sobre HTTP, escreve _config.json, chama o manager, abre o navegador, e — quando algo dá errado — encerra o processo. Hoje os dois rodam em sequência no corpo do módulo, e é por isso que importar o arquivo é sinônimo de executar a CLI.

Exemplo concreto do que fica testável. Hoje a matriz de flags só pode ser exercitada rodando o bin de verdade:

parseArgs(["--port", "9000"])        // → { mode:"serve", port:9000, portWasExplicit:true, ... }
parseArgs(["docs", "export", "--out", "d"]) // → { mode:"export", dir:"docs", outDir:"d", ... }
parseArgs(["-p", "80"])             // Number("80") || port → porta explícita 80
parseArgs(["--port", "abc"])        // Number("abc") = NaN → falsy → mantém default (8080)

Já a semântica de porta pede uma abstração extra. "Tentar porta 8000, se ocupada tentar 8001… até 20 vezes, a menos que a porta tenha sido explícita" é uma máquina de estados pequena e deliciosa de testar — desde que main aceite as dependências injetadas (um listen falso que falha com EADDRINUSE nas duas primeiras chamadas, um openUrl que só registra que foi chamado, um delegation falso). O mesmo vale para o export: um erro lançado é um valor que o teste captura com assert.throws; um process.exit é um processo morto.

argv → parse no corpo do módulo → process.exit() no meio → server real no require

Antes: require("./serve.js") = executar a CLI inteira

parseArgs(argv) → main(options, deps?) async → exit code (return) · require.main === module → CLI

Depois: pureza no corpo, side effects só na footer do bin

Para o main, o fluxo de decisão fica assim:

flowchart TD A["main(args)"] --> B{mode?} B -- help --> C["help(); return 0"] B -- init --> D["init.js init(); return 0"] B -- export --> E["export.js run(); catch → return 1"] B -- manager --> F["manager.js start()"] B -- unregister --> G["registry.remove(); return 0"] B -- serve --> H{"pingManager ok e !noRegister?"} H -- sim --> I["addToManager; return 0"] H -- não --> J{"_config.json existe?"} J -- não --> K["writeConfig default"] J -- sim --> L K --> L["registry.add; createRoot; listen"] L --> M{"porta explícita?"} M -- sim, ocupada --> N["erro claro; return 1"] M -- não, ocupada --> O["próxima livre (até 20), com aviso"] M -- livre --> P["banner + open browser"] O --> P

Fluxo de main() — cada losango vira um caso de teste; as setas para "exit code" são returns, não process.exit.

3Mudanças

Três frentes, ordenadas para que cada uma se apoie na anterior: primeiro o parse puro, depois o main com deps injetáveis, por último o contrato de erro do export.

serve.js

O coração da mudança. Todo o bloco de top level (laço de argv, os if (mode === …) com process.exit, e a chamada a serveSingle()) sai do corpo do módulo e vira duas funções exportadas:

  • parseArgs(argv) — pura. Recebe o array de argumentos (não lê process.argv nem process.env direto; o default de porta fica como parâmetro opcional) e devolve o objeto de opções { mode, dir, port, portWasExplicit, doOpen, noRegister, unregister, outDir }. O caso -h/--help passa a ser um mode: "help" em vez de imprimir-e-matar — a decisão vira dado.
  • main(args, deps) — assíncrona, retorna o código de saída (número), nunca chama process.exit. Recebe as opções já parseadas (ou um argv) e um objeto opcional de dependências para tudo que toca o mundo: delegação ao manager (pingManager/addToManager), abertura de browser (openUrl), e a criação do servidor. Isso torna a máquina de fallback de porta (a recursão start(attemptPort, attemptsLeft) com MAX_FALLBACKS = 20 e a distinção explícita-vs-implícita) exercitável com um listen de mentira que simula EADDRINUSE.

No rodapé do arquivo, o guarda:

if (require.main === module) {
  main(parseArgs(process.argv.slice(2))).then(code => process.exit(code));
}

Tudo que o usuário do bin vê — mensagens, ordem de prints, códigos de saída, comportamento idêntico — permanece: os process.exit só mudam de endereço, do meio do módulo para a footer. A seção serveSingle é reabsorvida por main quase sem mudança de lógica (auto-scaffold de _config.json, registry.add, banner, open por SO); só os exits viram return 1 (com o cuidado de fechar o servidor antes, nos erros de porta).

export.js

Mudança mínima e cirúrgica: em run(), o ramo de pasta inexistente deixa de fazer console.error + process.exit(1) e passa a throw new Error(...) com a mesma mensagem. O arquivo ganha uma footer require.main === module que faz o inverso: chama run(), captura, imprime erro: … e process.exit(1) — o comportamento CLI que já existia, apenas formalizado. O resto do pipeline (copy, manifest, __docs__, injeção) é intocado.

Novos arquivos de teste

Sem framework novo (o projeto é zero-deps): testes em test/ rodando com node --test, seguindo a filosofia já validada por registry.saneLayout:

  • test/serve-args.test.js — matriz de flags contra parseArgs: defaults, -p/--port explícito, --port abc mantendo default, subcomandos, --out, flags booleanas, -h virando mode:"help".
  • test/serve-port.test.js — o fallback: sem --port, um listen falso que falha 2× em EADDRINUSE deve pousar na terceira porta; com --port explícito e porta ocupada, main resolve com código 1 e a mensagem certa; a 21ª tentativa esgota MAX_FALLBACKS. Também cobre o caminho da delegação: com um pingManager falso que responde, nada de servidor é criado — só addToManager.
  • test/export.test.js — assert.throws para pasta inexistente (o caminho que antes matava o runner), e um export happy-path em pasta temporária verificando manifest.json e __docs__/.

Ganhos resumidos

parseArgs testável diretamente (matriz de flags sem subprocesso); lógica de fallback de porta testável com listen falso; caminho de erro do export testável com assert.throws; e o bin fica exatamente como estava — os quatro process.exit apenas se mudam para trás do guarda require.main === module.

4Quiz

1. O que a expressão require.main === module significa dentro de um arquivo do Node?

✅ B. require.main aponta para o módulo de entrada do processo; a comparação dá true apenas na execução direta. É o idiomático "sou programa ou sou biblioteca?".

2. Por que process.exit() no corpo de serve.js impede testes com require("./serve.js")?

✅ C. O código do corpo executa no momento do require — com serve.js atual, --help ou init matam o processo de teste no ato; no modo padrão, sobe um servidor real com fs.watch. O runner morre junto.

3. Na semântica atual de portas do serve.js, qual a diferença entre passar e não passar --port?

✅ A. É exatamente o papel de portWasExplicit: porta explícita é "request, not a hint" — morre com mensagem clara se ocupada; implícita é hint, com MAX_FALLBACKS = 20.

4. Por que main() no plano aceita dependências injetadas (delegação, openUrl, listen) em vez de usar os módulos reais?

✅ D. Injeção transforma efeitos em observações: um listen falso que falha duas vezes permite testar o fallback determinísticamente; um pingManager falso permite testar a delegação sem um manager real rodando.

5. No plano para export.js, como fica o tratamento de "pasta não encontrada" e por quê?

✅ B. Lançar devolve a decisão ao chamador; o bin continua imprimindo erro: pasta não encontrada: … e saindo com 1, mas o teste captura a exceção sem morrer — o mesmo contrato que registry.js já pratica com saneLayout.
