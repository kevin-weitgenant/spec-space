Plano: client/lib.js — identidade, BASE e api()

O mesmo bloco de oito linhas que responde "quem sou eu?" está copiado, letra por letra, em três clientes do browser. Este plano extrai essa regra — junto do wrapper de fetch que também se repete — para um único módulo, client/lib.js, injetado antes de todos os outros.

1Contexto

O que já existe no repo e por que essa duplicação apareceu — e por que ela é mais perigosa do que parece.

Rampa para iniciante (pode pular)

O docs-in-html serve pastas de HTML num servidor de desenvolvimento. Quando o servidor devolve uma página, o módulo inject.js acrescenta, antes de </body>, algumas tags <script>: o cliente de hot-reload (reload.js), o editor inline (edit.js), o destaque de mudanças (changes.js) e, na "shell" (a página com sidebar), o navegador de arquivos (nav.js). Esses scripts rodam dentro da página do usuário e precisam responder a uma pergunta aparentemente boba: que arquivo é este? A resposta depende de onde a página vive — sozinha no servidor, ou sob o gerenciador multi-docs num prefixo tipo /meu-projeto/ — e é exatamente aí que a mesma lógica foi copiada três vezes.

O bloco "quem sou eu", três vezes

Para um cliente saber se deve recarregar a página, salvar o arquivo certo ou comparar com o snapshot correto, ele precisa converter location.pathname no caminho relativo à raiz de docs. Em client/reload.js (linhas 26–30):

var me = (isShell ? "index.html" : decodeURI(location.pathname).replace(/^\/+/, "")) || "index.html";
var baseRel = decodeURI(BASE).replace(/^\/+|\/+$/g, "");
if (baseRel && me.toLowerCase().indexOf(baseRel.toLowerCase() + "/") === 0)
  me = me.slice(baseRel.length + 1) || "index.html";

O mesmo bloco aparece verbatim em client/changes.js (linhas 27–31) e, em forma quase idêntica, em client/edit.js (linhas 12–16). Três cópias da mesma regra sutil — decodeURI, strip da barra inicial, comparação case-insensitive com o prefixo do gerenciador, fallback para index.html.

Detectar a shell: duas técnicas, o mesmo sinal

O sinal de "esta página é a shell" é o elemento #docList. Dois lados o detectam de formas diferentes, porque vivem em mundos diferentes:

  • No cliente (DOM pronto): client/reload.js:23 usa document.getElementById("docList"); client/edit.js:6 faz o mesmo para se abster de editar a shell.
  • No servidor (pré-DOM): inject.js:50 decide quais scripts injetar testando o HTML cru com a regex /<[^>]+\bid\s*=\s*["']docList["']/i — o arquivo nem chegou ao browser ainda.

O wrapper de fetch que também se repete

Quem chama as APIs privadas (/__save__, /__manifest__, endpoints de criação/renomeação) precisa montar a URL: BASE.replace(/\/+$/, "") + url. Acontece em client/nav.js (função api(), linha ~136, e o fetch de /__manifest__, linha ~236) e em client/edit.js (função save(), linha ~99). Cada cópia embute também JSON.stringify do corpo e tratamento de erro — de novo, com pequenas variações.

O custo real dessa duplicação

Uma mudança na regra de slug/base — por exemplo, aceitar caminhos com %20, ou um novo formato de prefixo do gerenciador — exige três edições sincronizadas em três arquivos, e nenhuma delas é testável de forma isolada: a lógica só roda no browser, dentro de uma IIFE, lendo location. É o tipo de código onde o bug aparece só depois que o usuário aperta F5 num endereço profundo.

2Intuição

Três perguntas de identidade, uma resposta só. O que muda é dar a essa resposta um endereço.

A pergunta é uma, os lugares são vários

Pense num exemplo concreto. O gerenciador serve seus docs em /docs-proj/ e você abriu /docs-proj/guias/intro.html num F5 direto (fora da shell). O pathname é /docs-proj/guias/intro.html, mas o que o reload client, o editor e o diff de mudanças precisam saber é apenas guias/intro.html. Cada um dos três chega lá sozinho, com o seu bloco copiado de oito linhas. Se amanhã o prefixo puder ter maiúsculas ou a regra de fallback mudar, são três lugares para errar.

A intuição do plano é a mais antiga da engenharia: quando a mesma pergunta é feita em três lugares, a resposta merece um endereço próprio. Não estamos inventando abstração — estamos dando nome a algo que já existe, duplicado.

me() copiado ×3 → lib.me() · BASE.replace + fetch ×3 → lib.api(path) · getElementById("docList") ×2 → lib.isShell()

Antes e depois: três regras espalhadas convergem para um módulo.

Por que um módulo UMD (e não ESM)

Os clientes atuais são scripts clássicos, carregados por tag <script src> sem módulos. Para que lib.js funcione nesse mundo e dentro do node --test (que usa CommonJS), o formato natural é o guard UMD: dentro do browser ele publica window.docsLib; dentro do Node ele faz module.exports. É o mesmo padrão de adaptador barato que permite testar a regra de prefixo passando um pathname qualquer, sem servidor e sem browser:

me("/docs-proj/guias/intro.html", "/docs-proj/") // → "guias/intro.html"

É aqui que a extração paga sozinha: hoje essa linha é impossível de executar num teste; depois, ela é só uma chamada de função pura.

A simetria que não se pode capturar

Tem uma tentação a evitar. inject.js também detecta a shell — mas opera sobre HTML cru, antes de existir DOM, no servidor (ou no export estático). isShell() usa document.getElementById, que não existe ali. As duas detecções respondem a mesma pergunta em camadas diferentes; uni-las forçaria uma das duas a mudar de mundo (regex no cliente, ou DOM no servidor). A duplicação de um teste de dois usos entre camadas é o preço honesto da arquitetura — e o plano a mantém.

O servidor decide o que injetar via regex; os clientes compartilham lib.js via DOM. Setas tracejadas = tags injetadas.

3Mudanças

Seis arquivos: um novo módulo, quatro consumidores e uma linha a mais no injetor. Nenhuma mudança de comportamento para o usuário.

client/lib.js (novo)

O coração do plano. Uma IIFE com guard UMD que exporta três funções puras o suficiente para rodarem tanto no browser quanto num teste do node --test. A interface cabe num cartão postal:

me(pathname?, base?)   // caminho relativo à raiz de docs
api(path, body?)       // fetch(BASE normalizado + path)
isShell()              // !!document.getElementById("docList")

O corpo de me() é o bloco de oito linhas que hoje vive em três lugares, parametrizado: em vez de ler location.pathname e window.DOCS_BASE direto, recebe-os como argumentos com defaults vindos do browser — é isso que torna a lógica testável. api() centraliza o BASE.replace(/\/+$/, "") + url, o Content-Type JSON e o JSON.stringify do corpo, deixando o tratamento de resposta com cada chamador (o editor quer alert em falha; o nav quer traduzir 409). A normalização de BASE_N também mora aqui.

client/reload.js

As linhas 23 e 26–30 desaparecem em favor de lib.isShell() e lib.me(). O resto — eleição de líder por Web Locks, BroadcastChannel, filtro por root — fica intocado, porque é exatamente onde está a complexidade própria do reload, não a compartilhada. É a definição de uma boa extração: mover o que é comum, não o que é difícil.

client/edit.js

As linhas 6 e 12–16 dão lugar às mesmas duas chamadas; o guard inicial ("não editar a shell") vira if (lib.isShell()) return;. Em save() (linha ~99), o fetch manual com BASE.replace(/\/+$/, "") + "/__save__" vira uma chamada a lib.api("/__save__", { path: lib.me(), html }) — o editor mantém seu próprio .catch com alert, pois a política de erro continua sendo local. Todo o resto (contenteditable, serialize, strip de data-injected) não muda.

client/changes.js

As linhas 27–31 são substituídas por lib.me(). Ponto de atenção que o plano trata explicitamente: a chave de localStorage — "docs-in-html:snap:" + BASE + ":" + me — deve continuar byte a byte igual à atual, ou o usuário "perde" o histórico de mudanças de todos os docs na primeira carga pós-deploy. O plano inclui verificação manual disso.

client/nav.js

O consumidor mais leve. A função api() local (linha ~136) passa a delegar ao wrapper de lib.js, mantendo seu mapeamento de erro 409 → mensagem amigável; o fetch de /__manifest__ (linha ~236) usa o mesmo caminho. O nav não usa me() (a shell sabe quem é), então aqui o ganho é só o leverage do wrapper.

inject.js

Uma mudança de uma linha: a lista de tags ganha lib.js na frente, antes de reload.js e companhia, com data-injected como todo o resto (o editor já sabe estripá-la ao salvar). E o plano é explícito sobre o que não muda: a regex /<[^>]+\bid\s*=\s*["']docList["']/i da linha 50 permanece. Ela não pode usar isShell() porque opera sobre a string HTML crua, no servidor, antes de qualquer DOM existir — e o comentário do próprio arquivo avisa que é detecção por contexto de tag, imune a páginas que apenas mencionam docList em prosa. Forçar as duas camadas a compartilhar seria trocar duplicação controlada por acoplamento errado.

Trade-off honesto: uma tag a mais por página

Cada página servida passa a carregar mais um script (uma requisição HTTP e alguns bytes, sem cache no dev server). Em troca: a regra de identidade vive num lugar, muda num lugar, e ganha testes de node --test com me("/slug/a.html", "/slug/"). Quatro call sites, uma interface — a dívida é paga na primeira mudança de regra de slug.

4Quiz

Cinco questões para checar se a intuição ficou de pé. Clique para responder; pode mudar de ideia quantas vezes quiser.

1. Por que o inject.js não pode simplesmente usar lib.isShell()?

✅ B. A detecção do inject.js acontece no servidor (ou no export), sobre HTML puro; isShell() depende de document. São a mesma pergunta em camadas diferentes — e o plano mantém as duas.

2. Qual o custo concreto do bloco de identidade duplicado verbatim em três arquivos?

✅ C. Três cópias = três lugares para errar; e como a lógica só roda no browser lendo location, nada é testável sem servidor. O custo é de manutenção, não de performance.

3. Para que serve o guard UMD no lib.js?

✅ A. O mesmo arquivo funciona como script clássico (injetado por tag) e como módulo CommonJS dentro do teste — um adaptador barato que destrava a testabilidade.

4. Qual cuidado especial a migração do changes.js exige?

✅ D. A chave "docs-in-html:snap:" + BASE + ":" + me é o contrato persistente com o usuário; qualquer variação (mesmo cosmética) faz os snapshots parecerem novos.

5. Em edit.js, por que o tratamento de erro do save() (o alert) fica no cliente e não dentro de lib.api()?

✅ B. Extração boa move o que é comum (URL, método, headers, corpo), não o que é local. Tratamento de resposta varia por chamador e deve ficar com ele.
