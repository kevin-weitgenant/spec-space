1Contexto

O spec-space é um servidor de documentação em HTML puro: um src/cli/serve.js que publica uma pasta de docs, um manager multi-raiz, um cliente de navegador (edição, navegação, diff) e um exportador estático.

O projeto nasceu com uma decisão de arquitetura que define todo o resto: toda interação com o mundo exterior passa por um único adapter — o módulo src/env/ops.js. Sistema de arquivos, diretório home, spawn, watch, abrir URLs: tudo isso é chamado via ops.*, nunca diretamente via node:fs. Em produção, o adapter padrão delega ao Node real; nos testes, ops.setOps(fake) troca a porta de entrada por uma implementação em memória.

Rampa para iniciante (pode pular)

Um teste de unidade é um pedacinho de código que chama uma função ou módulo sozinho e confere se a saída é a esperada — sem servidor, sem navegador, sem rede. Para isso funcionar, o código precisa de seams ("costuras"): pontos únicos onde um comportamento pode ser trocado sem alterar quem chama — aqui, em vez de o código chamar fs.readFileSync direto, ele chama ops.readFileSync. Nos testes, um fake (uma imitação em memória, ex.: um sistema de arquivos que é só um Map) ocupa esse lugar: o módulo acha que está falando com o disco, mas nenhuma pasta real é tocada.

A segunda decisão: o servidor é um conglomerado de funções puras e contextos por raiz (src/server/roots.js), de modo que guardas de segurança, resolução de caminhos e a tabela de endpoints são testáveis sem subir um servidor HTTP de verdade. A terceira: o código de cliente que precisa ser confiável (diff.js, lib.js) é escrito em UMD — funciona tanto via <script> no navegador quanto via require() no Node — para que a lógica crítica rode em node --test sem navegador algum.

2Estratégia de teste

Zero dependências, executor nativo e mentiras controladas no lugar de infraestrutura real.

  • node:test + node:assert — o executor embutido do Node. Nenhum framework, nenhuma instalação, nenhum lockfile inchado. Rodar a suíte inteira leva < 1 s.
  • Adapter falso via setOps() — um fs em memória (um Map), um watch emissor de eventos controlado, um spawn que apenas grava chamadas. O home real do usuário nunca é lito.
  • Funções puras — safeRelPath, resolveIn, parseArgs, diffOps, me() são testadas por chamada direta: entrada → saída, sem mocks.
  • listen falso — nos testes de porta, http.createServer é substituído por um servidor de mentira cujo listen(port, cb) falha sob demanda (EADDRINUSE, EACCES) e registra todas as portas tentadas.
  • Diretórios temporários — fs.mkdtempSync(os.tmpdir()) cria pastas de verdade quando o teste precisa de disco real (deleção, export), com t.after limpando tudo.
  • Resposta/req de mentira — objetos { writeHead, end } e Readables cumprem o contrato HTTP mínimo que src/server/roots.js exige.
teste→ setOps(fake) / parseArgs(args)→ módulo sob teste→ assert no resultado

4As suítes em detalhe

Suíte por suíte: por que cada uma existe e o que exatamente ela trava.

ops.test.js — a costura do ambiente (5 testes)

Por que esta suíte existe
Se a troca de adapter (setOps) não funcionar, nenhum outro teste consegue mentir sobre o mundo — esta é a suíte que valida a fundação de todas as demais.

src/env/ops.js é a única porta para o mundo exterior; se ela quebrar, todos os módulos que dependem dela ficam cegos. A suíte verifica que setOps/resetOps realmente trocam e restauram o adapter, que o registry funciona por inteiro (add/list/save, add duplicado é no-op, registry.json vai para o home falso), e que o reload colapsa dois eventos do mesmo arquivo em um único broadcast — debounce de 150 ms que existe porque o Windows dispara vários eventos por salvamento. Um último teste grava lançamentos de openPath/openUrl/spawn sem executar nada, e um teste de sanidade confere que o adapter padrão lê um arquivo real como o node:fs.

roots.test.js — as guardas de segurança (6 testes)

Por que esta suíte existe
Um servidor que escreve arquivos a pedido do navegador precisa provar que nenhum caminho malicioso escapa da raiz de docs.

Este é o coração defensivo do pacote. O servidor aceita nomes de arquivos vindos do navegador (endpoints /__delete__, /__save__, /__rename__…), então um caminho malicioso como ../../etc/passwd precisa morrer antes de qualquer operação de filesystem. Os testes cobrem:

  • safeRelPath: aceita caminhos aninhados normais (incluindo espaços); rejeita traversal (../), caminhos absolutos, barra invertida (a\b), segmentos ., prefixos ./_, caracteres proibidos (< > : " | ? *, controles) e não-strings.
  • resolveIn: devolve { rel, abs } apenas quando o caminho absoluto resolvido permanece dentro da raiz (defesa em profundidade — nem confia só no parser).
  • ENDPOINTS: cada caminho /__*__ tem método HTTP e função nomeada — a tabela contratal do servidor.
  • endpoint de deleção: um POST com ../../etc/passwd recebe 400 e o filesystem nunca é consultado — o teste usa req/res de mentira para provar que a guarda vem primeiro.
  • readJsonBody: JSON válido passa; lixo devolve null (e corpos acima do limite de bytes são destruídos, no código).
Por que isso importa
Um endpoint de arquivos sem guarda de traversal é uma vulnerabilidade de leitura/escrita arbitrária. Estes seis testes são a prova de regressão mais valiosa do pacote: qualquer refatoração que amoleça safeRelPath ou resolveIn falha imediatamente.

diff.test.js — o núcleo de diff puro (11 testes)

Por que esta suíte existe
O diff é a matemática mais delicada do pacote; testá-la em Node puro garante correção sem depender de como a UI desenha o resultado.

client/diff.js calcula o diff entre a versão salva e a editada de um documento, exibindo blocos novos, editados e removidos na UI. A suíte testa a matemática, não a UI:

  • Ops mínimas: listas idênticas → []; inserção pura → um único { t: "+", b: 2 } (prefixo/sufixo comuns são aparados).
  • Orçamento: matrizes de 2100×2100 sem trecho comum devolvem null — o diff desiste graciosamente em vez de travar a aba com 4 milhões de células de programação dinâmica.
  • Unicode: “configuração rápida” → “configuração lenta” produz ops − e + corretas (sem quebra por surrogate pairs ou normalização).
  • marks: bloco novo vira kind: "new"; um par remover+adicionar com texto similar vira um único edit carregando o texto antigo; um bloco que apenas se moveu (mesmos textos, ordem nova) não é marcado — falso positivo de edição seria o bug mais visível ao usuário.
  • wordDiff: “npm” → “pnpm” gera exatamente [-npm, +pnpm]; strings idênticas viram só tokens de contexto.
  • similarity: 1 para iguais, 0 para disjuntas — a régua que decide quando um par −/+ merece virar “edit”.

lib.test.js — a identidade da página (9 testes)

Por que esta suíte existe
Se me() errar o caminho do documento, o salvamento e o diff gravam no arquivo errado — por isso o contrato é fixado caso a caso.

client/lib.js responde “quem sou eu?” para cada página: me(pathname, base) converte a URL do documento em um caminho relativo à raiz de docs. Essa regra era copiada em três scripts diferentes antes de virar um módulo — e cada cópia podia divergir. Os testes fixam o contrato: prefixo do manager é removido de forma case-insensitive e com ou sem barra final; / vira index.html; um prefixo que apenas começa parecido (/docs-projeto/x com base /docs-proj) não é removido; caminhos percent-codificados (pasta%20com%20espa%C3%A7o) são decodificados; e isShell() sem document devolve false em vez de explodir — o que é exatamente o que permite que este arquivo seja testado no Node. Estabilidade da chave de snapshot: se me() mudar, o cache de diff e os endpoints gravam no arquivo errado; daí a cobertura exaustiva de casos-limite.

UMD: um arquivo, dois mundos
lib.js e diff.js são UMD: via <script> publicam window.docsLib etc.; via require() exportam module.exports. É essa duplicidade deliberada que torna os testes acima possível sem puppeteer, playwright ou um único npm install.

serve-args.test.js — a matriz de CLI (8 testes)

Por que esta suíte existe
A CLI é a primeira coisa que o usuário toca; uma matriz de argumentos garante que defaults, portas e flags não regridam.

parseArgs(argv, opts) recebe o argv como argumento (nunca lê process.argv direto), o que o torna uma função pura testável em matriz. Defaults (serve, ., porta 8000, abrir browser); defaultPort substituível; -p/--port marca a porta como explícita; --port abc (NaN) mantém o default mas ainda conta como explícita; subcomandos init/export --out site/manager; -h/--help viram mode: "help" — uma decisão de retorno, não um efeito colateral de process.exit; flags --no-open, --no-register, --unregister e o re-armar com -o.

serve-port.test.js — a semântica de fallback de porta (4 testes)

Por que esta suíte existe
"Tentar a próxima porta" versus "morrer com mensagem clara" é a diferença entre um usuário feliz e um script quebrado — e depende de um único flag.

Aqui mora o comportamento que os usuários realmente sentem. Com um listen falso que registra cada tentativa:

  • Sem --port, dois EADDRINUSE seguidos → o servidor avança 9001 → 9002 → 9003 e segue vivo. Fallback automático é o comportamento amigável.
  • Com --port explícito, um único EADDRINUSE → código de saída 1 e a mensagem “já está em uso”. A porta explícita é um pedido, não uma sugestão: tentar outra seria desobedecer o usuário (e quebrar scripts que assumem a porta).
  • Manager vivo (pingManagerDep devolve 4478): nenhum servidor é criado; o site apenas se registra no manager (addToManagerDep), que passa a servi-lo.
  • EACCES na porta 80: código 1 com a dica de porta privilegiada — diagnóstico educado em vez de stack trace.
O parâmetro escondido: portWasExplicit
A distinção inteira entre “tentar a próxima” e “morrer com mensagem clara” depende do flag portWasExplicit produzido por parseArgs. É por isso que a suíte de args e a de porta são, na prática, uma história só contada em dois arquivos.

export.test.js — o export estático de verdade (2 testes)

Por que esta suíte existe
O export é o único caminho que escreve em disco de verdade nos testes — para garantir que o site gerado é estático, completo e não mexe no original.

O caminho triste primeiro: pasta inexistente lança (/pasta não encontrada/) em vez de chamar process.exit — o que antes matava o próprio test runner. O caminho feliz monta uma mini-site em um temp dir (index, guia, _config.json) e roda run(src, out) de verdade, conferindo no disco: manifest.json existe; __docs__/lib.js foi copiado; _config.json não é embarcado; o shell ganha as tags /__docs__/lib.js, /__docs__/nav.js e window.DOCS_EXPORT mas nenhum reload.js (sites estáticos não têm watcher); os docs recebem data-injected; e a pasta fonte permanece intocada — o export nunca reescreve o original.

5Como rodar

Sem setup: nenhum npm install, nenhum runner externo.

npm test          # atalho para node --test tests/
node --test       # idem, a partir da raiz do repo

Saída esperada: 1..45, # tests 45, # pass 45, # fail 0 — em menos de meio segundo (a única espera real é o debounce de 150 ms do teste de reload, cerca de 250 ms no total). Para um único arquivo: node --test tests/roots.test.js.

6O que não é testado — e por quê

As lacunas são deliberadas: cada linha abaixo explica o trade-off de zero dependências.

ÁreaCoberta?Motivo
Cliente DOM no navegador (nav.js, edits, eventos, renderização)NãoRequereria browser headless (uma dependência pesada) para validar coisas que o próprio usuário vê ao abrir a página; o custo de manutenção supera o ganho em um pacote de zero dependências.
Integração HTTP de ponta a ponta (fetch real ao servidor)ParcialOs endpoints são exercitados via req/res falsos (unidade de handler), não via sockets reais — o contrato testado é o que pode quebrar silenciosamente.
Comportamento real do fs.watch por SONãoNão-determinístico por natureza (o Windows dispara múltiplos eventos); o teste usa um watcher falso e valida o debounce, que é a parte sob nosso controle.
Renderização visual do diff (cores, ícones)NãoÉ cosmética; a correção semântica (quais blocos mudaram) está 100% nos testes de diffOps/marks.
O trade-off declarado
O pacote escolhe profundidade em lógica (guardas, diff, parsing, fallback de porta) em vez de amplitude em integração. Quando um bug de navegador aparecer, o manual de reprodução é: abrir a página. A regressão que dói é a lógica que ninguém olha — e essa está coberta.

7Quiz

Cinco perguntas sobre o que a suíte realmente protege. Clique para responder; pode trocar de resposta à vontade.

1. Um POST para /__delete__ com {"path": "../../etc/passwd"} chega ao handler. O que o teste de roots.js espera?

✅ B. A guarda (safeRelPath/resolveIn) rejeita o traversal antes de qualquer ops.stat ou deleção — é exatamente isso que o teste prova com req/res de mentira.

2. O usuário sobe o servidor com --port 9005 e a porta está ocupada. Qual comportamento os testes exigem?

✅ C. Porta explícita é um pedido: o fallback automático existe só quando a porta foi escolhida por default. Os dois primeiros testes de serve-port.test.js fixam exatamente essa assimetria.

3. Por que lib.test.js consegue testar um módulo de navegador sem navegador?

✅ A. O build UMD exporta module.exports no Node, e me(pathname, base) recebe os valores que no navegador viriam de location/window.DOCS_BASE como argumentos. isShell() sem document devolve false — testado explicitamente.

4. Em diff.test.js, os blocos ["A","B","C"] → ["C","A","B"] produzem quais marks?

✅ B. Textos iguais em ordem nova = movimento, não edição. Marcar isso seria um falso positivo gritante na UI de revisão; o teste trava o comportamento com deepStrictEqual(m, []).

5. O que a suíte de ops.test.js prova sobre o teste de reload (o watcher falso emitindo “index.html” duas vezes)?

✅ C. O Windows dispara vários eventos por save; o debounce por arquivo é a defesa. O watcher falso emite “index.html” duas vezes e “guide/a.html” uma — o teste exige exatamente dois broadcasts.
