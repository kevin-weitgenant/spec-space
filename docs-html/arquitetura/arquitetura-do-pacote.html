1Visão geral

O pacote spec-space  é um servidor de desenvolvimento zero-build para pastas de documentação em HTML puro: sidebar em árvore automática, live reload, edição WYSIWYG inline, highlights do que mudou desde sua última visita, pan/zoom para Mermaid e SVGs — e um manager que serve todas as suas pastas num único processo.

📋 Dois documentos, duas perguntas
Este responde "como funciona por dentro". Para "o que o pacote oferece" (a lista completa de features pela jornada de uso), veja ✨ Features.

A arquitetura se organiza em cinco módulos profundos — cada um com uma responsabilidade única e uma interface pequena:

2A costura ops — uma porta para o mundo

ops.js é a ÚNICA porta pela qual o projeto fala com o mundo exterior: sistema de arquivos, processos, home dir.

Em produção, o adaptador default envolve node:fs, node:child_process e node:os diretamente. Em teste, ops.setOps(fakeOps) troca o adaptador inteiro por uma versão em memória — sem disco real, sem processo real, sem home real. ops.resetOps() devolve o mundo verdadeiro.

💡 O módulo é um Proxy
O module.exports é um Proxy que delega sempre ao adaptador corrente. Isso significa que setOps() vale globalmente, até para módulos que capturaram ops no require — o proxy sempre encaminha para current. Os nomes/assinaturas dos métodos de fs espelham o node:fs: migrar um call site é um rename, não um rewrite.

O que a costura expõe, além do fs:

  • homeDir() — o home do usuário (registry e scan);
  • spawn(bin, args) — processo em background detached, fire-and-forget;
  • execFile — para resolução do binário do Warp;
  • openPath(abs) — reveal no gerenciador de arquivos (Explorer /select, Finder -R, Linux abre o pai), escrito uma vez só;
  • openUrl(url) — abrir o browser default (start/open/xdg-open conforme o SO).

Quem consome: roots.js (endpoints, estáticos, shell), reload.js (ops.watch), serve.js (openUrl), manager e registry. É por aqui que os testes simulam EADDRINUSE, um manager no ar ou um disco inteiro sem tocar em nenhum deles.

3CLI requireable — serve.js

O arquivo é ao mesmo tempo programa (binário) e módulo: parseArgs() e main() são exportadas e testáveis in-process.

  • Puro no parse. parseArgs(argv, opts) recebe um ARRAY de argumentos (não process.argv) e devolve opções como dados; -h vira mode:"help" — imprimir é trabalho do main().
  • Deps injetáveis. main(args, deps) recebe pingManagerDep, addToManagerDep e openUrl por injeção — os testes simulam um manager vivo ou o browser abrindo sem que nada disso exista. Nunca chama process.exit: devolve o exit code, e o footer decide.
  • Footer require.main. Todo efeito colateral que antes rodava no require-time (parse do argv, exit, server) mora atrás de if (require.main === module). Requerer o módulo é silencioso.
  • Servidor vivo resolve undefined. Quando o serve sobe de verdade, main resolve undefined — o footer não faz exit; o próprio server mantém o processo vivo (mesmo contrato do script pré-refactor).

Portas honestas: dica vs. exigência

Sem --port, a padrão (8000 ou $PORT) é uma dica: ocupada, cai para a próxima livre com um aviso, até MAX_FALLBACKS = 20 tentativas. Com --port explícito é uma exigência: ocupada, morre com erro claro em vez de trocar em silêncio (inclusive com a dica "pode ser outra instância de spec-space").

Os outros comportamentos do modo serve

  • Delegação: pinga o manager primeiro; se está no ar (e sem --no-register), registra a pasta via POST /api/add, imprime o link e nem abre servidor — com aviso se --port foi ignorado.
  • Auto-scaffold: primeiro serve de uma pasta sem _config.json cria um com defaults amigáveis (título derivado do nome da pasta).
  • Higiene: registry.add silencioso; server.on("close") fecha o watcher do root.
🧭 Subcomandos
init, export e manager são apenas requires + retorno: manager mantém o processo vivo (server próprio), os outros dois devolvem exit code 0/1 para o footer. --unregister remove do registry e sai.

4Contexto por pasta — roots.js e cia.

createRoot(root, opts) devolve { root, base, handle, reload }: o handler tem a mesma assinatura de um listener do http.Server. opts.base é o prefixo de URL ("" no single-root, "/<slug>" no manager). Dois consumidores, um handler — a correção se escreve uma vez.

Handlers nomeados + tabela ENDPOINTS

Cada endpoint /__*__ é uma função nomeada de escopo de módulo com a mesma forma (ctx, req, res) — onde ctx carrega o root dir e o bookkeeping de config por root (shiftIcons/pruneIcons/readAnim). O handle despacha pela tabela declarativa ENDPOINTS — toda a superfície /__*__ num relance:

RotaMétodoHandlerO que faz
/__manifest__GETendpointManifestJSON com tree + título + animação + root/sep/platform.
/__delete__POSTendpointDeleteApaga doc (.html apenas) ou pasta vazia (409 se não). Sincroniza config.icons.
/__rename__POSTendpointRenameRenomeia/move doc ou pasta; recusa mover pasta pra dentro de si; reescreve chaves de icons.
/__mkdir__POSTendpointMkdirCria pasta (409 se já existe).
/__save__POSTendpointSaveGrava o HTML inteiro de volta (editor inline; até 10 MB).
/__reveal__POSTendpointRevealAbre o gerenciador de arquivos — uma linha, ops.openPath().
/__order__POSTendpointOrderPersiste a ordem manual por pasta no _config.json.
/__title__POSTendpointTitlePersiste o título (trim, cap de 200 chars) no _config.json.

Além da tabela, o módulo exporta as peças testáveis: readJsonBody (JSON com cap de tamanho — default 4 KB, sobrecarregado destrói a conexão), safeRelPath ("guides/v2" → válido | null: sem .., sem \, sem nomes esquisitos), resolveIn (resolve dentro do root ou null), ENDPOINTS, MIME e send — unit-testáveis sem subir servidor.

As decisões que atravessam o módulo

  • O contrato #docList — o shell é reconhecido por estrutura (uma tag real com id="docList"), não por URL. A detecção usa regex de contexto de tag: uma página que só menciona id="docList" em prosa (como este doc!) não é enganada.
  • Injeção em tempo de resposta — nenhum arquivo em disco é transformado no dev. A lógica de quais scripts entram (inject.js) é compartilhada com o export: uma heurística, dois destinos. Toda tag injetada carrega data-injected — é assim que o editor devolve o arquivo limpo ao disco.
  • Deep links sem recursão — navegação top-level para /pasta/doc.html (com Sec-Fetch-Dest: document, exceto o próprio index.html) devolve o shell em volta; o iframe pede de novo com Sec-Fetch-Dest: iframe e recebe o doc puro. Sem o header (curl, browsers antigos), doc puro também.
  • O servidor nunca confia no cliente — guardas de caminho em todos os endpoints, JSON com cap, HTML sempre no-store (um live reload nunca mostra doc velho), estáticos bloqueados fora da pasta (403), %-escapes malformados → 400.
  • Config é lida a cada pedido — _config.json muda título/favicon/ordem/ícones com hot reload, sem restart. config.js também mora nele o humanize() (Unicode-aware) e o applyShellConfig().
  • manifest.js — buildTree(root): só pastas e .html/.htm, esconde dotfiles/prefixo _/index.html; pastas vazias são mantidas; order fixa a ordem; cada doc carrega mtime (alimenta o "dot verde").
  • reload.js — createReload(root, onEvent?): ops.watch recursivo com debounce por arquivo (150 ms; timers e o próprio watcher são unref()ados — ficam fora do critério "o processo ainda tem trabalho?") e broadcast SSE em /__reload__. onEvent(relPath) é o gancho do hub do manager. Sem fs.watch, degrada graciosamente.

5Ecossistema multi-docs

Servir pastas uma a uma para de escalar no segundo projeto: o manager serve todas as suas docs num processo só, cada uma em http://localhost:4400/<slug>/.

  • Um handler, N instâncias — o manager não reimplementa nada: cria um contexto roots.js por pasta e roteia por prefixo de slug (reescreve req.url e chama ctx.handle). Roots são sincronizados com o registry a quente.
  • Slug do título — /my-project-handbook/ do title; colisões ganham -2; api é reservado.
  • SSE multiplexado — todos os roots faneeam eventos num hub único: uma conexão SSE por browser, não uma por root. A mensagem carrega { base, path }.
  • API — /api/ping, /api/docs, /api/add, /api/remove, /api/layout (atômico e sempre saneado — saneLayout poda órfãos, grupos vazios, e acrescenta docs novas no fim), /api/reveal, /api/open-warp, /api/scan. POSTs exigem Content-Type: application/json — um form cross-origin não consegue setar isso, bloqueando chamadas drive-by. Reveal/Warp só agem sobre pastas registradas.
  • Warp — resolveWarp(): $WARP_BIN → locais padrão por SO → PATH, com cache por processo; no Windows o caminho vira URL file:// (o Warp parseia argumento posicional como URI).
  • registry.js — ~/.docs-in-html/registry.json: arquivo corrompido é backupeado e resetado, layout do mural revalidado contra os docs reais. O manager persiste a própria porta ao subir (a delegação funciona mesmo sem a env var).
  • delegation.js — pingManager() nas portas candidatas (env > registry > 4400) com timeout curto; addToManager() devolve o slug escolhido. scan.js importa em lote: acha pastas com _config.json que "pareça nosso" sob o home, com skip-list e profundidade máxima.

6Publicação estática — export.js

O que o servidor decide por requisição, o export decide UMA vez e escreve em disco: arquivos puros, zero servidor, sidebar e pan/zoom funcionando (surge dist).

run(root, outDir) também é requireable, com footer require.main: pasta inexistente lança ("pasta não encontrada") e o footer imprime + exit 1. Cinco passos:

  1. Copia a pasta pro output — pulando SKIP_FILES (_config.json e os legados _order.json/_icons.json: config não embarca, vai assada) e evitando copiar o output pra dentro de si mesmo;
  2. manifest.json — buildTree(src) na raiz do output (ordem + ícones já aplicados, título pro tab title);
  3. client/ → __docs__/ — mesmo caminho que as tags injetadas referenciam;
  4. Shell garantido — index.html embutido (se a pasta não tem) com title/favicon aplicados, reescrito também se existe;
  5. Reinjeção — cada .html reescrito com injectScripts(html, { staticMode: true }).
🔗 Deep link no estático
No modo estático, inject.js adiciona ao <head> de todo doc (antes de qualquer render) o bootstrap de deep link: doc aberto direto na janela top pula para /?p=<path> (âncora preservada), e o shell pega o parâmetro e abre o doc no iframe. Também define window.DOCS_EXPORT = true — o nav.js entra em modo read-only (lê /manifest.json) e edit/changes nem são injetados.

7Clientes do browser

Scripts injetados nas páginas, servidos de /__docs__/*. Três princípios atravessam todos: identidade por estrutura (não por URL), comunicação via eventos DOM (docs-in-html:change) e UI própria marcada data-injected.

A ordem de injeção (inject.js)

  1. lib.js sempre primeiro — em toda página, dev e export: o módulo de identidade que os demais consomem (window.docsLib).
  2. Dev only: um <script> define DOCS_BASE no manager (prefixo /slug/) e reload.js entra em toda página; no export, define DOCS_EXPORT e nada de reload.
  3. Shell (tag real com id="docList"): nav.js. Doc não-shell (dev): edit.js + diff.js + changes.js, todos defer — diff.js imediatamente antes de changes.js, para a ordem de execução valer (o changes consome window.DIFF).
  4. mermaid-zoom.js (defer) pela heurística: blocos .mermaid, <figure> ou .panzoom/.diagram/.zoomable — e sem pan/zoom próprio (mesmo cuidado anti-prosa da detecção de shell).
client/lib.js — o módulo de identidade UMD

A interface cabe num cartão-postal: me(pathname?, base?) → caminho relativo ao root da docs ("guias/a.html"; tira a barra inicial, tira o prefixo do manager case-insensitivamente, cai em index.html); api(path, body?) → fetch POST com BASE_N + path e corpo JSON (o tratamento da resposta fica com cada chamador); isShell() → !!document.getElementById("docList"); BASE/BASE_N → window.DOCS_BASE cru e sem barra final. Esse bloco "quem sou eu?" era copiado em reload.js, changes.js e edit.js; o wrapper de fetch vivia em nav.js e edit.js — agora mora aqui, uma vez só. UMD: tag <script> publica window.docsLib; require() ganha module.exports — a regra do prefixo é testável com node --test, sem browser.

client/diff.js — o núcleo puro de diff UMD

Extraído de changes.js para ser testável com node:test (sem DOM, sem window, sem localStorage). Os algoritmos foram copiados ipsis litteris, com duas diferenças conscientes: o guard UMD no rodapé (mesmo arquivo serve <script>, anexando window.DIFF, e require()) e marks() recebendo a lista de textos novos como parâmetro, fechando sua única impureza. Dentro: diffOps(a, b) — LCS com trim de prefixo/sufixo comuns (docs grandes demais, > 4M células, degradam sem marcação), e wordDiff — diff por tokens para o word-diff dentro de um bloco editado.

client/nav.js — a sidebar viva

Busca /__manifest__ (ou /manifest.json no export) e renderiza a árvore: pastas colapsáveis com memória em localStorage, ícones Lucide embutidos + emoji, animação configurável, ordem manual por drag & drop, doc ativo + ancestrais expandidos, URL com pushState/popstate, tab title "Doc · Site", esconder sidebar. Assinatura da árvore: a cada mudança re-busca o manifest, mas só reconstrói o DOM se o conjunto de arquivos mudou. Gerenciamento: menu kebab "⋯" por item (copy path, copy full path, reveal, move-to, delete com confirmação em dois cliques), menu de contexto da sidebar (new folder, collapse all), rename inline, drag & drop — tudo pelos endpoints POST /__*. No export: read-only + deep link /?p=.

client/reload.js — quando recarregar (e uma conexão só)

HTTP/1.1 permite ~6 conexões por origem — um SSE por tab travaria a 7ª. As tabs elegem um líder via Web Locks que mantém a única conexão SSE (origin-root: multiplexada sob o manager) e re-transmite todos os eventos crus por um BroadcastChannel; cada receptor filtra pelo seu root (base) e decide com shouldReload(): meu arquivo mudou → recarrega; sou o shell → só eu mesmo (preserva a sidebar); .js/.css compartilhado → o doc em exibição recarrega. A tab líder fecha? O lock passa adiante. Usa window.docsLib para saber quem é.

client/edit.js · changes.js · mermaid-zoom.js · manager.html

edit.js — botão "✏ Editar" (Ctrl+E) liga contenteditable; Ctrl+S grava via /__save__ (clone do body com tudo que é data-injected removido; pre/code como texto puro; estado dirty no botão; beforeunload com mudanças pendentes).

changes.js — achata os blocos do doc, diff LCS contra o snapshot do localStorage da última visita, marca diferenças (chip "novo"; word-diff com o velho riscado), sobrescreve o snapshot. Minimap estilo VS Code, favicon com ponto azul + prefixo "● " no título (sinais no window.top), pílula "N mudanças · ↓ próxima · ✓ já vi tudo". Consome window.DIFF.

mermaid-zoom.js — lightbox pan/zoom com event delegation + pseudo-elemento CSS (sobrevive aos rewrites do Mermaid) e lista INTERACTIVE (nunca sequestra SVG em button, a, [onclick], label, summary). Carrega svg-pan-zoom do CDN sob demanda.

manager.html — o mural de cards: título + favicon por docs, pastas/grupos com drag & drop persistido via POST /api/layout, ações Warp/reveal/remover, botão Escanear.

8Fluxos

1. Startup: CLI → servidor ou manager

2. Live reload: do save à página atualizada

🔑 Uma conexão por browser
Só a tab líder segura o SSE (Web Locks); a liderança migra sozinha quando ela fecha. Sob o manager o hub multiplexa todos os roots nessa única conexão — com 10 tabs e 5 docs há 1 conexão, não 50.
