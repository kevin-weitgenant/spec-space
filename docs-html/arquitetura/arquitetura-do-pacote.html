📦 docs-in-html — Arquitetura do Pacote

docs-in-html é um servidor de desenvolvimento zero-build para pastas de documentação em HTML puro. Ele gera automaticamente uma barra lateral (sidebar) em árvore a partir das suas pastas, oferece live reload, edição WYSIWYG inline, highlights do que mudou desde sua última visita, pan/zoom para diagramas Mermaid e SVGs — e ainda um manager que serve todas as suas pastas de docs num único processo. A filosofia: HTML em vez de Markdown — sem etapa de build.

💡 Você está lendo este documento dentro do próprio docs-in-html — os diagramas abaixo podem ser clicados para pan/zoom, e qualquer edição no arquivo dispara o live reload. Meta-documentação! 😄
📋 Este documento responde "como funciona por dentro". Para "o que o pacote oferece" (a lista completa de features pela jornada de uso), veja ✨ Features.

Os módulos profundos

Cada seção abaixo explica o módulo — o design, as decisões, a interface. No fim de cada uma, expanda os arquivos para o detalhe fino, um por um.

🚀 CLI & ciclo de vida serve.js

O ponto de entrada (definido em bin no package.json). É um despachante, não um servidor: quase todo o trabalho pesado mora nos outros módulos. Suas quatro decisões de design:

  • Servir = registrar = delegar. Antes de subir servidor próprio, ele pinga o manager (delegation.js). Se este está no ar, a pasta é registrada lá via POST /api/add e o CLI nem abre servidor — só imprime o link. O manager é o serve dessa pasta agora.
  • Auto-scaffold. Primeiro serve de uma pasta sem _config.json cria um com defaults amigáveis (título derivado do nome da pasta).
  • Portas honestas. Sem --port: a padrão (8000 ou $PORT) ocupada → tenta a próxima livre com um aviso (até 20 tentativas). Com --port explícito é uma exigência: ocupada, morre com erro claro em vez de trocar em silêncio.
  • Subcomandos. init, export e manager são apenas requires + process.exit — cada um com seu próprio módulo.
serve.js CLI

Parse manual de argv: docs-in-html [dir] [--port N] [--no-open] [--no-register] [--unregister] + subcomandos. Abre o navegador com start/open/xdg-open conforme o SO. No modo serve: pinga o manager → auto-scaffold → registry.add silencioso → createRoot(ROOT, { base: "" }) instalado como handler do http.Server → lógica de portas com fallback. No fim, o server fecha o watcher do root no evento close.

🧩 Contexto por pasta roots.js · inject.js · config.js · manifest.js · reload.js · shell.js · init.js

O módulo mais profundo do pacote. createRoot(root, opts) devolve { root, base, handle, reload }, onde handle(req, res) tem a mesma assinatura de um listener do http.Server. opts.base é o prefixo de URL ("" no single-root, "/<slug>" no manager) — usado no <base> do shell e no DOCS_BASE injetado nos clientes. Dois consumidores, um handler: correção se escreve uma vez.

As decisões que atravessam todos os arquivos deste módulo:

  • O contrato #docList — o shell é reconhecido por estrutura (uma tag real com id="docList"), não por URL. Shells customizados e deep links funcionam de graça. A detecção usa regex de contexto de tag: uma página que só menciona id="docList" em prosa (como este doc!) não é enganada.
  • Injeção em tempo de resposta — nenhum arquivo em disco é transformado no dev. A lógica de quais scripts entram (inject.js) é compartilhada com o export: uma heurística, dois destinos. Toda tag injetada carrega data-injected — é assim que o editor devolve o arquivo limpo ao disco.
  • Deep links sem recursão — navegação top-level para /pasta/doc.html devolve o shell em volta; o iframe dentro dele pede de novo com Sec-Fetch-Dest: iframe e recebe o doc puro.
  • O servidor nunca confia no cliente — guardas de caminho em todos os endpoints (nada sai da pasta, sem .., sem nomes esquisitos), JSON com cap de tamanho, HTML sempre no-store (um live reload nunca mostra doc velho).
  • Config é lida a cada pedido — _config.json muda título/favicon/ordem/ícones com hot reload, sem restart.

roots.js servidor — o coração

O contexto por pasta: shell (index.html do usuário ou embutido, com title/favicon aplicados e <base> garantido), tabela de rotas acima, guardas de caminho (safeRelPath/resolveIn), arquivos estáticos com tabela MIME e bloqueio de path traversal (403 fora da pasta), deep links via Sec-Fetch-Dest, e a manutenção de config.icons quando arquivos são renomeados/apagados da sidebar (shiftIcons/pruneIcons).

inject.js dev + export

injectScripts(html, { staticMode, base }) — a lógica de quais scripts entram, usada pelo dev server (na resposta) e pelo export (em disco):

  • reload.js em toda página (dev only — nada a recarregar num site estático).
  • nav.js só no shell (tag real com id="docList").
  • edit.js + changes.js em todo doc que não é shell (dev only — dependem de /__save__ e do SSE).
  • mermaid-zoom.js quando há blocos .mermaid, <figure> ou .panzoom/.diagram/.zoomable — e a página não traz pan/zoom próprio (mesmo cuidado anti-prosa da detecção de shell).
  • No manager, um <script> define window.DOCS_BASE = "/<slug>/"; no export, define window.DOCS_EXPORT (modo read-only) e injeta no <head> o bootstrap de deep link: doc aberto direto no host estático pula para /?p=<path> e o shell o abre no iframe.
config.js servidor

O arquivo único de configuração de uma pasta: title, favicon (emoji vira data-URI SVG), sidebarAnim (reveal | slide | guide), icons (antigo _icons.json) e order (antigo _order.json). A leitura mescla os legados como fallback; a primeira escrita os absorve — sem comando de migração. Também mora aqui o humanize() (auth-service.html → "Auth Service", Unicode-aware: Integração fica Integração) e o applyShellConfig() (aplica título/favicon ao shell — o título só substitui o <title>Docs default; um index.html customizado mantém o que seu autor escolheu).

manifest.js servidor

buildTree(root) percorre a pasta recursivamente: só pastas e .html/.htm; esconde dotfiles, prefixo _ e o próprio index.html (que é o shell); pastas vazias são mantidas (a sidebar pode criar/revelar docs nelas); entradas de config.order fixam a ordem (pinneados primeiro na ordem salva; o resto alfabético, pastas antes de arquivos); cada doc carrega mtime — alimenta o "dot verde" de doc alterado na sidebar.

reload.js servidor

createReload(root, onEvent?) devolve { handle, close }: fs.watch recursivo com debounce por arquivo (150 ms) — o Windows dispara vários eventos para um único save, e o timer por caminho os colapsa num só broadcast SSE (data: {"path": "..."} em /__reload__). onEvent(relPath) existe para o manager: cada root faneia seus eventos para o hub multiplexado dele. Sem fs.watch, degrada graciosamente (avisa e segue estático).

shell.js + init.js servidor CLI

shell.js é o layout embutido (cabeçalho com <span id="dl-title"> editável, <aside> com <ul id="docList"> e um <iframe>) — o contrato estrutural que identifica "esta página é um shell". init [dir] escreve esse shell como index.html inicial (recusa sobrescrever) e cria o _config.json.

🛰️ Ecossistema multi-docs manager.js · registry.js · delegation.js · scan.js

Servir pastas uma a uma para de escalar no segundo projeto. Este módulo serve todas as suas docs num processo só, cada uma em http://localhost:4400/<slug>/:

  • Um handler, N instâncias — o manager não reimplementa nada do servidor: cria um contexto roots.js por pasta e roteia por prefixo de slug (reescreve req.url e chama ctx.handle). Roots são sincronizados com o registry a quente; slug que muda ganha contexto novo (o prefixo está "assado" no shell/reload).
  • Slug do título — o URL vem do title do _config.json ("My Project — Handbook" → /my-project-handbook/); colisões ganham -2; api é reservado.
  • SSE multiplexado — todos os roots faneiam eventos num hub único: uma conexão SSE por browser, não uma por root (HTTP/1.1 limita a origem a ~6). A mensagem carrega { base, path } para o cliente filtrar.
  • Registry tolerante — ~/.docs-in-html/registry.json: arquivo corrompido é backupeado e resetado, chaves desconhecidas preservadas, pastas apagadas somem da view. Também guarda o layout do mural (ordem, pastas/grupos, colapso), sempre revalidado contra os docs realmente registrados — o servidor nunca confia cegamente no payload da UI.
  • API defensiva — POSTs do manager exigem Content-Type: application/json: um form cross-origin não consegue setar isso, bloqueando chamadas drive-by de sites aleatórios. Reveal/Warp só agem sobre pastas registradas.
manager.js servidor

Roteamento por prefixo: /api/* (ping, docs, add/remove, layout atômico, reveal, open-warp, scan), /<slug>/* → contexto do root, / → página de cards (client/manager.html). O botão "⌨ Warp" resolve o binário em $WARP_BIN → locais padrão por SO → PATH (com cache por processo; no Windows o caminho vira file:// URL porque o Warp parseia argumento posicional como URI). Persiste a própria porta no registry ao subir — a delegação funciona mesmo sem a env var no shell do CLI. Fecha os watchers de todos os roots no SIGINT/SIGTERM.

registry.js servidor

add/remove/list do registro + slugify() (acentos removidos, colisões -2), slugsFor(dirs) (slug único por pasta, do título do config com fallback pro nome da pasta), cardInfo() (título/favicon por card, lido a cada chamada — hot reload), getLayout()/saveLayout() com o saneamento descrito acima (saneLayout poda caminhos órfãos, grupos vazios, e acrescenta docs novas no fim).

delegation.js cola CLI ⇄ manager

pingManager() dá GET /api/ping nas portas candidatas (env > registry > 4400) com timeout curto — um manager ausente não pode atrasar o serve. addToManager() faz o POST /api/add e devolve o slug que o manager escolheu (o CLI imprime exatamente o URL certo).

scan.js CLI

Varredura única sob $HOME (+pastas extras) procurando pastas com _config.json que "pareça nosso" (parseia e tem ao menos uma chave conhecida — filtra arquivos homônimos de outras ferramentas). Skip-list (node_modules, AppData…) e profundidade máxima 6; não desce dentro de uma docs já encontrada. É ferramenta de import: depois disso, o registry é a fonte da verdade. Um cache lembra o último conjunto encontrado para a UI destacar o que é novo.

📤 Publicação estática export.js

docs-in-html export [dir] [--out] decide uma vez o que o servidor decide por requisição e escreve em disco — resultado: arquivos puros, zero servidor, sidebar e pan/zoom funcionando (leia-se surge dist). O que o dist/ contém: seus HTMLs com as tags de script já escritas, um manifest.json (árvore + ordem + ícones + título) e __docs__/ (os clientes). No site estático a sidebar e o zoom funcionam; o CRUD não (não há endpoints). Deep links funcionam pelo bootstrap do inject.js + o ?p= do nav.js. _config.json não embarca — as configurações vão assadas no output.

export.js CLI

Cinco passos: copia a pasta (menos config; evita copiar o output pra dentro de si mesmo) → gera manifest.json via buildTree → copia client/ para __docs__/ → garante o index.html (shell embutido com title/favicon aplicados, se a pasta não tem) → reescreve cada .html com injectScripts(html, { staticMode: true }). Nunca escreve na pasta fonte.

🌐 Clientes do browser client/nav.js · reload.js · edit.js · changes.js · mermaid-zoom.js · manager.html

Os scripts injetados nas páginas (servidos de /__docs__/*). Três princípios atravessam todos:

  • Identidade por estrutura, não por URL. "Sou o shell?" é document.getElementById("docList"); "qual é o meu arquivo?" é o pathname menos o DOCS_BASE. Depois de um F5 num deep link, o shell vive em /pasta/doc.html e continua sendo reconhecido.
  • Comunicação via eventos DOM. O canal SSE alimenta o reload.js, que re-transmite como CustomEvent("docs-in-html:change") — é assim que o nav.js (que não recarrega) fica sabendo que deve re-buscar o manifest.
  • UI própria carrega data-injected — nada do que o dev server adiciona à página parar no disco quando o editor salva.
client/nav.js cliente — a sidebar viva
  • Busca /__manifest__ (ou /manifest.json no export) e renderiza a árvore: pastas colapsáveis com memória em localStorage, ícones por pasta, animação configurável, ordem manual por drag & drop.
  • Assinatura da árvore: a cada mudança re-busca o manifest, mas só reconstrói o DOM se o conjunto de arquivos mudou — edição de conteúdo não reseta scroll/colapso/ativo.
  • Clique num doc → carrega no <iframe> e sincroniza a URL com pushState (deep links, botão voltar via popstate); load do iframe destaca o ativo e expande os ancestrais.
  • Gerenciamento de arquivos: renomear, mover (drag & drop ou "Move to…"), criar pasta, excluir (dois cliques com confirmação visual) — tudo pelos endpoints POST /__*. Dot verde em docs alteradas (mtime do manifest + evento docs-in-html:change). Garante allowFullscreen no iframe.
  • No export (window.DOCS_EXPORT): modo read-only — a árvore funciona, CRUD não; e o deep link /?p=… abre o doc certo dentro do iframe.
client/reload.js cliente — quando recarregar (e uma conexão só)

O problema: HTTP/1.1 permite ~6 conexões por origem — um SSE por tab travaria a 7ª tab. A solução: as tabs da mesma origem elegem um líder via Web Locks que mantém a única conexão SSE e re-transmite todos os eventos crus por um BroadcastChannel; cada receptor filtra pelo seu root (base). A tab líder fecha? O lock passa para a próxima automaticamente. (No manager, a mensagem SSE já vem multiplexada com {base, path}.)

client/edit.js cliente — edição WYSIWYG inline

Um botão "✏ Editar" (canto superior direito de todo doc; Ctrl+E) liga contenteditable no body: clique no texto, digite, Ctrl+S salva via POST /__save__. Você nunca vê tags. Detalhes finos: pre/code editam como texto puro; todo UI próprio carrega data-injected e é removido antes de gravar; o estado "dirty" aparece no próprio botão.

client/changes.js cliente — o que mudou desde sua última visita

A cada load, o cliente achata os blocos do doc (h1..h4, p, pre, li, blockquote), faz um diff LCS contra o snapshot do localStorage da última visita, marca as diferenças (novo → verde + chip "novo"; editado → word-diff com o velho riscado) e sobrescreve o snapshot. Tudo client-side — funciona mesmo se a mudança aconteceu com nenhuma tab aberta ou com o servidor reiniciado (o baseline é sua última visita, não o estado do servidor). Complementos: minimap estilo VS Code com marcadores clicáveis, favicon da tab com um ponto azul, e o pill "N mudanças · ✓ já vi tudo". Sinais de tab (favicon/título) vão para o window.top, que é same-origin sob serve e manager.

client/mermaid-zoom.js cliente — pan & zoom estilo mkdocs-material

Injetado com defer em páginas com Mermaid, <figure> com SVG, ou classes .panzoom/.diagram/.zoomable (e sem pan/zoom próprio). Clique no diagrama → lightbox com arrastar/scroll, botões +/−/ajustar e tela cheia (funciona dentro do iframe do shell). Carrega svg-pan-zoom do CDN sob demanda.

Duas engenharias espertas: event delegation + pseudo-elemento CSS (o Mermaid reescreve o próprio DOM ao renderizar — listeners em nós internos morreriam) e nunca sequestrar cliques interativos (SVG dentro de button, a, [onclick]… continua fazendo o que devia).

client/manager.html cliente — o mural

Página de cards do manager: um card por docs registrada (título + favicon), organizados num mural com pastas/grupos, drag & drop persistido via POST /api/layout, ações por card (abrir no Warp, reveal, remover) e o botão "Escanear" (/api/scan). HTML+JS puro, zero build — mesmo espírito do shell.

Conceitos-chave para lembrar

  1. Zero build, zero dependências — só node:* builtin. A "mágica" (sidebar, reload, zoom, edição) entra por injeção em tempo de resposta (ou, no export, escrita única em disco), nunca transformando seus arquivos.
  2. Um handler, dois modos — roots.js é o contexto por pasta; single-root e manager são só prefixos diferentes (base). Correção se escreve uma vez.
  3. Servir = registrar = delegar — toda pasta servida entra no registry; se o manager está no ar, o CLI nem sobe servidor, só registra lá.
  4. O contrato #docList — shell é reconhecido por estrutura (tag real), não por URL. Shells customizados e deep links funcionam de graça.
  5. Reload seletivo + uma conexão só — cada página recarrega só o que lhe diz respeito; e por origem existe uma única conexão SSE, mantida por uma tab líder eleita via Web Locks e re-transmitida por BroadcastChannel.
  6. Uma heurística de injeção, dois destinos — dev server e export compartilham inject.js; tag carrega data-injected para o editor devolvê-la limpa ao disco.
  7. Sobreviver ao Mermaid — delegation + pseudo-elemento CSS em vez de listeners inline.
  8. O servidor nunca confia no cliente — guardas de caminho em todos os endpoints, JSON content-type obrigatório nos POSTs do manager, layout saneado antes de gravar.

🧠 Quiz — cheque seu entendimento

Clique numa opção para ver se acertou (e a explicação).

1. Você roda docs-in-html ./docs com o manager já no ar. O que acontece?

Um segundo servidor sobe numa porta livre ao lado do manager. O CLI pinga o manager, registra a pasta lá via /api/add e só imprime o link — nenhum servidor novo. Erro de porta, porque o manager já usa a 4400.

✅ Essa é a delegação (delegation.js): o manager é o serve dessa pasta agora. --no-register desliga o comportamento.

2. O que roots.js representa na arquitetura?

O módulo que gerencia dependências npm do pacote. O contexto de UMA pasta de docs (handler HTTP completo, shell, manifest, CRUD de arquivos, SSE) — instanciado com base vazia pelo serve e com /<slug> pelo manager. Uma fila de requisições do manager.

✅ Single-root e multi-root são o mesmo handler com prefixos diferentes — correção escrita uma vez vale para os dois modos.

3. Você tem 8 tabs abertas do mesmo servidor dev. Quantas conexões SSE existem nessa origem?

Uma — as tabs elegem um líder (Web Locks) que re-transmite os eventos via BroadcastChannel. Oito — cada tab abre seu próprio EventSource. Sete — o limite do browser rejeita a oitava.

✅ Sem isso, a 7ª tab travaria para sempre: HTTP/1.1 limita a origem a ~6 conexões. O lock migra sozinho quando a líder fecha.

4. Por que as tags injetadas carregam data-injected?

Para o browser não cachear os scripts. Para o manager saber de que root veio a página. Para o editor inline (edit.js) identificá-las como UI do dev server e removê-las antes de gravar o arquivo via /__save__.

✅ O que é injetado na resposta nunca deve parar no disco — senão o arquivo do usuário acumularia scripts a cada edição.

5. Como o changes.js sabe o que mudou num doc desde sua última visita, mesmo que nenhuma tab estivesse aberta quando a mudança ocorreu?

O servidor guarda versões dos arquivos e envia o diff no reload. Ele guarda um snapshot dos blocos do doc em localStorage a cada visita e faz um diff LCS na próxima carga — tudo client-side. Ele compara o mtime do arquivo com a hora do último clique.

✅ O baseline é a sua última visita, não o estado do servidor — sobrevive a restarts e a mudanças offline.

6. Qual é o papel do debounce de 150 ms no reload.js do servidor?

Colapsar os múltiplos eventos que alguns SOs (notoriamente o Windows) disparam para um único save. Aguardar o editor terminar de gravar antes de ler. Limitar a taxa de requisições ao /__manifest__.

✅ Um save no Windows pode gerar vários eventos de watch para o mesmo arquivo; o timer por caminho garante um único broadcast por save real.

7. No export estático, o que acontece quando alguém abre /guides/api.html direto na barra de endereço?

404, porque não há servidor para o deep link. Recebe o doc puro, sem sidebar — limitação conhecida. Um bootstrap injetado no <head> detecta que é a janela top e pula para /?p=guides/api.html; o shell pega o parâmetro e abre o doc no iframe com a sidebar.

✅ O deep-link bootstrap (inject.js) + o tratamento de ?p= no nav.js fazem o bounce — âncoras preservadas.

8. Onde vivem o título, favicon, ordem manual e ícones de pastas de uma docs?

Em variáveis de ambiente do servidor. No _config.json da pasta (que absorve os legados _icons.json/_order.json na primeira escrita); o manager também guarda o layout do mural no registry. Em cada arquivo HTML, numa meta tag.

✅ Config por pasta em _config.json (lido a cada request — hot reload), layout do mural em ~/.docs-in-html/registry.json. No export, tudo vai assado no output.

9. Por que a detecção de "esta página é um shell" usa regex de contexto de tag, e não um simples includes('id="docList"')?

Porque uma página pode só mencionar id="docList" em prosa ou código de exemplo (como este doc!) — e seria enganada. Por performance: regex de tag é mais rápida. Porque o HTML pode estar minificado.

✅ A regex exige uma tag real (<... id="docList">). O mesmo cuidado vale para detectar pan/zoom próprio antes de injetar o mermaid-zoom.

10. O scan.js encontra uma pasta com um _config.json que não é do docs-in-html. Como ele decide?

Importa mesmo assim — false positives são inofensivos. Aborta o scan inteiro. Só considera "nosso" um _config.json que parseia e tem ao menos uma chave conhecida (title, favicon, sidebarAnim, icons, order).

✅ O filtro semântico descarta arquivos homônimos de outras ferramentas. E o scan é só import: depois disso o registry é a fonte da verdade.
