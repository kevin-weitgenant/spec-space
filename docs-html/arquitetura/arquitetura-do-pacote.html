1Visão geral

O pacote inteiro em cinco frases; o resto do doc só detalha o que elas resumem.

⚡ Em 30 segundos
  1. spec-space é um servidor de docs zero-build: você escreve HTML puro, ele entrega as páginas enriquecidas na hora (sidebar, reload, edição, diff, zoom).
  2. O servidor tem 4 camadas em src/: cli (comandos) → server (HTTP) → domain (as regras) → env (a única porta pro mundo).
  3. O browser recebe scripts injetados de client/ a cada resposta — a página ganha vida sem build nenhum.
  4. Tudo é testável porque efeitos colaterais moram atrás de duas costuras: o seam env/ops.js e o rodapé require.main da CLI (45 testes, zero deps, sem disco/rede/browser).
  5. Um manager serve N pastas num processo só (:4400), e o export congela tudo em estático para publicar.
📋 Dois documentos, duas perguntas
Este responde "como funciona por dentro". Para "o que o pacote oferece" (features pela jornada de uso), veja ✨ Features. Para o mapa completo dos testes, 🧪 Testes.
Rampa para iniciante (pode pular) — siga a vida de um comando, em três passos: ① você digita spec-space docs/ — o cli decide o destino: manager já no ar? registra lá. Senão, sobe um servidor. ② cada request que chega cai no server (roots.js), que pergunta ao domain ("qual é a árvore? qual o título? como é o shell?") e monta a resposta. ③ a resposta sai com scripts do client/ injetados no HTML — a página ganha vida (sidebar, reload, edição). E atravessando tudo: qualquer toque no mundo externo (arquivo, processo, relógio) passa pela única porta env/ops.js.

2Camadas — como um pedido atravessa o pacote

Cada camada conta a mesma história em três blocos: o problema, a ideia, onde vive.

🌍 env/ops.js — a única porta pro mundo

O problema

Nove módulos usavam node:fs direto; abrir-no-OS existia em 4 cópias; testar qualquer coisa exigia disco real, processos reais, home real.

A ideia

Uma costura única: todo efeito colateral (fs, spawn, home, abrir URL/caminho) passa por src/env/ops.js. Em produção, o adaptador default envolve o Node; em teste, ops.setOps(fakeOps) troca o mundo inteiro por uma imitação em memória — e resetOps() devolve o real.

Onde vive

src/env/ops.js · consomem: roots, reload, serve, manager, registry, scan

server/* + domain/*→ env/ops.js→ fs · spawn · clock · home
O Proxy, os métodos e por que setOps() vale globalmente

O module.exports é um Proxy que delega sempre ao adaptador corrente — então setOps() vale até para módulos que capturaram ops no require. As assinaturas espelham o node:fs: migrar um call site é um rename, não um rewrite.

Além do fs, a costura expõe: homeDir() (registry e scan); spawn(bin, args) (processo detached fire-and-forget); execFile (resolução do binário do Warp); openPath(abs) (reveal — Explorer /select, Finder -R, Linux abre o pai — escrito uma vez só); openUrl(url) (start/open/xdg-open conforme o SO).

É por aqui que os testes simulam EADDRINUSE, um manager no ar ou um disco inteiro sem tocar em nenhum deles.

⌨️ cli/serve.js — programa e biblioteca ao mesmo tempo

O problema

O CLI inteiro era efeito colateral de require: argv no top-level, process.exit() em 4 pontos. Requerer serve.js num teste ou matava o runner ou subia um servidor de verdade.

A ideia

Requireable: parseArgs(argv) pura (o -h vira mode:"help" — decisão como dado) e main(args, deps) que devolve o exit code em vez de chamar exit. Todo efeito colateral mora atrás do rodapé if (require.main === module) — requerer é silencioso.

Onde vive

src/cli/serve.js (bin do package.json) · testado por serve-args e serve-port

🔌 Portas honestas: dica vs. exigência
Sem --port, a padrão (8000 ou $PORT) é uma dica: ocupada, cai para a próxima livre com aviso, até MAX_FALLBACKS = 20. Com --port explícito é uma exigência: ocupada, morre com erro claro — nunca troca em silêncio.
Comportamentos do modo serve e subcomandos

Delegação: pinga o manager primeiro; se está no ar (e sem --no-register), registra a pasta via POST /api/add, imprime o link e nem abre servidor — com aviso se --port foi ignorado.

Auto-scaffold: primeiro serve de uma pasta sem _config.json cria um com defaults amigáveis. Higiene: registry.add silencioso; server.on("close") fecha o watcher.

Servidor vivo resolve undefined: quando o serve sobe de verdade, main resolve undefined — o footer não faz exit; o server mantém o processo vivo.

Subcomandos: init, export e manager são requires + retorno (manager mantém o processo vivo; os outros devolvem exit code ao footer). --unregister remove do registry e sai.

🖥️ server/roots.js — um contexto por pasta

O problema

Toda a lógica de segurança e bookkeeping de uma pasta de docs vivia closure-private atrás de um (req,res) cru — a maior quantidade de código não-testado do pacote, duplicada entre serve e manager.

A ideia

createRoot(root, {base}) → { handle, reload }: cada endpoint /__*__ é uma função nomeada (ctx, req, res), despachada por uma tabela declarativa ENDPOINTS — toda a superfície HTTP especial num relance. Dois consumidores (serve e manager), um handler: a correção se escreve uma vez.

Onde vive

src/server/roots.js + seus assessores de domain/

serve.js· manager.js→ createRoot(root, base)→ manifest · config · shell · inject

O módulo também exporta as peças testáveis: readJsonBody (JSON com cap de tamanho — default 4 KB), safeRelPath ("guides/v2" → válido | null: sem .., sem \, sem nomes esquisitos), resolveIn, ENDPOINTS, MIME e send — unit-testáveis sem subir servidor.

As decisões que atravessam o módulo

O contrato #docList — o shell é reconhecido por estrutura (uma tag real com id="docList"), não por URL; a regex de contexto de tag não é enganada por prosa (como neste doc!).

Injeção em tempo de resposta — nenhum arquivo em disco é transformado no dev; a lógica de quais scripts entram (src/domain/inject.js) é compartilhada com o export. Toda tag carrega data-injected — é assim que o editor devolve o arquivo limpo.

Deep links sem recursão — navegação top-level para /pasta/doc.html (Sec-Fetch-Dest: document) devolve o shell em volta; o iframe pede de novo com iframe e recebe o doc puro. Sem o header (curl), doc puro também.

O servidor nunca confia no cliente — guardas de caminho em todos os endpoints, JSON com cap, HTML sempre no-store, estáticos bloqueados fora da pasta (403), %-escapes malformados → 400.

Config lida a cada pedido — _config.json muda título/favicon/ordem/ícones com hot reload; config.js também mora nele o humanize() (Unicode-aware) e o applyShellConfig().

Assessores do domain — manifest.js (buildTree: só pastas e .html/.htm, esconde dotfiles/_/index.html, pastas vazias mantidas, order fixa a ordem, cada doc carrega mtime pro "dot verde"); reload.js (ops.watch recursivo com debounce de 150 ms, timers e watcher unref()ados, broadcast SSE em /__reload__; sem fs.watch, degrada graciosamente).

3Ecossistema multi-docs

Servir pastas uma a uma para de escalar no segundo projeto: o manager serve todas as suas docs num processo só.

Rampa para iniciante (pode pular) — imagine cinco projetos, cada um com sua pasta de docs. Em vez de cinco servidores (cinco portas, cinco terminais), o manager é um único servidor em :4400 que conhece todas as pastas. O slug é o "apelido de URL" derivado do título (/my-project-handbook/), e o registry é um arquivinho no seu home (~/.docs-in-html/registry.json) com as pastas, slugs e o layout do mural.
O problema

N projetos = N servidores, N portas para decorar, N terminais abertos.

A ideia

Um handler, N instâncias: o manager não reimplementa nada — cria um contexto roots.js por pasta e roteia por prefixo de slug (reescreve req.url e chama ctx.handle), sincronizado com o registry a quente. Servir uma pasta nova = registrá-la (o CLI até delega e nem sobe servidor).

Onde vive

src/server/manager.js · delegation.js · domain/registry.js · domain/scan.js · UI em client/manager.html

🔑 Uma conexão SSE por browser
Todos os roots faneeam eventos num hub único: uma conexão SSE por browser, não uma por root. A mensagem carrega { base, path } — cada tab filtra o seu. Com 10 tabs e 5 docs há 1 conexão, não 50.
API do manager, Warp e as peças do registry

Slug do título — /my-project-handbook/ do title; colisões ganham -2; api é reservado.

API — /api/ping, /api/docs, /api/add, /api/remove, /api/layout (atômico e sempre saneado — saneLayout poda órfãos, grupos vazios, e acrescenta docs novas no fim), /api/reveal, /api/open-warp, /api/scan. POSTs exigem Content-Type: application/json — um form cross-origin não consegue setar isso, bloqueando chamadas drive-by. Reveal/Warp só agem sobre pastas registradas.

Warp — resolveWarp(): $WARP_BIN → locais padrão por SO → PATH, com cache por processo; no Windows o caminho vira URL file:// (o Warp parseia argumento posicional como URI).

registry.js — arquivo corrompido é backupeado e resetado; layout do mural revalidado contra os docs reais; o manager persiste a própria porta ao subir (a delegação funciona mesmo sem a env var).

delegation.js — pingManager() nas portas candidatas (env > registry > 4400) com timeout curto; addToManager() devolve o slug escolhido.

scan.js — importa em lote: acha pastas com _config.json que "pareça nosso" sob o home, com skip-list e profundidade máxima.

4Clientes do browser

Scripts injetados nas páginas, servidos de /__docs__/*. Três princípios atravessam todos: identidade por estrutura (não por URL), comunicação via eventos DOM, UI própria marcada data-injected.

Rampa para iniciante (pode pular) — UMD é um modo de escrever JavaScript que funciona tanto numa tag <script> no browser (publicando, p.ex., window.DIFF) quanto via require() no Node — o MESMO arquivo roda na página e nos testes. SSE é um canal onde o servidor empurra eventos sem que o browser pergunte — é o trem do live reload.

A ordem de injeção

lib.js→ reload.js→ nav.js (shell)| edit.js→ diff.js→ changes.js· mermaid-zoom?

lib.js sempre primeiro, dev e export: é o módulo de identidade que os demais consomem (window.docsLib). No manager, um <script> define DOCS_BASE; no export, DOCS_EXPORT (e nada de reload). Shell ganha nav.js; doc não-shell ganha edit.js + diff.js + changes.js (todos defer, diff imediatamente antes de changes — o changes consome window.DIFF). mermaid-zoom.js pela heurística (blocos .mermaid, <figure> ou .panzoom/.diagram/.zoomable, sem pan/zoom próprio).

client/lib.js — o módulo de identidade (UMD)

A interface cabe num cartão-postal: me(pathname?, base?) → caminho relativo ao root da docs (tira a barra inicial, tira o prefixo do manager case-insensitivamente, cai em index.html); api(path, body?) → fetch POST com BASE_N + path e corpo JSON (tratamento da resposta fica com cada chamador); isShell() → !!document.getElementById("docList"); BASE/BASE_N → window.DOCS_BASE cru e sem barra final.

Esse bloco "quem sou eu?" era copiado em reload.js, changes.js e edit.js; o wrapper de fetch vivia em nav.js e edit.js — agora mora aqui, uma vez só.

client/diff.js — o núcleo puro de diff (UMD)

Extraído de changes.js para ser testável com node:test (sem DOM, sem window, sem localStorage). Os algoritmos foram copiados ipsis litteris, com duas diferenças conscientes: o guard UMD no rodapé e marks() recebendo a lista de textos novos como parâmetro, fechando sua única impureza.

Dentro: diffOps(a, b) — LCS com trim de prefixo/sufixo comuns (docs grandes demais, > 4M células, degradam sem marcação) — e wordDiff — diff por tokens para o word-diff dentro de um bloco editado.

client/nav.js — a sidebar viva

Busca /__manifest__ (ou /manifest.json no export) e renderiza a árvore: pastas colapsáveis com memória em localStorage, ícones Lucide embutidos + emoji, animação configurável, ordem manual por drag & drop, doc ativo + ancestrais expandidos, URL com pushState/popstate, tab title "Doc · Site", esconder sidebar.

Assinatura da árvore: a cada mudança re-busca o manifest, mas só reconstrói o DOM se o conjunto de arquivos mudou. Gerenciamento: menu kebab "⋯" (copy path, copy full path, reveal, move-to, delete com confirmação em dois cliques), menu de contexto (new folder, collapse all), rename inline, drag & drop — tudo pelos endpoints POST /__*. No export: read-only + deep link /?p=.

client/reload.js — quando recarregar (e uma conexão só) · o fluxo completo

HTTP/1.1 permite ~6 conexões por origem — um SSE por tab travaria a 7ª. As tabs elegem um líder via Web Locks que mantém a única conexão SSE e re-transmite todos os eventos crus por um BroadcastChannel; cada receptor filtra pelo seu root e decide com shouldReload(): meu arquivo mudou → recarrega; sou o shell → só eu mesmo (preserva a sidebar); .js/.css compartilhado → o doc em exibição recarrega. A tab líder fecha? O lock passa adiante.

edit.js · changes.js · mermaid-zoom.js · manager.html

edit.js — botão "✏ Editar" (Ctrl+E) liga contenteditable; Ctrl+S grava via /__save__ (clone do body com tudo que é data-injected removido; pre/code como texto puro; estado dirty no botão; beforeunload com mudanças pendentes).

changes.js — achata os blocos do doc, diff LCS contra o snapshot do localStorage da última visita, marca diferenças (chip "novo"; word-diff com o velho riscado), sobrescreve o snapshot. Minimap estilo VS Code, favicon com ponto azul + "● " no título (sinais no window.top), pílula "N mudanças · ↓ próxima · ✓ já vi tudo". Consome window.DIFF.

mermaid-zoom.js — lightbox pan/zoom com event delegation + pseudo-elemento CSS (sobrevive aos rewrites do Mermaid) e lista INTERACTIVE (nunca sequestra SVG em button, a, [onclick], label, summary). Carrega svg-pan-zoom do CDN sob demanda.

manager.html — o mural de cards: título + favicon por docs, pastas/grupos com drag & drop persistido via POST /api/layout, ações Warp/reveal/remover, botão Escanear.

5Publicação estática

O que o servidor decide por requisição, o export decide UMA vez e escreve em disco.

Rampa para iniciante (pode pular) — um site estático é um punhado de arquivos entregues por qualquer servidor burro (ou de graça: Surge, GitHub Pages) — sem Node rodando. O export "congela" a experiência do modo dev; o preço: nada que precise de servidor (editar, apagar, live reload) existe no estático.
O problema

Publicar as docs sem carregar um Node junto — e sem perder sidebar, ordem, ícones e deep links.

A ideia

Decidir de antemão tudo que o dev decide por request e escrever em disco: arquivos puros, zero servidor, prontos pra surge dist. run(root, outDir) também é requireable (pasta inexistente lança; o footer imprime + exit 1).

Onde vive

src/cli/export.js, usando buildTree e injectScripts(staticMode) do domain

copia a pasta
(pula _config.json + legados)→ manifest.json→ client/ → __docs__/→ shell garantido→ reinjeta cada .html
🔗 Deep link no estático
No modo estático, o inject.js adiciona ao <head> de todo doc o bootstrap de deep link: doc aberto direto na janela top pula para /?p=<path> (âncora preservada), e o shell abre o doc no iframe. Também define window.DOCS_EXPORT = true — o nav.js entra em modo read-only e edit/changes nem são injetados.
🧪 E os testes?
7 suítes em tests/ rodando com node --test puro (45 testes, zero deps) — a arquitetura existe para que eles não precisem de disco, rede nem browser. O mapa completo, suíte por suíte, está no doc dedicado: 🧪 Testes do Pacote.

6Glossário de domínio

O vocabulário que o resto do doc usa sem re-explicar.

seam (costura) — ponto do código onde uma peça pode ser trocada sem mexer em mais nada; aqui: a fronteira com o mundo exterior (fs, processos).
adapter — implementação de um lado do seam: o Node real em produção, uma imitação em memória nos testes.
módulo profundo — faz UMA coisa bem, esconde os detalhes, mostra uma interface pequena — aparelho de som com poucos botões.
requireable — arquivo que funciona como programa E como biblioteca; efeitos colaterais atrás de if (require.main === module).
UMD — mesmo arquivo JS na tag <script> (publica no window) e no require() do Node (module.exports).
SSE — Server-Sent Events: canal onde o servidor empurra eventos ao browser sem polling.
root — uma pasta de docs servida; contexto criado por createRoot.
shell — a página com id="docList"; o contrato estrutural do layout.
doc — um .html da pasta, renderizado no iframe do shell.
manifest — árvore JSON (docs/pastas/ordem/mtime) que alimenta a sidebar.
registry — ~/.docs-in-html/registry.json: pastas conhecidas + layout do mural.
slug — apelido de URL derivado do título da docs (/my-project-handbook/).
mural — página de cards do manager com grupos e ordenação.
data-injected — marca em toda UI injetada pelo dev server; o editor a remove ao salvar o arquivo limpo.

7🎯 Quiz

Cinco perguntas para checar se o porquê das decisões ficou claro — clique numa resposta; pode tentar de novo à vontade.

1. Por que o projeto concentra todo acesso a fs/processos num único módulo src/env/ops.js?

✅ C. A costura existe a serviço da verificação: um único ponto de troca (o Proxy delega ao adaptador corrente) simula EADDRINUSE, manager no ar ou um disco inteiro nos testes, sem efeitos colaterais.

2. Para que serve o rodapé if (require.main === module) em src/cli/serve.js?

✅ B. Sem o footer, o simples require("./serve") num teste já dispararia o servidor. Com ele, parseArgs/main viram funções puras importáveis; o "modo programa" fica atrás da guarda.

3. Por que o src/domain/inject.js garante que diff.js seja injetado imediatamente antes de changes.js?

✅ A. diff.js (UMD) anexa window.DIFF; changes.js depende dele para diff LCS e word-diff. Injetados com defer na ordem certa, a execução respeita a dependência.

4. O que a tabela declarativa ENDPOINTS em src/server/roots.js compra, na prática?

✅ D. A tabela é sobre legibilidade e verificabilidade, não performance: um relance mostra cada rota, método e handler; revisar segurança e escrever roots.test.js contra ENDPOINTS fica trivial.

5. Por que lib.js precisa entrar primeiro, em toda página — no dev e no export?

✅ B. Antes do lib.js, cada cliente copiava seu próprio bloco "quem sou eu?". Agora ele entra primeiro (dev E export) e publica window.docsLib — a pergunta de identidade é respondida uma vez só, para todos.
